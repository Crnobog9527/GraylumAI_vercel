# CORE-PATH-V2：旧路径 100 人公平压测基线（2026-10-28）

计划 `docs/launch/tasks/CORE-PATH-V2.md` 3.2 节第 7 条要求：切换前用同一桩、同一账号池对现有路径跑一次存档。本文是那一次。
结论先说：**旧路径在 staging Micro 上撑不住 3.1 节的通过线；50 人以内基本不出错，75 人起开始出现 57014 和"工作空间服务暂不可用"，100 人失败率 13%–27%。**

## 1. 怎么跑的（以及哪些地方不同于最终验收）

| 项 | 实际做法 |
|---|---|
| 数据库 | staging Supabase（Micro、PostgREST 连接池 8）。`runtime_rw_v2` 行不存在（DB-RW-A/B/C 的开关全关 = 旧路径） |
| 应用 | **本机** `next start`，代码 = staging `edabecfb4`（含 DB-RW PR-A/B/C，开关关），连 staging 库；不是 Vercel 上的部署 |
| 模型 | 仓库压测桩 `scripts/loadtest/openrouter-stub.mjs`（1.5 秒首字、每 50 ms 一段、约 6 秒回复；教练第一次调用返回 `read_skill_file` 工具调用，第二次约 4 秒；回执 `gen-load-` 开头；Decisions 前置检查答低风险）。本机 fetch 拦截器把 openrouter.ai 的三个路径转发到桩，**其余出口默认拒绝**，只放行桩（127.0.0.1）、staging Supabase、本机假 Redis；另在 DNS 层拒绝所有付费供应商域名 |
| 限流 Redis | 本机假实现（总是放行），不是 Upstash——与之前所有 DB-PERF 压测一致，所以限流不会成为失败原因，也意味着限流本身的开销没测 |
| 计费模式 | `staging_test`，每档新建一个测试窗口（`max_calls` 1000、`all_actors`），`runtime_payg_staging.windowId` 指向它 |
| 账号 | 100 个全新测试账号（本批现注册，每档重复使用同一批；账号池 = 教练 VU 各占一个，其余 VU 一人一个），新账号第一次请求时由应用生成档案和开户积分 |
| 节奏 | 混合 chat:coach:library = 5:3:2，每人回复后等 7.5–22.5 秒，每档 2.5 分钟（含 10 秒爬坡） |
| 档位 | 30 → 50 → 75 → 100 → 50（回归）→ 100（复测）；档间冷却 10 分钟（第 3 档与第 4 档之间因一次建窗口失败，实际间隔约 14 分钟） |
| 采样 | `pg_stat_activity` 每秒一次（等待事件、阻塞者、被等待的表）、`pg_locks` 每个后端的关系锁数；Supabase 指标 API 每 30 秒一次（CPU、内存、交换区） |

**拦截器验证（跑之前做的，结果在 `fake-provider.jsonl` 里）**：向 `openrouter.ai/api/v1/models` 发请求被拒绝（`refused openrouter path`）；向 `api.openai.com`、任意其他域名被拒绝（`refused host`）；`dns.lookup('openrouter.ai')` 返回 `ENOTFOUND`；桩没起时向 openrouter 的聊天地址发请求得到本机 `fetch failed`，不会走到真实地址。压测期间（08:20 之后）拦截器没有记录到任何 `refused` / `dns_refused` 事件，即没有任何代码试图访问被拒绝的出口。这只能证明本进程的 fetch 和 DNS 解析被限制，不证明所有网络出口都被限制。

不同于最终验收的地方：本机 Mac 同时跑 Next、压测驱动、桩和采样，客户端侧延迟含本机开销；Redis 是假的；桩有上述教练多轮缺陷；CPU 采样每档只有 2–4 个点（指标 API 30 秒一次），**CPU 数字只作量级参考**。

- 每次请求的数据库往返（应用侧计时，`rt`）：14–16 次/请求，一轮对话 = 一次流式请求 + 一次读取。

## 3. 对照 3.1 节通过线（100 人一行）

| 通过线 | 旧路径实测 | 是否通过 |
|---|---|---|
| 失败 0、57014 0 | 失败 13%–27%，57014 16–18 次/档 | 否 |
| 整轮 p95 ≤ 桩回复时间 + 2 s（约 8 s） | 100 人 161–167 s；30 人也 47.5 s | 否（含教练多步和排队） |
| 数据库 CPU 平均 < 60% | 样本太少（2–4 点），均值 41–51%，峰值 61–88% | 无法判定 |
| 交换区不涨 | 约 470–490 → 820–990 MB | 否 |
| `LWLock:LockManager` < 2% | 1.2%–4.4%（50 人一档 4.4%） | 临界；不是失败主因 |

最多撑多少人：**约 50 人（0 失败）**；75 人起不达标。差距：失败率 ≥ 12%，admit 阶段 mean 15–28 秒（目标是回合整体 8 秒以内）。

## 4. 这次看到的几件事

1. **行锁等待 16%–22% 集中在 `runtime_test_windows` 这一张表**（采样里 `tuple` 等待的被等待表：30 人档 200 次采样、100 人档 960 / 1320 次）。这是 `staging_test` 模式下所有权限检查和 `bill2_payg_claim` 对**同一个测试窗口行** `FOR UPDATE` 的结果；正式环境的 `production` 模式不走这行。因此 staging 压测在这条路径上比正式环境更差，3.1 节"全站共用行 0"的静态扫描应把它算作旧路径独有。
2. 每次 admit 持有的关系锁随人数上升（91 → 125–135），符合"持锁时间变长"。
3. 本批 CPU 采样只有 2–4 点，计划 3.3 的"每轮核·秒 k"只能给量级：约 **1.5–2.1 核·秒/轮**（CPU 均值 × 2 核 × 档时长 / 回合数；与 3.3.1 用的 1.15 同量级，偏大）。这个数要等新路径的完整采样（每 5 秒）才有意义。
4. 一次基础设施事故：第 4 档开始前创建测试窗口的 Supabase CLI 调用失败一次，批次中断，约 10 分钟后用重试版本接着从第 4 档续跑；前三档数据有效。

5. **压测桩的一个缺陷影响了这次基线（审查发现，已在 PR 里修复，基线未重跑）**：跑基线时的桩用"消息里有没有工具结果"判断是不是教练的第二次调用，而教练会话会把以前各轮的工具结果留在历史里，所以**同一教练会话从第二轮起，桩直接返回短文本，不再调用 `read_skill_file`，教练回合少了一次文件读取和一次模型调用**。对基线的影响：教练回合（占 30%）从第二轮起的数据库工作量和时长被低估，整轮延迟偏短；聊天和资料库不受影响。影响多大没有量化；修复后的桩只看最新一条用户消息之后的工具结果。如果要把基线当精确数字用，需要在修复后的桩上重跑一批。

## 5. 复现与恢复

- 驱动与采样脚本（`load.mjs`、`lockwatch.sh`、`dbmetrics.mjs`、拦截器）在本机、不进仓库（含 staging 登录辅助）；桩、账号重置脚本、预算与闭包检查在 `scripts/`。
- 跑完恢复：`runtime_payg_staging` 与跑前备份逐字一致（读回确认）；本次创建的所有测试窗口已停用（启用中的窗口回到 3 个）；`runtime_rw_v2` 行保持不存在；本批 100 个测试账号及此前的 110 个压测账号全部已封禁。
