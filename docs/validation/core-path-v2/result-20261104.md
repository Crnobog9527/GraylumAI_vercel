# CORE-PATH-V2：新路径 100 人复测结果（2026-11-04 UTC，V2-13 第四次跑）

计划出处：`docs/launch/tasks/CORE-PATH-V2.md` 3.1、3.2；运行计划 `vercel-run-plan.md`；上一批 `result-20261101.md`（本机应用）。
这是第一次在真 Vercel 部署上跑整套（第 6 档被驱动中止，本批作废，见结论 3）。单机 500/2000/5000 外推（3.3.3）这次没做。

**结论（先写）：**
1. **数据库/基础设施没有成为瓶颈。** 30 → 100 人五档（第 6 档未采样）：
   - 实例连接峰值 26（线 45），事务内空闲最长 0.012 秒，`LWLock:LockManager` 0。
   - 57014 为 0，429 为 0，Redis 不可用 0，资料库读取 0 失败。
   - 账目每档都平：失败回合扣 0，预占没有新增。
   - 压过 100 人后回落到 50 人，比同样 50 人的第 2 档还快。
2. **失败和变慢全部来自应用自己的在途上限。** 每个模型最多 20 个在途调用（代码里写死，`quote.ts` 的 `DEFAULT_MODEL_CONCURRENCY`）。
   - 75 人档失败 4，100 人档失败 26，第二次 100 人档失败 19 后被驱动中止，全部是 `TURN_PROVIDER_BUSY`。
   - p95 变长是排在后面的调用在等名额：主模型调用中位数不变，p95 多 3–8 秒。
   - 上限已由 #1733 改成按模型配置、默认 150，需要重跑验证。
3. **这批按规则作废，不能当验收结论。**
   - 采样覆盖检查是 NOT COVERED：采样器设 4800 秒，整套约 95 分钟，第 6 档没采到。
   - 失败 0、p95 ≤ 8 秒两条线没过。
   - 数据库 CPU 和交换区还没取得。
   - 总控安排上限修好后用 `SAMPLE_SECONDS=6000` 重跑整套，结果补进本文件。

## 3. 两类原因分开

### 3.1 应用自己的在途上限（全部失败、大部分变慢）

- **机制：** `packages/api/src/services/turn/limiter.ts`。每个模型的在途调用记在 Upstash 的一个计数里，跨实例共用，键是 `model:<ai_models.id>`。超过上限就退避重试，最多 10 秒，然后报 `TURN_PROVIDER_BUSY`。
- **上限值：** 本批用的是 `quote.ts` 的常量 20（#1733 前）。
- **撞上限的模型：** 主模型 gpt-6-luna，它同时承担自由对话的主调用和教练每轮的前两个调用。教练的整理调用用 claude-sonnet-5.5，单独计数，没有撞到。
- **75 人档主模型"已发起、未结束"的调用数（含排队），每 5 秒取一点：**
  - 刚开始那一波 51 个，下一个点 40 个。75 人同时开跑，远超 20 个名额。
  - 之后稳定在 11–22 个，大多数时候 15–19 个，已经贴着上限。
  - 这一档的 4 个失败都是开头那一波。到 100 人档，失败分布在约 91 秒内，说明稳定阶段的需求也已超过 20。
- **用桩的固定时长证明变慢是排队：** 桩每次回复的时长是固定的，所以超出部分就是在等名额。主模型每次调用从发起到结束：

  | 调用 | 第 1 档（30 人）中位数 / p95 | 第 4 档（100 人）中位数 / p95 |
  |---|---|---|
  | 自由对话主调用 | 6.08 / 6.13 秒 | 6.20 / 14.11 秒 |
  | 教练第 1 个调用 | 1.60 / 1.67 秒 | 1.71 / 6.78 秒 |
  | 教练第 2 个调用 | 4.09 / 4.27 秒 | 4.12 / 7.27 秒 |

  - 中位数几乎不变，说明网络、桩和数据库都没变慢。
  - p95 多出来的 3–8 秒，就是排在后面的调用在等名额。
  - 自由对话主调用 p95 14.1 秒，加定位判定约 0.4 秒，加回合外约 2.2 秒（见第 4 节），约等于整轮 p95 17.3 秒。
- **换真模型会更严重：** 真模型的回复比桩长，同时需要的名额 ≈ 每秒新增调用数 × 每次调用时长。
  - 75 人档每秒约 3.6 个主模型调用，用桩时约 18 个在途。
  - 回复时长是桩的 2–4 倍时，100 人约需 50–100 个名额。
  - 上限 20 会大面积繁忙。#1733 改为按模型配置（`runtime_payg.modelConcurrency`），默认 150，等名额仍是 10 秒。

### 3.2 数据库 / 基础设施（没有瓶颈）

- **连接和等待（第 1–5 档）：**
  - 实例连接峰值 26/45；执行中最多 7。
  - 等待事件采样里只出现过零星的 CPU（最多 9/29）和 IO:WalSync（最多 2/29），没有锁等待，`LockManager` 0。
- **没有后遗症：** 回落档（第 5 档，50 人）p95 11.3 秒、首字 6.7 秒，比第 2 档（同样 50 人）的 13.4 / 8.8 秒还快。压过 100 人后，连接池和数据库都没有留下问题。
- **authenticator 连接数：** 见上表；Pool size 实际控制什么列进"上线后再看"。
- **其他基础设施：** Vercel 函数地区一直是 pdx1，和数据库同区；Upstash 没有超时（0 次 `TURN_PROVIDER_LIMIT_UNAVAILABLE` / `rate_limit_unavailable`）；桩在 Vercel 上没有出错，2,881 个模型调用里 2,832 个成功、49 个按设计未发送。
- **还缺：** 数据库 CPU 和交换区，待截图。这是唯一还没取得的数据库侧证据。

## 4. 每轮应用内开销（总控 11-04 要求单列）

数据来源是库里每个回合各步的时间戳。样本是校准加第 1 档的 111 个完成的自由对话回合，那时还没有排队。下表为各步中位数：

| 段 | 时长 |
|---|---|
| 开轮 → 发出定位判定 | 0.04 秒 |
| 定位判定（桩 0.3 秒 + 往返） | 0.38 秒 |
| 判定结束 → 发出主模型调用 | 0.10 秒 |
| 主模型调用（桩 6.0 秒 + 往返） | 6.08 秒 |
| 拿到结果 → 收尾结算 | 0.03 秒 |
| **开轮 → 收尾合计** | **6.64 秒**（p95 6.89） |

- **回合内部，应用自己只花约 0.17 秒**，其余是桩时间和定位判定。
- **定位判定约 0.4 秒**，只有没确认定位的账号才有。压测账号全都没有定位，所以每轮都带着它。
- **回合外约 2.2 秒：** 驱动看到的整轮中位数 8.8 秒减去回合内 6.64 秒，和校准算出的"额外 2.32 秒"一致。这一段包括：
  - 开轮之前：登录核验、限流、读设置与报价、各项检查；
  - 结果送回驱动；
  - 驱动经美国代理到 Vercel iad1 的网络往返。

  库里看不到这一段，要在应用里加分段计时才能拆到具体哪一步。这是除在途上限外的头号优化目标。11-04 第一次用本机隧道自检时，这一段约 4 秒，现在桩在 pdx1，降到约 2.2 秒。
- **所以"p95 ≤ 8 秒"这条线在 30 人、没有排队时也过不了：**
  - 自由对话：桩 6 秒 + 定位判定 0.4 秒 + 回合外 2.2 秒 ≈ 8.6 秒（中位数）。
  - 教练：三次调用串行，桩合计约 6 秒以上。

  要过线，需要两件事之一：压掉回合外开销，或者让定位判定不在每轮都跑（真实老用户本来就不跑）。另一种做法是把判定线改成"桩回复 + 判定 + 2 秒"，这属于判定标准的改动，要总控 / Owner 定。

## 5. 上线后再看

- Supabase Data API 的 Pool size（后台显示 8）实际控制什么：本批 authenticator 查询连接到过 12，全部空闲、在轮换（总控 11-04）。
- 等名额最多 10 秒要不要放长（例如 30 秒）。这是"慢一点但不失败"的体验取舍，要 Owner 定。
- 资料库读取 p95 约 2 秒（list / search 各一次 tRPC）：没有失败，但比回合内开销大一个量级，值得单独看。
- 回合外约 2.2 秒的分段计时（见第 4 节）。
- 驱动正式改进（复测后提 PR）：
  - 续期与密码登录的返回码分开记；
  - 逐个续期、429 等待；
  - 文档写明 staging 登录有 hCaptcha、密码兜底无效；
  - 采样时长按整套实际用时设（这次 4800 秒不够）。
