# FUSION-COMPARE 停止扣费一致性修复

目标：停止后每列费用、对比合计和个人中心积分记录与账本实际消费一致。
验收：已产生用量的停止列按已用量计费并正确显示；零用量列不收费；总计等于各列费用及流水净额。
范围：定位费用与页面不一致、修复同范围问题并补先红后绿回归；不改变定价、权益或已有扣费规则，不操作 staging，不调用付费模型，不自行合并。

## 定位与改动

- 只读核对测试站案例：两列各扣 10，共 20；GPT 列虽未保存回答，已确认输入 2,477、输出 2,644，按原规则收费正确。
- `bill2_cancel` 的 `closed=true` 表示关闭新调用，不保证费用已结算。原页面按它停止轮询、释放冻结提示和显示最终总计，会漏掉晚到回执确认的费用。
- 页面改以 `closed=true` 且费用状态为 `settled/refunded` 收口，等待费用确认；使用同一列快照计算合计，优先使用包含补偿的净扣费，停止提示不再把“没有保存回答”等同于免费。
- 每次出现新的已结算列，失效余额、积分摘要和积分记录缓存，复用现有查询读取新流水。
- 积分记录读取失败时明确显示失败及重试按钮，不显示空列表或“共 0 条”；读取中也不显示确定的条数。
- 使用现有测试账号只读调用实际 `getCreditTransactions({limit:50, actualOnly:true})`：HTTP 200、总计 360、当前页 50 条，包含本次两笔 -10 的实际消费且不含它们的预留/释放。已有过滤符合 Owner 决定，无须改账本、权限或数据库。

## 回归与验证

- 先红后绿：新增“停止已关闭调用，但费用仍 cost_pending”的回归，在旧实现把它误判为失败；修复后正确保持待核对并继续轮询。
- 页面纯逻辑测试 14 项通过；积分摘要重试策略 3 项通过。
- 真实 Chrome 在本地包含本次组件的 HTTP preview 操作，三项通过：点击全部停止后等待晚到结算（两列各 10、合计 20，原空缓存刷新成两笔消费）；零用量列免费且无对应消费；积分记录失败后点击重试恢复实际记录。
- API 相关单元测试 61 项通过，覆盖积分路由、对比读取、单列执行和流式显示。
- 网站/API 类型检查、ESLint、代码大小检查通过。浏览器测试及集成测试均放入现有 CI 入口。
- 新增真实本地数据库集成用例：实际派发后挂起回执，重复/并发停止，观察 closed + cost_pending；晚到回执后并发 finalize，检查只扣一次、零用量列不收费、钱包 = 流水净额 = 合计；以用户权限运行实际过滤，并验证读不到其他用户记录。
