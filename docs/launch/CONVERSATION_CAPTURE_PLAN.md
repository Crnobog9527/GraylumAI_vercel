## 0. 一句话结论

Owner 2026-10-02 选了方向 B：右侧信息和整理器不再按一条固定的题目顺序走；只要最后 Skill
要求的信息都收齐、整理好，顺序无所谓；右侧内容由导师和用户实际聊到的东西来创建和填写。

这就是 [Master Plan v12 第 3 节](MASTER_PLAN.md) 已经锁定、但还没实现的体验：
"每一步只确认一次"、"笔记只分草稿 / 已确认"、"用户在第一步顺口说出的后面步骤的信息，会被整理进
对应栏目，Agent 之后不再重复问"、"手动改过的内容，整理模型不能覆盖"（第 3.2、3.5 节；第 2.2 节
已把"层级题号 1.1/1.2、只展示已到达的问题、逐题确认"列为被取代的旧规则）。现在的实现仍是逐题模式，
所以 #584 合并后的 staging 验收里出现了"导师已经聊到别的话题，右侧还停在 1.1"。

推荐做法：

1. **清单不变**：Skill 发布包里每一步声明的信息字段，仍是"收齐没有"的标准和报告的结构化输入。
2. **整理改到服务器上写**：服务器在一个事务里完成授权、来源保护和写入。只有"能证明是整理器写的、
   之后没人动过"的字段或"从没有过内容"的空字段才会被直接写；其他一律变成"根据对话整理的更新"，由用户采用或忽略。
3. **导师不再绑定一道"当前题"**：看整份清单，先补当前步骤最有价值的缺口，不再机械拉回 1.1。
4. **确认改成每步一次**：绑定用户看到的整步内容，点一次确认；沿用现有确认流程和数据库规则。
5. **提问卡的答案仍然绑定它回答的那张卡**，0155 不用改。
6. **补充笔记**（Owner 已明确要做）：放在核心修复之后的一对 PR。

## 1. 现状（只读核对的事实）

### 1.1 信息存在哪里

- 每一步的信息存在 `artifact_rounds.steps -> <stepId> -> information`，格式 `{字段id: {status, value, nature}}`。
  唯一的写入函数是 `opc_information`（`packages/db/migrations/0107_opc_workbench.sql:467-490`）：
  - 必须一次写整步的全部字段，带 `expectedVersion` 防并发；每个值最多 400 字，整步最多 12000 字节；
  - 只接受 `status/value/nature` 三个键，**没有任何来源记录**：用户手改、旧页面自动填入的整理结果，
    存下来都一样；
  - 不检查"是否已到达"，不保护已确认的值；每次写入版本号 +1，并让本步和依赖它的后续步骤失效
    （`artifact_invalidate`），在 `artifact_requests` 里留一条不可改的历史记录。
- 读取用 `opc_query`（最新包装链 0134 → 0116 → 0111）：`information[step] = {schema, values, reached,
  previouslyConfirmed}`，另有 `turns[] = {executionId, stepId, questionId, roundId, kind, informationVersion}`。
- 每次导师执行都冻结一份 `scopeMaterial`（`runtime/admission.ts:199`），其中 `content.work.steps` 带着准入
  那一刻各步的信息值、状态和版本号；导师请求的输入里也带着它（`runtimeScopeInput`，`admission.ts:183`）。
  `opc_save_result`（0107:237-248）和 0116 的 `informationVersion` 都从这里取值。这份材料由
  `runtime_work_projection`（最新定义 0139:30-41）生成，**把整份 `r.steps` 原样放进去**；`runtime_material_allowed_before_b1`
  （0139）比较冻结材料和当前投影时，除 `steps` 外逐字比较，`steps` 允许变化。
- "已到达"分两类：
  - **准入权威**：`service.ts:128-191` 用 `opcQuestions.ts` 的 `reachedQuestions` / `displayedQuestion`，
    不在范围内报 `OPC_QUESTION_NOT_REACHED`；
  - **展示和历史投影**：`opc_historical_reach`（0111:19-53），以及页面里的 `reviewableQuestions`、
    `navigatorRows`、`isReviewOnlySelection`、建议采用的过滤（`page.tsx:1921-1923`）和卡片能否回答的判断
    （`agent-turn-display.ts` 的 `questionCardStatus`）。F1 要一并清理后者。
  - 数据库写入路径本身不认"题目进度"。

### 1.2 整理器怎么工作

- 整理器和导师在同一次执行、同一笔计费运行单里：导师回复后，再调一次整理模型
  （`runtime/execute.ts:325-346`，不读会话历史，`historyItems: 0`，输入后面附上导师回复）。
  输出 JSON 存为执行结果的 `summary`，**数据库不解析它**。
- 整理器输入（`service.ts:211-228`）：用户这句话、答过的卡片（五项：question、options、
  selectedOption、selectedIndex、recommended）、`currentQuestion`、`allowedWorkflow`（当前步 + 已确认步，
  且只含"已到达"字段）、`currentStepMaterial`（当前步全部字段的已有值，#584 加的）。
- **真正把整理结果写进右侧的是浏览器**：`page.tsx:626-709` 解析 `summary`，只填这一轮冻结的那道题、
  而且只在那道题为空时填；其他情况变成"导师建议调整"卡片，用户点"采用"才写。写入走普通自动保存
  （`opc_information`）。页面没打开时就没人写；`targetStepId` 指向别的步骤时直接丢弃。

## 2. 目标（验收口径）

沿用 Master Plan 第 3.5 节，本方案负责其中这几条：

1. 用户在任何时候说出的、属于清单里任何一项的信息，回复后几秒内出现在右侧对应栏目（草稿）。
2. 导师不重复问已经记下的信息；跑题时简短回应、顺势补当前步骤最缺的内容，不念题号、不机械拉回。
3. 每一步只点一次确认；确认的是用户看到的那一版；必需项缺失时，确认前明确告诉用户还差什么。
4. 已确认、用户手动改过、或无法证明来源的内容，整理器都不会直接改，只给"根据对话整理的更新"。
5. 撤权、注销或换轮次后，旧执行的整理结果不会再写进草稿。
6. 刷新、断网、重新登录后，右侧内容和确认状态都能恢复；补应用不会再调模型、不重复收费、不计入限流。
7. 页面和数据库不写死某个 Skill 的步骤和问题（工程规范第 6 节）。

v12 第 3.2 节第 4 条的"文字确认"（D10，已锁定）不在本批交付，见第 8 节第 4 项。

## 3. 设计

### 3.1 两层：Skill 清单 + 补充笔记

- **Skill 清单**（权威）：已发布 Skill 的 `workflow.yaml` 里每步的信息字段（`id/title/required/elicitation`）。
  它决定"收齐没有"，也是报告（#547 REPORT-GEN）读取的结构化事实。不改 Skill 格式。
- **补充笔记**：对话里有价值、但对不上任何字段的内容，由整理器记成草稿笔记，挂在最相关的那一步下；
  随这一步一起核对、确认，报告里作为"对话补充资料"使用。
  - 不单独建表，存在 `steps.<stepId>.notes`：`opc_revise` 整份复制 `steps`，修订自动带上；
    0149 的注销已覆盖 `artifact_rounds.steps`；随步骤确认和失效，不出现第二套状态。
  - 最小结构：`{id: uuid, text: ≤400 字, source: "capture"|"user", executionId?, createdAt}`；每步最多 8 条。
    整理器能看到已有笔记，只新增不重复的内容；宿主再按规范化文本去重。用户可以增、改、删；
    用户改过的笔记整理器不再动（和字段同一套保护）。8 条上限不代替整步载荷上限（第 3.8 节）。
  - 账号修订（0134）未改动的步骤会把源步骤的 `notes` 一起复制；已有改动的步骤保留目标轮次自己的。沿用这个现有继承机制，
    不另做改造；B3 对两支分别测试。继承来的 `fieldMeta` 不会让字段变成可直接写（第 3.2.2 节要求本轮的 capture 记录）。

### 3.2 整理怎么写：服务器一个事务完成

**选择：从"浏览器写"改为"服务器写"。** 只放宽浏览器投影会留下三个问题：页面关了就没人写；"手动改过不能
覆盖"需要服务器知道每个字段是谁写的；导师下一轮要看到最新清单才能"不重复问"。

#### 3.2.1 授权和绑定（P1-2）

新增数据库函数 `opc_capture_apply(p_actor_id, p_draft_id, p_execution_id)`，只授予 service role，浏览器调不到。
它自己读执行结果，不接受调用方传入的整理内容。参照 `opc_save_result`（0107:237-248），在**同一事务**里按下面的顺序判断，
每一条执行得到唯一一个结果（统一见下表，正文其他地方都以此表为准）。

**第一组：身份和归属**（不通过就拒绝，什么都不写，包括处理记录——无法确认归属的执行不能在任何项目里留下痕迹）

1. `bill2_actor(p_actor_id)`；草稿属于该用户、`bill2_scope_allowed(..., positioning_draft)` 通过；
2. 锁顺序与 `opc_information` / `opc_save_result` 一致：读 `opc_drafts` → `artifact_projects ... FOR UPDATE` → 读 `artifact_rounds`；
3. 执行的 `session_id` 等于草稿会话、`actor_id` 等于用户。

通过第一组后，这条执行可以安全归属到这份草稿，后面的结果才允许在本草稿项目里留处理记录。

**第二组：能不能处理**（按顺序，命中第一条就停）

4. 执行还没 `completed` → `not_ready`；
5. 冻结的 `attachedOrganizer.input` 不是带 `captureFormat = "v2"` 的 JSON → `skipped_format`（合法的旧格式执行优先得到这个结果，
   不归入拒绝）；
6. 冻结身份不符：没有对应的 `opc_turns` 行（`session_id`、`request_id`、`token = payload.opcTurnToken`）、`purpose` 不是 `mentor`、
   `payload.revisionId` / `moduleId` 与轮次和项目不一致 → `denied_binding`；
7. 执行所属轮次（`opc_turns.round_id` 和 `scopeMaterial.content.work.roundId`）不是草稿的当前轮，或当前轮已不是 `draft` 状态 → `stale_round`；
8. **执行内容当前不可读**：`runtime_history_available(e.id)` 为 false（0158 定义：执行没有 `unavailable_reason`，并用
   `runtime_billing_allowed` 检查这次执行和全部祖先的冻结材料、来源和模型）→ `unavailable`。撤权后的执行结果不会被写进仍可访问的草稿。
   这一项在锁内、写入前最后检查。补应用一次检查多条时，用 0158 的批量 helper `runtime_history_availability(uuid[])`
   （只供数据库函数内部调用，已对 service role 收回直接权限）；两者是同一套权限判断；
9. 整理结果不是严格的 JSON 对象，或格式不符合第 3.3 节 → `invalid_output`；
10. 否则按第 3.2.2–3.2.3 节处理 → `applied`（至少写了一项）或 `suggested`（只生成了更新或全部丢弃）。

**结果分类（唯一口径）**

| 结果 | 草稿内容 | 处理记录（`opc_capture`） | 是否终结 | 理由 |
| --- | --- | --- | --- | --- |
| 第一组不通过 | 不改 | **不记** | — | 归属未确认，抛 `OPC_CAPTURE_DENIED` |
| `not_ready` | 不改 | 不记 | 否 | 执行可能稍后完成；补应用的候选本来只取已完成的 |
| `skipped_format` | 不改 | 记 | 是 | 冻结的格式不会再变 |
| `denied_binding` | 不改 | 记 | 是 | 冻结身份和当时的绑定是固定事实 |
| `stale_round` | 不改 | 记 | 是 | 轮次只会向前；已发布的轮次不会回到草稿（修订会建新轮次） |
| `unavailable` | 不改 | **不记** | 否 | 模型或来源权限可能恢复；补应用候选先用批量 helper 过滤掉当前不可读的执行，所以它不会挡在队首 |
| `invalid_output` | 不改 | 记 | 是 | 冻结的整理结果不会再变 |
| `applied` / `suggested` | 按规则改 | 记 | 是 | — |
| 数据库或事务错误 | 不改（本批回滚） | 不记 | 否 | 原样抛出，**不吞掉、不标成成功** |

"记"的处理记录只含执行 id、结果码、规则版本，以及 `applied` 时每个被写步骤写入后的版本号（第 3.2.2 节靠它判断"capture 之后有没有人工写入"），
不含任何内容。所以"拒绝"和"不写内容"是两回事：终结的拒绝会留一条不含内容的处理记录，但草稿内容一定不变。

`unavailable` 的执行如果之后恢复可读，会重新成为候选；那时步骤版本通常已经变化，按第 3.2.2 节整次只生成更新，不会用旧材料覆盖新内容。

幂等：处理记录写在 `artifact_requests`，request id 用独立命名空间（由 `'opc_capture:' || 执行 id` 推导），`action = 'opc_capture'`；
同 id 但 payload 不同报冲突，不能"见到同 id 就成功"。**一条执行已有记录时，重复调用先重跑第一组和第 8 项**：第一组不通过 → 拒绝、不写；
第 8 项不通过 → 返回 `unavailable`，不改原记录、不返回内容；都通过才返回原记录的结果。返回值只含字段 id 和结果码，不含内容。

并发撤权：如果撤权和 capture 同时提交，capture 在锁内最后检查第 8 项；撤权先提交 → `unavailable`。
capture 先提交、之后才撤权的情况，与今天用户自动保存了这段内容再撤权完全相同，按现有规则处理，本方案不改变它。
用两个数据库连接测试这两种顺序。

`opc_query` 和补应用读取执行状态时，复用上面同一套检查，不另写权限判断。capture 和 `runtime_admit` 保持为两个独立事务；
capture 不新增对会话、运行单的更新锁，只用权限函数自己的锁。实施时用两个数据库连接实测授权先后和无死锁。

#### 3.2.2 字段能不能直接写（P1-1、P2-1）

字段来源记在 `steps.<stepId>.fieldMeta.<字段id>`：`{source: "capture"|"user", executionId?, fp?, suggestion?}`，
其中 `fp` 是整理器写入时的 `{value, status, nature}` 指纹。`information` 本身格式不变。

**一个字段只有满足下面之一才"可直接写"：**

- (a) `fieldMeta.source = "capture"`，当前 `{value, status, nature}` 的指纹等于 `fp`，**并且能证明那次写入之后没有人工写过**：
  本轮有这条 `fieldMeta.executionId` 对应的 `opc_capture` 记录，而且本轮本步所有 `expectedVersion` 不小于该记录写入后版本号的
  `opc_information` 记录里，这个字段的值都等于 `fp`。只看指纹不够：用户把 A 改成 B 再改回 A，指纹相同，但历史里有 B，
  这样的字段受保护。`opc_information` 每次都写整步，所以只要用户写过这个字段的别的值（包括清空），历史里一定有。
  证明不了（例如找不到本轮的 capture 记录、记录已被注销清除）就受保护。不建新表，用的是现有不可变历史和单调递增的步骤版本号。
- (b) 当前值为空、状态 `unknown`、没有 `fieldMeta`，**并且本轮历史上从没有过非空值**
  （查本轮本步的 `opc_information` 和 `opc_capture` 记录；用户清空过的字段因此受保护）。

**其余一律受保护，只生成"整理的更新"：**

| 字段情况 | 处理 |
| --- | --- |
| 旧草稿里非空、没有 `fieldMeta`（不知道是用户手改还是旧页面自动填的） | 受保护。不回填来源、不猜。 |
| 旧草稿里被清空过的字段（历史上有过值） | 受保护。 |
| `confirmed` / `deferred`（不论新旧） | 受保护。 |
| `fieldMeta.source = "user"` | 受保护。 |
| `source = "capture"` 但指纹已变，或指纹相同但之后历史里出现过别的值（A→B→A、清空再恢复） | 受保护。 |
| 从别的轮次继承来的 `fieldMeta`（`opc_revise` 复制、0134 未改动步骤复制） | 本轮没有对应的 capture 记录，受保护。 |
| 字段所在步骤已确认 | 受保护，且只存更新、不改版本、不让步骤失效。 |

**整份材料校验（P2-1）**：整理器看的是整份清单，基于旧材料推出的内容不能写进没动过的字段。所以先比较本轮
所有步骤当前的 `version` 和这次执行冻结的 `scopeMaterial.content.work.steps.*.version`：只要有任何一步不一致
（有人改过任何字段，或更新的一次整理已经写过），**这次执行的全部条目都只生成更新**，不直接写。
不建依赖引擎；冻结的版本号就是可靠的比较基线。新的 `opc_capture_apply` 和 `opc_capture_resolve` 只在信息或正文真正改变时
加版本号（只存更新、忽略更新都不加，第 3.2.4 节），所以"忽略一条更新"不会让后来的执行全部降级。现有 `opc_information`
保持原样：即使提交的值和原来相同也会加版本号（自动保存去重由页面负责）。

代价：用户在导师回复期间手动改了右侧，这一轮的整理结果都会变成更新而不是直接写入。验证时观察频率。

#### 3.2.3 写入

- 可直接写：值写入、状态 provisional（或 unclear），`fieldMeta` 记 `source: capture`、执行 id 和 `fp`；
  被写到的未确认步骤版本号 +1，并按现有规则让依赖步骤失效。
- 生成更新：`fieldMeta.suggestion = {executionId, seq, value, status, nature, basis, hash}`。`seq` 是执行的先后顺序
  （`runtime_executions` 的创建时间，id 兜底）。**每字段只保留顺序最新的一条**：较旧的执行晚到时不能替换较新的更新。
  只存更新不改版本号、不让步骤失效。
- 丢弃：值为空、超 400 字、字段或步骤不存在、状态不是 provisional/unclear；记在返回结果里。
- 用户正在打字时，capture 让版本号变化，自动保存会收到冲突，现有三方合并（`information-merge.ts`）处理：
  不同字段各保留，同一字段弹出现有的冲突提示。

#### 3.2.4 采用和忽略（P2-2）

新增 `opc_capture_resolve(p_actor_id, p_draft_id, p_request_id, p_step_id, p_field_id, p_execution_id, p_hash,
p_action, p_expected_version)`，只授予 service role，经 tRPC 薄路由调用：

- 必须带用户看到的那条更新的 `executionId` 和 `hash`；服务器上的更新已经换成别的 → 报 `OPC_SUGGESTION_CHANGED`，
  不做任何改动，页面刷新后让用户重新看。
- **采用**：把更新的值写进 `information`（`expectedVersion` 校验、版本号 +1、按现有规则失效），
  `fieldMeta.source` 记为 `user`（用户明确采纳的内容此后受保护），清掉这条更新。
- **忽略**：只清掉这条更新；正文没变，所以**不加版本号、不调用 `artifact_invalidate`**。
- 幂等：同一 `p_request_id` 重放返回原结果。
- `opc_information` 的参数**不变**，只改函数体：值有变化的字段把 `fieldMeta.source` 标为 `user` 并更新 `fp`
  （清空也算变化），其余校验原样保留，`notes` 和其他键不动。这样新旧签名不会重载，回退简单（第 5.2 节）。

#### 3.2.5 什么时候调用，补应用要有界

不新建队列或定时任务（AGENT-CORE"整理的触发"）：

1. 导师流式请求结束、结果确定后，服务器调用一次 `opc_capture_apply`；
2. 新的一轮准入前（`prepareStep`），先补应用本草稿还没应用的执行，保证导师和整理器看到最新清单；
3. 页面打开时调用幂等接口 `opc.capturePending({draftId})`。

补应用的处理约定（P2-B）：

- 候选：**当前轮**、`completed`、**带 v2 标记**、尚未有 `opc_capture` 记录的导师执行，按执行顺序取最早的**最多 5 条**
  （旧格式执行不进候选，否则旧草稿里成批的旧执行会堵住准入；`skipped_format` 只出现在指定执行 id 的单条调用里）；
  用 `opc_turns` 和 `artifact_requests` 主键定位，不扫描整段会话历史（避免把 #586 修掉的长会话延迟带回来）。
- **一批一次 RPC、一个事务**：最多 5 条在同一次 `opc_capture_apply` 调用、同一个事务里依次处理。每条按第 3.2.1 节的判断得到结果；
  只有解析整理结果时用一个 PL/pgSQL `BEGIN ... EXCEPTION` 块，**只捕获 JSON 解析错误**，转成 `invalid_output`。
  这个块只用来隔离坏内容，它不会单独提交。存储、锁、事务错误一律不捕获：**失败的这一批全部回滚**（包括本批前面已处理的条目
  和它们的处理记录），只有之前已经成功返回的批次保留；下一次调用幂等地重试整批。不新建队列，也不改成逐条 RPC。
- **坏条目不挡队首**：`invalid_output`、`skipped_format`、`denied_binding`、`stale_round` 都是终结结果，记下后不再进候选；
  `unavailable` 的执行在选候选时就被批量可读性检查过滤掉。所以同一条坏内容不会每次都卡在最前面。
- 返回 `{processed: [{executionId, result}], remaining, hasMore}`。
- **新一轮导师准入前必须处理完**：`prepareStep` 循环调用补应用直到 `hasMore = false`，最多 4 次（20 条）；仍有剩余就
  拒绝这次准入（`OPC_CAPTURE_PENDING`，在任何计费和模型调用之前），页面提示"正在整理之前的对话"，用户再发一次时继续处理。
  实际情况下待处理通常是 0–1 条。
- 页面打开时的 `capturePending` 同样按 `hasMore` 继续，最多 4 次，剩余的留给下一次准入前处理。
- 并发：两个客户端同时补应用时，项目行锁让它们排队；后来的看到已有记录直接跳过，结果幂等。

和重放、计费、限流的关系：

- 原请求的重放（`runtime_admission_replay`）**优先于**补应用，在补应用之前返回；补应用失败只记日志，
  不影响已完成请求的恢复。
- 补应用只读已保存的执行结果和写数据库，**不调用模型、不新建 BILL2 运行单、不扣积分、不经过
  RATE-LIMIT 的调用闸门（#590）**。测试：在"暂停新调用"打开时，补应用和重放都照常工作，计费和限流计数不变。

### 3.3 整理器的输入和输出

- 输入：用户这句话、答过的卡片（五项不变）、当前步骤 id、`captureFormat: "v2"`、**整份清单**（所有步骤的所有字段：
  标题、必需、角色、状态、当前值，以及该字段是否受保护）、未确认步骤的已有笔记。去掉 `currentQuestion` 和"已到达"过滤。
  当前值取自这次准入时的服务器数据，和冻结的 `scopeMaterial` 一致。
- 输出改为列表：`{"inputKind": ..., "patches": [{"stepId","fieldId","value","status","nature","basis"}], "notes": [...]}`，
  最多 12 项。规则沿用 #584：按字段角色合并（user_fact 只加用户说的；agent_proposal 才能采用导师的具体建议）、
  返回合并后的完整值、400 字内压缩、没有新内容返回空列表、永远不写 confirmed/deferred。新增：一句话里有几项就写几项，
  写到真正对应的字段，可以是别的步骤。去掉"答非所问返回空 patch"等只适用于逐题模式的句子。
- 数据库解析：`opc_capture_apply` 只接受严格的 JSON 对象（和现在 `readMentorTurn` 直接 `JSON.parse` 一样，代码框包裹视为无效）。
  前端 / TS 解析器仍保留，用于显示历史，并同时接受旧格式（`targetStepId + informationPatch`）。
  加一组对照用例，保证 SQL 和 TS 对同一批样本的接受与拒绝一致。

### 3.4 导师

- 去掉"当前题"和题号（`questionLabel`）。系统指令里给整份清单的状态（缺 / 草稿 / 已确认 / 暂缓 / 受保护），不带值；
  **字段的当前值由每轮冻结的 `scopeMaterial`（随导师输入发送）提供**，这是手动修改之后、会话历史被截断之后
  仍然可靠的来源，保留不动。
- 新规则要点（B2 同步改写整份模板，见第 3.6 节）：
  - 先回应用户真正说的话；整理器会把有用信息记到对应栏目，导师不用把用户拉回某一题；
  - 然后挑**当前步骤**最有价值的必需缺口问一个问题；已经是草稿或已确认的，不再问，除非需要澄清矛盾；
  - 用户一次说了好几项，简短确认都记下了，再问下一个缺口；
  - 当前步骤必需项都有内容后，提示用户在右侧核对并确认这一步；不替用户确认、不说"已确认"；
  - 卡片用于当前步骤里某一个缺口；#582 出卡规则表的意图保留，只把"当前字段"改成"当前步骤里卡片针对的那一项"。
  - **出卡分寸（Owner 决定并入 B2）**：只有两种情况出卡——用户已有材料构成的方案选择（推荐其中一个并说明理由），
    以及不了解用户也能列出的中性范围或类别（不推荐）。**开放的个人内容（经历、优势、故事、客户、目标）一律不出卡，
    即使用户要求给选项也不出**；改在正文里举几个例子，并明确说明"这是我的猜测、由你决定，因为目前信息还不够做专业判断才这样猜"，
    然后用一个开放问题请用户自己说。出卡时卡片必须字段完整、推荐与正文一致；正文不重复列出卡片选项。
  - 目标模型是 Claude Sonnet 5.5（Owner 已定）。提示词按它调，不再为 Gemini 做兼容取舍。
- 这些规则对应 Skill 自己的写法（"用户在前面已经说过的，不要再问；一个回答里包含了好几项信息，就一起记下"），
  宿主只是不再和它打架。

### 3.5 轮次身份、开场和提问卡绑定（不改 0155）

- task 格式 `opc-question:<字段id>` 保留，含义改为"这一轮的焦点字段"，**只是身份，不再限制导师说什么、整理器写哪个字段**：
  - 新的一轮：宿主选焦点 = 当前步骤里第一个还缺内容的必需字段（按 Skill 声明顺序），都有内容就取第一个未确认字段，
    再没有就取最后一个字段。
  - **回答提问卡的一轮继承卡片所在轮次的 task**，继承值从服务器读到并验证过的那次执行取（`resolveAnswerCard` 已经读的
    `runtime_view`），不信浏览器传来的 questionId。于是 0155 的"两次 task 相同"检查原样通过；再加上"同一会话最新一次执行、
    同一草稿/轮次/步骤、卡片逐字相等、选项原文相等"，答案仍绑定它回答的那张卡。卡片的问题本身（五项）交给整理器决定写到哪个字段。
  - 准入检查从"必须是已到达的题"改为"必须是本步骤 schema 里的字段"；已冻结的旧请求在检查之前就重放返回。
    尚未准入的旧请求（浏览器里存着、还没发出去的）按新规则检查，旧 questionId 都是 schema 字段，可以通过。
- 前端去掉"卡片只能在它那道题显示时回答"的判断，改为"同一步骤最新一次已完成执行的卡片可以回答"。
  测试：卡片出现后焦点已经变了（整理器填了焦点字段），同一步最新的卡仍能回答。
- 开场：每一步、每一轮只开场一次，身份 `openingRequestId(草稿, 轮次, 步骤, 该步第一个字段 id)`（确定性，来自 Skill 声明）。
- 这样 `runtime_admit` 和 `runtime_view` 都不用改。

### 3.7 每步确认（绑定可见快照）

- 必需项都有内容（或写了暂缓原因）时，聊天区出现宿主生成的**本步小结卡**（不调模型）："这一步的信息已经齐了：
  核对并确认 / 我还要补充"；右侧同时出现"确认这一步"按钮。
- 点"核对并确认"打开整步核对页：所有字段和笔记可改；必需项按第 8 节第 2 项的规则处理。
- 提交时把**用户看到的整步快照**写进确认信封：全部字段的 value/status/nature、全部笔记、轮次、步骤 `version` 和
  `reviewVersion`，以及核对页上显示的每条"整理的更新"的身份（`executionId` + `hash`）。第一阶段前重新读取并逐项比较；
  任何一项不同（中途来了整理结果、另一个标签页改过、出现了新的或换掉了的更新），就停下、刷新核对页、请用户重新看，
  **不悄悄确认用户没看过的内容**。确认的对象是已经写进字段的正文；还没处理的更新不会被确认，确认后仍留在那里，
  用户可以之后采用（采用会让这一步回到草稿，按现有规则重新确认）。
- 之后沿用现有确认信封的三个阶段（`opc_information` 把整步设为 confirmed/deferred → `save` → `confirm`），
  数据库确认规则不用改。这是三个事务，断网时按信封续做；已有的单题确认信封先按原样续完。
- 确认后自动进入下一步并由导师开场；下一步里已经从对话中记下的草稿直接显示，导师不再重复问。
- 回头修改已确认的步骤：改动即让这一步回到草稿、后续步骤标"需要复核"（现有 `artifact_invalidate`），重新确认即可。
- 按钮变化：
  - 删除："确认当前信息，继续"、手动模式的"确认本题并继续 / 暂缓本题 / 暂时跳过本题"、题目导航（1.1、1.2 行）；
  - 新增："确认这一步"、小结卡；
  - 保留："确认正式定位"（规则不变）；
  - 改名："导师建议调整 · 采用这些修改" → "根据对话整理的更新 · 采用 / 忽略"，显示改动前后对比。

**冻结材料的裁剪（P2-C，选定方案：改现有投影函数，列入 B1）**

现有 `runtime_work_projection`（0139）把整份 `steps` 冻结进 `scopeMaterial`，只改别的函数挡不住 `fieldMeta` 进去。B1 在同一个迁移里
重新定义这个函数（签名不变），对每一步：

- 保留：`information`（当前值，导师和整理器的可靠来源）、`notes`（用户刚编辑的笔记由此进入下一轮导师和整理器的输入，不依赖可能被截断的聊天历史）、
  版本、确认、证据等现有键（权限和 `informationVersion` 依赖它们）；
- `fieldMeta` 只保留每个字段一个"受保护"布尔值，去掉 `fp`、执行 id 和更新正文。

旧请求的冻结材料不受影响：已冻结的内容和 hash 原样保存，重放用冻结的那份；`runtime_material_allowed_before_b1` 对 `steps` 本来就不做逐字比较，
新旧投影形状不同不会让旧请求失效。回退时把这个函数恢复成回退那一刻的前一个定义（第 5.2 节）。
用例：新冻结的材料里没有更新正文和指纹；旧请求恢复和重放不受影响；满额笔记和满额字段下冻结载荷 ≤ 262144 字节、导师和整理器输入不超限。

3. 重新定义 `opc_information` 的**函数体**（签名不变）：维护 `fieldMeta`；原有校验全部保留。
4. `opc_query` 的 `information[step]` 增加 `meta`（来源、受保护标记、更新）和 `notes`。
5. 重新定义 `runtime_work_projection` 的函数体（签名不变）：第 3.8 节的冻结材料裁剪。

**为什么需要新函数**（AGENTS §5）：
- 考虑过的现有机制：`opc_information`（整步覆盖写，没有字段来源；交给浏览器就等于浏览器做规则）；浏览器投影（第 1.2 节的问题）；
  `opc_save_result`（只处理 `purpose = step` 的整步成果）；`opc_revise`（只处理已发布版本）。
- 缺的最小能力：服务器在一个事务里完成执行授权、按来源保护字段、合并一次整理结果；以及按身份采用或忽略一条更新。
- 权威来源不变：信息仍只存在 `artifact_rounds.steps`；历史仍在 `artifact_requests`；权限沿用现有函数。

笔记的写入（B3）另起一个迁移。

每个迁移按工程规范第 5 节：连续执行两次结构不变、更新 `built-fingerprint.json`、应用 staging 前后抓只读指纹。

## 5. 兼容和回退

### 5.1 进行中的草稿和新旧页面并存

- **旧草稿的字段**：按第 3.2.2 节——没有来源证明的非空字段、被清空过的字段、confirmed/deferred 一律受保护，只生成更新；
  只有从没有过内容的空字段可以直接写。不做任何回填。新面板照常显示旧的"单题已确认"字段；确认整步时一起提交。
- **新旧页面并存**（B1 已上线、F1 还没上线，或用户开着旧标签页）：
  - 旧页面自动保存经过新的 `opc_information`，值有变化的字段都标为 `user`。旧页面自动填入的整理结果因此也会被当成用户内容保护——
    宁可多保护，不会被覆盖。
  - B2 上线后，新执行的整理结果是新格式（`patches`），旧页面的解析器读不到 `informationPatch`，**不会再自动填**；
    只有服务器的 capture 在写。
- **浏览器里存着的旧请求**：`opc-step:*`（带旧 questionId）和 `opc-confirm-step:*`（单题确认信封）。新页面先按原样续完，再切到新模式。
  已准入的请求在任何检查前重放返回；没准入的按第 3.5 节新规则检查。
- **旧格式整理结果**：没有 v2 标记，capture 不处理。它们当时已由旧页面处理过；页面恰好没打开的那几条会缺一次投影，接受。
- 已发布的版本不受影响；`opc_revise` 复制 `steps` 时带上 `fieldMeta`、`notes`。账号修订（0134）未改动的步骤也会复制它们，
  已有改动的步骤保留目标轮次自己的。不论哪种，继承来的字段在新轮次里都没有对应的 capture 记录，按第 3.2.2 节受保护。
  普通修订和账号修订的两支分别测试。
- 手动模式（"我已有定位"）：同一个面板，用户直接填写（全部标为 `user`），按步确认；导师可选开启。

### 5.2 组合回退顺序（P2-5、P2-A）

**停用（最常用，不动数据库）**

1. 先 revert F1（新面板）。此时旧页面 + 新 B2：旧页面发的 questionId 都是 schema 字段，准入通过；旧页面解析不到新格式，
   不会自动填；服务器 capture 仍按规则写，旧页面通过读取看到结果。可以工作。
2. 再 revert B2。新执行不再带 v2 标记，`opc_capture_apply` 对它们返回 `skipped_format`（空操作，不是报错），新写入就此停止；
   准入恢复"已到达"检查，旧页面恢复原来的逐题投影。
3. **顺序不能反**：如果先 revert B2、F1 还在，新面板发的焦点可能是未到达字段，会被旧准入拒绝。重新启用时反过来：先 B1 调用方、再 B2、再 F1。

**撤掉数据库函数（只在必须时）**

4. **先停 B1 的调用方**：revert B1 的服务端代码（流式请求结束时的调用、`prepareStep` 补应用、`capturePending` 路由），
   部署这个版本，并核验：普通导师请求、旧请求恢复、页面打开都不再调用新函数，且都正常。不加新的配置开关。
5. 然后再写回退迁移：两个新函数按完整签名 `DROP FUNCTION`（签名唯一，没有重载）；`opc_information`、`opc_query`、
   `runtime_work_projection` 恢复成**回退那一刻前一个版本的定义**——先核对当时线上的函数定义，不能直接抄旧迁移，以免覆盖之后其他 PR 的修改。
   顺序不能反：先删函数、调用方还在，就会出现"函数不存在"的报错。
6. 用户内容全部保留：整理写入的值就是普通草稿值；`fieldMeta`、`notes` 留在 jsonb 里，旧代码忽略。

**回退后再启用**

7. 回退期间旧的 `opc_information` 不维护 `fieldMeta`，用户手改的字段可能还挂着 `source: capture`。但回退期间的每次写入仍然留下
   `opc_information` 历史（带 `expectedVersion`），第 3.2.2 节 (a) 的历史检查会看到这些写入：改成别的值、清空、A→B→A 都会让字段受保护。
   所以再启用不需要修复步骤；但这依赖历史检查，不依赖指纹。

验证：

- "有新数据 → 回退 → 手改、清空、A→B→A → 再启用 → 新的整理结果对这些字段只生成更新"；
- 删函数前的部署核验：调用方移除后普通请求、旧请求恢复、页面打开都正常；
- 删函数后旧请求恢复正常；
- 同一回退迁移执行两次结构不变；重复回退和再启用各一次。

## 11. 剩余风险

- 整理质量仍取决于整理模型：一句话里信息很多时可能漏记或记错字段。漏记的内容只留在对话里，整理器没有历史；
  如果验证发现漏记明显，再考虑给整理器带上最近几轮用户原话（#584 P3-1 的方向），本批不做。
- 保守保护的代价：旧草稿里的旧内容、导师回复期间用户的手动编辑，都会让整理结果变成"更新"，需要用户多点一次"采用"。
- 跨步骤写入后，后面步骤在用户到达前就有草稿；界面要说明这是"从对话里记下的草稿"，不是已确认。
- 整理器输入变大（整份清单），每次整理的输入 token 会增加；计费逻辑不变。
- 与 #581/#586/#590/#591 的组合行为需要联合回归；任何一方的最终实现变化，都要在 B1/B2 开工前重新核对第 7 节。
- F1 对 `page.tsx` 的改动面大；浏览器验证要覆盖手动模式和账号修订两条旁路。
