# CONVERSATION-DRIVEN-CAPTURE：右侧信息跟着对话走（方案）

> 状态：仅方案，未实施。风险：实施部分为 high（数据库函数、迁移、准入规则）；本文件本身是文档。
> 写方案时的基线：staging `e49dc92f`（迁移到 0157）。本方案只引用代码事实，不改代码。

## 0. 一句话结论

Owner 2026-10-02 选了方向 B：右侧信息和整理器不再按一条固定的题目顺序走；只要最后 Skill
要求的信息都收齐、整理好，顺序无所谓；右侧内容由导师和用户实际聊到的东西来创建和填写。

这其实就是 [Master Plan v12 第 3 节](MASTER_PLAN.md) 已经锁定、但还没实现的体验：
"每一步只确认一次"、"笔记只分草稿 / 已确认"、"用户在第一步顺口说出的后面步骤的信息，会被整理进
对应栏目，Agent 之后不再重复问"、"手动改过的内容，整理模型不能覆盖"（第 3.2、3.5 节；第 2.2 节
已把"层级题号 1.1/1.2、只展示已到达的问题、逐题确认"列为被取代的旧规则）。现在的实现仍是逐题模式，
所以 #584 合并后的 staging 验收里出现了"导师已经聊到别的话题，右侧还停在 1.1"。

推荐做法（细节见第 3–6 节）：

1. **清单不变**：Skill 发布包里每一步声明的信息字段，仍是"收齐没有"的标准和报告的结构化输入。
2. **整理改到服务器上写**：整理结果由服务器按字段规则写入（现在是浏览器写），可以写本轮里任何
   一个还没确认的步骤的任何字段；已确认或用户手动改过的字段只给"根据对话整理的更新"，由用户采用。
3. **导师不再绑定一道"当前题"**：看整份清单，先补当前步骤最有价值的缺口，不再机械拉回 1.1。
4. **确认改成每步一次**：清单里必需项都有内容（或写明暂缓原因）后，用户在右侧核对整步、点一次确认。
5. **提问卡的答案仍然绑定它回答的那张卡**，数据库里的绑定检查（0155）不用改。

## 1. 现状（只读核对的事实）

### 1.1 信息存在哪里

- 每一步的信息存在 `artifact_rounds.steps -> <stepId> -> information`，格式 `{字段id: {status, value, nature}}`。
  唯一的写入函数是 `opc_information`（`packages/db/migrations/0107_opc_workbench.sql:467-490`）：
  - 必须一次写整步的全部字段，带 `expectedVersion` 防并发；每个值最多 400 字，整步最多 12000 字节；
  - 只接受 `status/value/nature` 三个键（`basis` 之类的来源信息会被拒绝）；
  - 不检查"是否已到达"，不保护已确认的值；每次写入都会让本步和依赖它的后续步骤失效
    （`artifact_invalidate`），并在 `artifact_requests` 里留一条不可改的历史记录。
- 读取用 `opc_query`（最新包装链 0134 → 0116 → 0111）：`information[step] = {schema, values, reached,
  previouslyConfirmed}`，另有 `turns[] = {executionId, stepId, questionId, roundId, kind, informationVersion}`。
- "已到达"只在两处存在：
  - TypeScript 准入检查：`packages/api/src/services/opc/service.ts:128-191`，用
    `packages/api/src/shared/opcQuestions.ts` 的 `reachedQuestions`，不在范围内报 `OPC_QUESTION_NOT_REACHED`；
  - 只读投影 `opc_historical_reach`（0111:19-53），从历史写入里算出"前面连续确认了几题再加下一题"。
  数据库写入路径本身不认"题目进度"。

### 1.2 整理器怎么工作

- 整理器和导师在同一次执行、同一笔计费运行单里：导师回复后，再调一次整理模型
  （`packages/api/src/services/runtime/execute.ts:325-346`，不读会话历史，`historyItems: 0`）。
  输出 JSON 存为执行结果的 `summary`，**数据库不解析它**。
- 整理器输入（`service.ts:211-228`）：用户这句话、答过的卡片（五项：question、options、
  selectedOption、selectedIndex、recommended）、`currentQuestion`、`allowedWorkflow`（当前步 + 已确认步，
  且只含"已到达"字段）、`currentStepMaterial`（当前步全部字段的已有值，#584 加的）。
- **真正把整理结果写进右侧的是浏览器**：`apps/web/src/app/positioning/[draftId]/page.tsx:626-709`
  解析 `summary`，只填这一轮冻结的那道题、而且只在那道题为空时填；其他情况变成一张"导师建议调整"卡片，
  用户点"采用"才写。写入走普通自动保存（`opc_information`）。页面没打开时就没人写。
- `targetStepId` 指向别的步骤时，浏览器直接丢弃（没有任何地方调用 `opc_revise`）。

### 1.3 导师提示词

- `packages/api/src/services/opc/agentTurnPrompt.ts`：给导师"当前题"（带 1.1 这样的编号）、当前题字段角色、
  当前步各字段状态（不含值）和已到达字段清单；规则包括"卡片只针对当前题"、
  "用户答别的话题时简短回应，再回到当前题或请他确认"（#584 加入，#582 原样保留并合进了出卡规则改写）。

### 1.4 确认和发布

- 现在每一题单独确认："确认当前信息，继续"（`page.tsx:1982-1988`）→ `confirmQuestionValues` 把这一题设为
  confirmed → `opc_information`；全部字段都确认或暂缓后，浏览器把各字段拼成本步正文，依次调用
  `workbench.execute` 的 `save` 和 `confirm`（`page.tsx:1107-1235`，没有 AI 生成环节）。
- 数据库规则：步骤确认要求必需字段是 confirmed 或 deferred（0107:503-516）；
  "确认正式定位"（publish）要求必需字段全部是 confirmed，暂缓的不行（0118:10-29）。
- 修订（`opc_revise`，0125:102-118）会整份复制 `steps`，包括 `information`。

### 1.5 提问卡绑定

- 0155 的 `runtime_admit`（`0155_runtime_answer_source.sql:33-77`）检查：答案引用的那次执行属于同一会话、
  是最新一次、已完成、同一草稿/轮次/步骤，**而且两次的 task（`opc-question:<字段id>`）相同**；
  卡片内容逐字相等；选了选项时输入必须等于选项原文。

### 1.6 问题的直接证据

- #497 总控审计（[评论](https://github.com/Crnobog9527/GraylumAI_vercel/pull/497#issuecomment-5948968015)，
  [更正](https://github.com/Crnobog9527/GraylumAI_vercel/pull/497#issuecomment-5949015697)）：
  整理器只能写"已到达"的 `goal`，于是讲受众、选平台的回答都被塞进了目标。
- #584 用"答非所问就返回空 patch，导师拉回当前题"止血；staging 验收
  （[#584 最后一条评论](https://github.com/Crnobog9527/GraylumAI_vercel/pull/584)）：整理器不再写错字段，
  但导师照样转去问产品和收费模式，右侧仍停在 1.1，"受众"这条信息只留在了对话里（#584 审查的 P3-1：
  整理器没有历史，之后走到受众题时可能再也记不上）。
- 结论：问题不在某句提示词，而在"一次只认一道题"的结构。只改提示词让导师"更听话地拉回 1.1"，
  会和 Owner 这次的决定正面冲突。

## 2. 目标（验收口径）

沿用 Master Plan 第 3.5 节，本方案负责其中这几条：

1. 用户在任何时候说出的、属于清单里任何一项的信息，回复后几秒内出现在右侧对应栏目（草稿）。
2. 导师不重复问已经记下的信息；跑题时简短回应、顺势补当前步骤最缺的内容，不念题号、不机械拉回。
3. 每一步只点一次确认；必需项缺失时，确认前明确告诉用户还差什么。
4. 已确认或用户手动改过的内容，整理器不会直接改，只给"根据对话整理的更新"让用户采用或忽略。
5. 刷新、断网、重新登录后，右侧内容和确认状态都能恢复；计费不重复。
6. 页面和数据库不写死某个 Skill 的步骤和问题（工程规范第 6 节）。

## 3. 设计

### 3.1 两层：Skill 清单 + 补充笔记

- **Skill 清单**（保留，权威）：已发布 Skill 的 `workflow.yaml` 里每步的信息字段（`id/title/required/
  elicitation`）。它决定"收齐没有"，也是报告（#547 REPORT-GEN）读取的结构化事实。不改 Skill 格式。
- **补充笔记**（新增，可选，见第 8 节 Owner 决定 1）：对话里有价值、但对不上任何字段的内容，由整理器记成
  草稿笔记，挂在最相关的那一步下面；随这一步一起核对、确认，报告里作为"对话补充资料"使用。
  - 质疑总控提案的一点：笔记**不单独建表**，存在同一份步骤数据里（`steps.<stepId>.notes`）。理由：
    `opc_revise` 本来就整份复制 `steps`，修订自动带上；账号注销已经覆盖 `artifact_rounds`（0149），
    不用新增注销接线；随步骤确认和失效，不会出现第二套状态。上限：每步最多 8 条、每条 400 字。
  - 笔记放在最后一对 PR，核心问题（清单跟着对话填）先上线，不被笔记拖住。

### 3.2 整理怎么写（服务器写，按字段规则）

**选择：从"浏览器写"改为"服务器写"。** 只放宽浏览器里的投影也能让多字段先跑起来，但会留下三个问题：
页面关了就没人写；"手动改过不能覆盖"需要服务器知道每个字段是谁写的；导师下一轮要看到最新清单才能
"不重复问"，而浏览器写入可能还没发生。所以由服务器写一次、写到位。

新增一个数据库函数 `opc_capture_apply`（只由服务端用 service role 调用，浏览器拿不到），每次执行最多应用一次：

| 情况 | 处理 |
| --- | --- |
| 字段属于本轮**未确认**的步骤，当前值等于整理器当时看到的值（逐字段比对） | 直接写入，状态 provisional（或 unclear），标记来源"整理"和执行 id |
| 字段当前状态是 confirmed / deferred，或标记为"用户手动改过" | 不写值，存为这个字段的"整理的更新"（每字段只留最新一条） |
| 当前值和整理器当时看到的不一样（用户刚改过，或更新的一轮已经写过） | 同上，变成"整理的更新"，不覆盖 |
| 字段属于**已确认**的步骤 | 只存"整理的更新"；不改值、不加版本号、不让步骤失效 |
| 值为空、超 400 字、字段或步骤不存在、状态不是 provisional/unclear | 丢弃这一项（记录在返回结果里） |
| 草稿已发布、轮次不是当前轮、执行不属于这个草稿、执行未完成 | 整个拒绝 |

- 写入后，被写到的未确认步骤版本号 +1，并按现有规则让依赖步骤失效（和 `opc_information` 一样）。
  用户正在打字的自动保存会因为版本号变化收到冲突，现有的三方合并（`information-merge.ts`）处理：
  不同字段各保留，同一字段弹出现有的冲突提示。
- 幂等：在 `artifact_requests` 里用由执行 id 推导出的固定 request id 记一条 `opc_capture`，重复调用直接返回上次结果。
- "整理器当时看到的值"取自这次执行冻结的整理器输入（服务器读，不信浏览器）。这一个逐字段比对同时解决了
  顺序颠倒（旧执行晚到）和用户同时编辑两个问题，不需要队列或排序状态。
- 谁来调用（不新建队列或定时任务，符合 AGENT-CORE"整理的触发"）：
  1. 导师流式请求结束时，服务器顺手调用一次；
  2. 新的一轮准入前（`prepareStep`），先把本草稿已完成、还没应用的执行补上，保证导师和整理器看到最新清单；
  3. 页面打开时调用一个幂等接口 `opc.capturePending({draftId})` 补做页面关闭期间完成的执行。
- 只应用新格式的执行（冻结的整理说明里带版本标记）。旧格式的执行保留在历史里，不再自动应用
  （它们当时已由旧页面处理过；页面恰好没打开的那几条会缺一次投影，影响很小，接受）。

**字段来源标记**：`steps.<stepId>.fieldMeta = {字段id: {source: "user"|"capture", executionId?, basis?,
suggestion?: {value, status, nature, basis, executionId}}}`，和 `information` 并列，不改 `information`
本身的格式（下游 `opc_profile`、报告、选题读取方式不变）。`opc_information` 重新定义：值有变化的字段
标为 `source: "user"` 并清掉它的"整理的更新"；新增可选参数，让用户"忽略"某条更新时一并清掉。

**为什么需要新函数**（AGENTS §5）：
- 考虑过的现有机制：`opc_information`（只能整步覆盖写，没有字段来源和"当时看到的值"，交给浏览器调用就等于
  浏览器做规则）；浏览器投影（第 1.2 节的三个问题）；`opc_revise`（只处理已发布版本的修订）。
- 缺的最小能力：服务器按字段、按来源、按"当时看到的值"合并一次整理结果。
- 权威来源不变：信息仍只存在 `artifact_rounds.steps`；新函数只是第二个写入口，不建新表、不建队列。

### 3.3 整理器的输入和输出

- 输入：用户这句话、答过的卡片（五项不变）、当前步骤 id、**整份清单**（所有步骤的所有字段：
  标题、必需、角色、状态、当前值）、未确认步骤的已有笔记。去掉 `currentQuestion` 和"已到达"过滤。
- 容量：整理器输入上限 24000 字符（`runtime/admission.ts:158`）。清单值总量超限时，按固定规则先去掉
  **已确认步骤的值**（保留标题和状态）；仍超限就在准入前拒绝、不收费（现有行为）。实施时用 staging
  当前定位 Skill（版本 4）的实际字段数实测。
- 输出改为一个列表：`{"inputKind": ..., "patches": [{"stepId","fieldId","value","status","nature","basis"}],
  "notes": [...]}`，最多 12 项。规则沿用 #584：按字段角色合并（user_fact 只加用户说的；agent_proposal
  才能采用导师的具体建议）、返回合并后的完整值、400 字内压缩、没有新内容返回空列表、永远不写
  confirmed/deferred。新增："一句话里有几项就写几项，写到真正对应的字段，可以是别的步骤"；去掉
  "答非所问返回空 patch"和"不要把受众写进目标以外的字段"这一类只适用于逐题模式的句子。
- 解析器同时接受旧格式（`targetStepId + informationPatch`），用于展示历史。

### 3.4 导师

- 去掉"当前题"和题号（`questionLabel`）。给导师：整份清单的状态（缺 / 草稿 / 已确认 / 暂缓，不带值，
  控制提示词长度；内容导师从会话历史里看得到）。
- 新规则要点（替换 `agentTurnPrompt.ts` 末尾"导航"那一段，#582 的出卡规则表保留）：
  - 先回应用户真正说的话；整理器会把有用信息记到对应栏目，导师不用把用户拉回某一题；
  - 然后挑**当前步骤**最有价值的必需缺口问一个问题；已经是草稿或已确认的，不再问，除非需要澄清矛盾；
  - 用户一次说了好几项，简短确认都记下了，再问下一个缺口；
  - 当前步骤必需项都有内容后，提示用户在右侧核对并确认这一步；不替用户确认、不说"已确认"；
  - 卡片只用于当前步骤里的某个缺口；其余出卡规则不变。
- 这些规则对应 Skill 自己的写法（"用户在前面已经说过的，不要再问；一个回答里包含了好几项信息，就一起记下"），
  宿主只是不再和它打架。

### 3.5 轮次身份、开场和提问卡绑定（不改 0155）

- 现在每轮的 task 是 `opc-question:<字段id>`，用于开场去重、重放身份、`opc_query.turns[].questionId`，
  以及 0155 的卡片绑定。**保留这个格式，只换它的含义**为"这一轮的焦点字段"：
  - 新的一轮：宿主选焦点 = 当前步骤里第一个还缺内容的必需字段（按 Skill 声明顺序），都有内容就取第一个未确认字段，
    再没有就取最后一个字段。焦点只是身份，不限制导师和整理器。
  - **回答提问卡的一轮继承那张卡所在轮次的 task**，所以 0155 的"两次 task 相同"检查原样通过；
    再加上"同一会话最新一次执行、同一草稿/轮次/步骤、卡片逐字相等、选项原文相等"，答案仍然绑定它回答的那张卡。
    卡片要回答的问题就是卡片本身（五项随整理器输入一起给），整理器决定写到哪个字段。
  - 准入检查从"必须是已到达的题"改为"必须是本步骤 schema 里的字段"；已冻结的旧请求在检查之前就重放返回，不受影响。
- 开场：每一步、每一轮只开场一次，身份 `openingRequestId(草稿, 轮次, 步骤, 该步第一个字段 id)`（确定性，
  来自 Skill 声明）。不再"每到一道新题自动开场一次"。
- 这样 0155 的 `runtime_admit` 和 `runtime_view` 都不用改，也就不和 #586（RUNTIME-VIEW-PERF，正在重写这两个函数）冲突。

### 3.6 每步确认

- 右侧显示整步清单。必需项都有内容（或写了暂缓原因）时，聊天区出现一张宿主生成的**本步小结卡**
  （不调模型）："这一步的信息已经齐了：核对并确认 / 我还要补充"；右侧同时出现"确认这一步"按钮。
- 点"核对并确认"打开整步核对：所有字段可改；必需项为空的必须填写，或者写原因暂缓（是否允许暂缓见 Owner 决定 2）。
  一次提交：沿用现有确认信封的三个阶段（`opc_information` 把整步设为 confirmed/deferred → `save` → `confirm`），
  **数据库确认规则不用改**。笔记（如果做）一起显示、一起确认，拼进本步正文。
- 确认后自动进入下一步并由导师开场；下一步里已经从对话中记下的草稿直接显示，导师不再重复问。

## 10. 剩余风险

- 整理质量仍取决于整理模型：一句话里信息很多时可能漏记或记错字段。漏记的内容只留在对话里，整理器没有历史；
  如果验证发现漏记明显，下一步再考虑给整理器带上最近几轮用户原话（#584 P3-1 的方向），本批不做。
- 跨步骤写入后，后面步骤在用户到达前就有草稿；导师和界面都要说明这是"从对话里记下的草稿"，不是已确认。
- 整理器输入变大（整份清单），每次整理的输入 token 会增加；计费逻辑不变。
- F1 对 `page.tsx` 的改动面大，是本批最容易出界面回归的地方；需要浏览器验证覆盖手动模式和账号修订两条旁路。
