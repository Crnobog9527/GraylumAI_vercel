## 1. 结论与决定边界

复用统一 Runtime、BILL2 v2、模型管理、system_settings、Redis 限流和现有诊断入口。
把正式环境的授权接入同一条钱路，不复制测试窗口、不新增账本、预算服务或审批系统。
首批仅开放已有证据覆盖的模型、固定线路、用途与请求格式；Fusion 上界未定义前继续关闭。

本次 Owner 已明确：

- 正式开放及准入名单没有固定到期日；花费上限以 OpenRouter 为准。
- q=100，默认 m=6；模型/线路覆盖仍须冻结，不能用全局新值重算旧账。
- 启动门槛沿用 #686：按典型名义费用 typicalUsd 和倍数自动算，不手填固定积分。
- 准入名单仅在换模型、换线路或实时计量检查异常时重新采样，不做按日历周期的重复采样。
- 正式站 `graylum-ai-vercel-v1` 暂停；main 已知依赖漏洞须随上线处理。

其中站点暂停状态为 Owner 提供，本任务未读取正式平台状态。
Master Plan RUNTIME-PROD ⑤ 的全站每日成本上限仍保留，由 OpenRouter 执行；
本次“花费上限以 OpenRouter 为准”限定执行位置，不取消每日上限，也不另建 Graylum 预算计数器。
正式批准包需采用覆盖全站流量的 OpenRouter 每日限额，另保留每用户每日次数限制、成本观察和紧急停止。
金额及告警接收渠道尚未获配置授权，见第 8 节。若拟采用非每日上限替代，须先由主窗口取得新决定
并同步 Master Plan 第 2.1 节及被取代条款；本文不授权这种变更。

**未被本次决定覆盖的产品问题**：Master Plan 第 ⑦ 项仍写强制 `data_collection: deny`，
第 10 节又记录其是否保留待确认。首版建议保留 deny、只开支持的线路；非 ZDR 不等于可训练。
在决定落定及线路能力核对前，不开放正式调用；不把建议写成已批准，也不在本方案作法律结论。
正式 32768 输出上限按 CHAT-NATIVE-OUTPUT 首版约束核验，不能把 staging 的 8192 证据冒充全容量证明。

## 3. 最小实现设计：开放资格和报价分离

### 3.1 唯一配置来源

- 模型身份、启用状态、线路目录、价格：仍在 `ai_models`，价格只用 `config.pricing`。
- 正式准入资料：建议扩展同一行 `ai_models.config` 的一个命名空间，保存 enabled、版本、
  endpointTag、profile/evidence 引用、用途、格式、思考变体和容量；准确 schema 在实施 PR 固定。
  不另建批准表、配置注册中心或与数据库竞争的代码常量名单。
- 模型默认覆盖仍用 `ai_models.price_multiplier`，全局 q/m 仍用现有 system_settings。
  当前 LLM 倍数按模型，`billing_provider_prices` 的线路倍数用于第三方服务，
  **不能把它误当成已经支持 OpenRouter 每条线路的 LLM 倍数**。
  最小补缺是在同一模型准入配置按 endpointTag 允许可选倍数，优先级为线路覆盖 → 模型覆盖 → 全局 6；
  保持现有第三方服务线路机制独立。快照保留所选线路、有效值和来源，TS/SQL 对应版本同步支持。
- 敏感凭据仍走现有私有存储；公开方案、PR、日志只记非敏感模型标识、版本和结果，
  不放 API key、account 指纹、测试账号、供应商回执正文或用户输入。

现有表和权限足够承担这些资料；仅需扩展已有配置 schema、管理界面与现有 SQL 校验，
不增加持久化基础设施。实际迁移只追加到 `packages/db/migrations/`，不修改历史迁移。

### 3.2 资格生命周期

1. 新模型/新线路默认不可收费。后台先读取目录和价格，选择精确线路，绑定用途、请求格式及思考参数。
2. 核对现有真实采样证据是否覆盖该组合、输入边界、输出语义、缓存及成本上界。
   初次准入使用获批预算；既有同模型同线路证据可复用，不能用 fixture 代替。
3. 管理员通过现有模型管理入口启用；正式配置操作须先取得第 8 节授权。
   上线批准覆盖已列出的初始模型/线路，不逐次请求价格审批。
4. 资格没有固定失效日期。模型/线路变更或实时计量异常时，停止受影响新调用，重新采样并复核后恢复。
   单纯调价、倍数变化或证据年龄不触发重新采样。
5. 用途、格式、思考或容量不在证据覆盖内时仍拒绝；不能借“无到期”扩大已验证范围。
   优先限制在现有覆盖范围；如果新增能力必须扩大范围，独立交接，不自动追加付费采样。
6. 沿用 `budget_conflict`、`metering_missing`、`metering_exit` 与计量复核记录。
   当前 claim 的异常阻断按模型生效；首版保留这一保守范围，不能宣称已做到仅封单线路。

资格撤销必须在 claim/dispatch 和 resume 的新调用处复核，不能仅挡新 run。
已派发调用的收据读取、结算和展示不因模型下架而丢失。

### 3.3 正式准入顺序

认证与目标环境确认 → 原请求幂等重放/已有运行恢复 → 权益和数据归属 → 新工作开关及消息限流 →
模型/固定线路资格 → 价格与 q/m → 冻结 run 身份和商业倍数 → 每次调用重新报价并原子 claim →
派发前复核撤销和调用限流 → 唯一 dispatch → 回执与结算。

正式只允许 BILL2 v2。缺少/关闭正式 PAYG 配置直接拒绝；不能沿用 staging 中
`runtime_payg_staging.enabled=false` 返回 undefined 后退回 v1 的行为。
环境不认识、合同不匹配、配置读取失败均拒绝，不能降级到本地 fixture 或旧收费接口。
现有 Legacy 入口关闭策略保持，不通过旧接口绕过新钱路。

SQL 检查范围必须覆盖 prepare、claim、dispatch、resume、取消及恢复，
包括 `runtime_billing_allowed`、窗口检查和 pending financial batch 的环境假设。
保留现有权限/RLS、锁序、幂等键、active_execution、runtime_epoch 和 stopAt 语义。
权限只来自服务端与 SQL，不来自客户端的 mode、model、价格或 actor 字段。

### 3.4 provider 语义

后台标签和准入比较要区分以下身份，不做全库字段重命名：

| 字段/概念 | 正式用途 |
| --- | --- |
| `ai_models.provider` | 现有模型记录的提供方/接口分类；其含义由 `providerUtils` 和当前模型数据确认，不能拿它猜实际服务线路 |
| call 的 `provider=openrouter`、`protocol=openrouter-chat-v1` | 本次调用的聚合服务和协议 |
| `providerLimits.providerSlug`、`endpointTag` | OpenRouter 精确服务线路；资格、价格、路由及线路倍数按它绑定 |
| 模型 ID 的前缀 | 模型发布方，不代表实际供应商线路 |
| call 的 `account` / `account_namespace` | 原凭据的私有账户绑定，供幂等和回执核对，不是供应商名称 |

实施检查现有 SQL 的 provider 判等和 transport 的接口解析，明确模型记录分类与 call 聚合服务
的映射；未知组合拒绝。先在局部边界用具名变量/类型澄清，只有真实数据不兼容时才追加最小迁移。
第三方搜索线路沿用自身身份和费用规则，不把它们硬塞进 OpenRouter 的 endpointTag。

## 4. 报价、门槛与结算

### 4.1 自动报价不等于自动换线路

沿用 MODEL-PRICING-SYNC 的快照来源；第 40 项的正式自动价格取代其旧方案中
“涨价待重新批准”的正式环境处理，staging 窗口上界仍照旧。
七天新鲜度是价格数据要求，**不是准入资格到期**。过期时由原请求路径刷新，
失败冷却 60 秒；正式必须成功落库或读到并发写入的新鲜快照，不能用未落库价格放行。
固定 `provider.only`、`allow_fallbacks:false`、`require_parameters:true`、冻结 `max_price`，
不因涨价、429 或供应商不可用自动换模型/线路。

每次尚未领取的 call 读取同线路新鲜价格，重算名义价格表和上界 U；
已领取 call 的价格、输入、请求 hash 和回执绑定不可改。
**当前 SQL 把 call 价格/hash 与 run stable policy 判等，尚不支持上述逐次刷新。**
实现必须版本化区分稳定身份/资格与逐 call 价格，复用既有 call payload 承载冻结报价，
在同一受保护领取路径验证快照来源、线路、价格版本与上界，禁止客户端任意提交价格。
仅调用 `deriveProductionPaygPricing` 然后绕过 SQL 判等不是可交付实现。

正式 v2 run 不保留按准入价格算死的美元总预算，也不因旧 run.deadline 阻断长期充值恢复。
沿用 [BILL-PAYG 第 6 节](BILL_PAYG_PLAN.md)：止损由 run 调用次数上限、每 call 的 U、
余额封顶 H 和 OpenRouter 全站限额承担；有限的是每次派发/查回执的时间，恢复使用原 run、
新 epoch 和新 call 时限，不重置调用数、不重放已付费工作。供应商涨价时后续 call 用新价冻结，
不能因旧 run.budget_usd 不足要求用户新开 run。固定美元窗口预算只保留在 staging。
实施须同步修改现有 claim 中 used+u 与 r.budget_usd 的比较及其他同类校验：
仅经正式授权的 production v2 分支改用上述保护，旧 staging/v1 预算与恢复契约不放宽。

### 4.2 q、m、L、G、H

沿用 [BILL2 契约](tasks/V3-BILL-2-provider-authoritative-billing.md) 的 v2 规则：

- q=100；默认 m=6，按获准模型/线路覆盖。run 冻结商业规则，call 复制所选有效 m_i；
  暂停继续、配置切换、恢复都不能重解释旧 run 的 q/m。
- `L=max(1,ceil(typicalUsd×q×m_i))`；typicalUsd 是模型＋用途的典型**名义美元费用**，非官方折后账单。
  按 #686 原事务冻结实际 L 和 threshold_version；同 call 的 L 和 G 必须用同一个 m_i。
- 可用余额 A≥L 才领取；`G=ceil(q×U×m_i)`，`H=min(G,A)`。
  A<L 在调用之间等待，未领取不派发。已有冻结必须从可用余额扣除，保留并发与退款中的隔离规则。
- 累计 `N=ceil(q×Σ(n_i×m_i))`，每次应计增量取累计差额，实际扣款受 H 限制；
  保持 C+E=N。不能每个 call 单独进位后相加，也不能用官方折后成本替换名义收费。
- 官方实际费用 c 单独对账，缓存差额保留；平台承担项不变成以后追收的欠款。
  可靠 token 缺失但 c 已知按现有 actual_fallback；费用未知保留 hold、进入 cost_pending。
  迟到回执只走现有幂等恢复，不能二次扣费或猜测退款。

例：typicalUsd=0.02、q=100 时 m=3 的 L=6，m=6 的 L=12。
例子仅验证公式，不代表正式模型的实际典型费用或本次配置指令。
提高倍数自动改变后续有效合同的门槛；不重新采样、不全局改写旧调用。

## 5. 限流、监控与告警

### 5.1 限流与供应商花费上限

复用 `runtime_rate_limits` 与 Upstash 滑动窗口，按认证用户计数、环境分 namespace。
首版建议显式沿用当前默认：消息 10/分钟、200/24 小时；调用 30/分钟、600/24 小时。
这是建议配置，正式写入须批准；24 小时为滑动窗口，不称为自然日额度。
BILL2 v2 继续沿用当前调用预留语义，充值不能绕过次数限额。
Redis/配置不可用拒绝新调用，不能退化成本机计数或默认放行。
重放、看历史、停用及已派发调用的对账不消耗新的模型调用额度。

全站花费上限由 OpenRouter 的正式运行凭据限额承担；若多凭据共享正式流量，
上线前确认所有凭据每日额度之和不超过已批准全站每日上限，不能把某一把 key 的上限说成全站上限。
优先一把专用运行凭据用于这批模型，避免建立自有总预算计数器。
不新增自动充值或自动提额。供应商拒绝后按原请求状态处理，不盲重试、不更换凭据绕限额。

OpenRouter 官方支持 key 的 USD limit、daily/weekly/monthly 重置或不重置，以及可空的 expires_at；
日重置为 UTC 午夜，与用户次数的滑动 24 小时不同。
“无固定到期日”不等于无花费限制；本方案沿用 Master Plan 每日上限，批准包填明 daily 和具体金额。
每月/不重置等能力只是供应商可选项，不能在未同步新决定时替代本方案的每日上限。
参见 [官方 key 配置](https://openrouter.ai/docs/api/api-reference/api-keys/create-keys)
和 [key 状态读取](https://openrouter.ai/docs/api/api-reference/api-keys/get-current-key)。
不承诺供应商限额在并发在途请求下零超额；保留单 call 上界及异常停止，并在小额验收记录误差。

### 5.2 最小监控接线（待实现）

复用 pino/Sentry、现有管理财务页、`bill2PaygReport.ts` 与 diagnostics cron，
不新增事件总线、轮询服务、指标账本或定时任务。现有诊断不等于这些告警已经接好。
请求内记录即时异常；低频余额/累计成本检查复用既有诊断调度，正式频率在配置批准中确定。
不得为了探活周期性调用付费模型。OpenRouter 余额/限额查询失败记“未知”，不能按零用量或无限余额显示。

| 观察项 | 建议触发与动作 | 证据/出口 |
| --- | --- | --- |
| 计量缺失、输入/输出/成本越界、C+E≠N、重复扣费迹象 | 首次立即告警，停止受影响模型新调用；可反复利用、损失不清或多扣用户款时全站停新调用并报告 | 现有 bill2_calls 标志、复核记录、账本；保留冻结与恢复 |
| cost_pending、未释放 hold、恢复失败 | 建议超过 15 分钟告警；接近既有恢复期限升级人工，不自动当失败退款 | 按最老未结算时长、数量展示，不输出用户正文 |
| 每用户次数限额、Redis 故障、资格/价格拒绝 | 技术故障首次通知；普通用户触限聚合；持续 5 分钟拒绝率异常时升级 | 结构化错误码、环境、模型、线路、版本 |
| OpenRouter 上限/余额 | 建议额度消耗 80% 提醒、95% 紧急；不足以覆盖可用单次上界或额度耗尽时停止新调用 | 供应商 key 使用量/余额；重置规则及查询时间一并展示 |
| 平台承担、名义/实际差额、全站日成本 | 从现有 calls/财务报表按 UTC 日聚合；反复异常或金额无法解释立即停；孤立可解释差额沿用现行规则人工处理 | 每日硬限额在 OpenRouter 执行，不以名义积分冒充供应商成本 |
| 上线可用性 | 登录、首字延迟、成功率、429/5xx、供应商拒绝、长对话容量 | 复用部署监控；约 100 条历史继续按已批准例外上线后观察 |

上述告警阈值是技术初值，不是已上线事实。接收渠道、通知可达性、静默/重复通知抑制
用现有监控平台配置；用合成事件验证首次通知与恢复通知，不往公开 PR 贴账号或敏感明细。
若现有 diagnostics 的频率达不到所定时效，实施时先复用请求即时事件并调整原调度，
不得把无法达到的“分钟级余额告警”写成已验收。

## 6. 回退开关与数据恢复

首选现有 `runtime_rate_limits.stopNewCalls=true`，阻止新消息及每一次新派发，包括 resume、
后台整理和报告。停止开关不是取消已发送请求：在途调用可能继续发生供应商费用，
必须保留原凭据可用性以查询收据、结算和展示已完成结果。

局部问题关闭该模型/线路资格；计量异常沿用现有模型级阻断。
资格撤销和价格故障不得阻断旧回执查询；绝不通过关闭 PAYG 退回 v1。
公开入口需要整体收回时，按已批准预案暂停正式站；站点暂停也会影响应用内恢复，
因此先安排原钱路的受控恢复入口，不能把“暂停站点”等同于“账已结清”。
供应商停 key 仅用于泄露等必须切断的情形，须说明它可能使原账户回执读取中断。

数据库以兼容的追加迁移为主。上线出错优先关新调用，再回退到**能读已产生正式合同**的已验证代码；
不能直接退到只认识 staging/v1 的旧版本。结构回滚不删除 calls、holds、receipts 或 ledger。
配置恢复采用上线前保存的完整旧版本，保留其他模型/用途条目；读回确认后再考虑重新开放。
恢复开放前必须解释原因、复核受影响证据并取得正式配置恢复授权，不能因告警消失自动重开。

### 7.2 必测矩阵

- 准入：已验证与未验证账号、禁用/删除账号、越权 workspace、错误环境/分支/数据库、

- 价格：同线路涨价/降价、七天边界、刷新失败/并发写入失败、未知字段、线路消失，

- 限流/运维：分钟与 24 小时、Redis 超时、配置修改不重置计数、开关生效、

### 7.3 正式上线顺序与停止点

1. **无正式副作用的准备**：完成 A–C，独立审查与 exact-version CI；最新 main 的依赖审计，
   将修复纳入拟上线版本。#697 仅是已知修复线索，不能单凭 staging 绿灯放行 main。
   核对 RUNTIME-PROD 依赖及 REL-1/D1 其余上线项，本文不能单独授权全站公开售卖。
2. **准备具体批准包**：列正式项目/域名/数据库目标、版本、迁移前后差异、旧配置恢复材料、
   初始模型/线路/证据及 q/m/typicalUsd、OpenRouter 每日限额金额、通知渠道与小额 smoke 预算。
   未读正式系统的事实标 NOT_RUN；先申请精确的正式只读核验权限，再形成最终写入批准包。
3. **正式只读核验（需批准）**：读取站点暂停状态、绑定、数据库版本/结构、迁移积压、
   配置存在性及供应商限额；不输出密钥。偏差只修订受影响计划，再审查/批准，不能盲套 staging。
4. **维护态准备（需批准）**：先保持站点暂停及新调用关闭，备份恢复材料；
   按兼容顺序应用已审查迁移、正式配置、凭据/限额与监控；所有值读回核对。
   不把 staging 测试用户/窗口/账号绑定复制到正式库。Vercel Pro 等付费升级单独列入批准包。
5. **上线触发（需批准）**：明确 main 合并可能自动触发生产部署，在触发前获得批准；
   核对分支集成和暂停站恢复是否自动接收流量。验证生产新调用仍关闭，再恢复站点访问。
   不能等 main 已合并或生产已部署才补审批。
6. **有上限的小额正式 smoke（需批准）**：指定受控身份、模型/线路、调用数与累计预算，
   覆盖一次成功、已确认拒绝、重复操作与回执对账；不为测限额故意耗光余额。
   smoke 开放阶段用现有部署访问保护限制公众访问，测试名单不成为长期准入系统；
   如果当前平台无法隔离 smoke 流量，保持模型调用关闭，修订具体上线步骤后再批准。
7. **对账后公开开放（需批准）**：核对官方成本、名义费用、实际扣款、平台承担、hold 释放、
   重复请求无新派发，确认告警与停止可用，再按批准范围开放。
   禁止把站点恢复、Runtime 开放和真实 Stripe 操作合成一个隐含授权。
8. **异常回退**：立即按预先批准的第 6 节范围停新调用，保留恢复；记录实际部署/供应商状态后再重试。
   观察成本、错误及未结算项，未解决账务或安全异常不继续扩流；不创建自动恢复开放任务。
