> 同意银行卡 Gold 首期改为"首月 49 美元"（自然月），用一次性优惠券实现。中国大陆的用户可以提供微信、支付宝单笔购买，也可以提供普通 Stripe 的银行卡订阅给他们。同意 MP 价格不含税，税在结账时另外加。同意银行卡订阅全部走 Stripe Managed Payments（中国大陆除外），暂不按美国单独分流。

## 一、大白话总结

**以后怎么收钱：**

| 用户在页面上选的付款方式 | 实际走哪里 | 谁是卖家 | 税 |
|---|---|---|---|
| 国际银行卡 / Apple Pay / Google Pay（订阅） | Stripe 结账页，开 MP | Stripe（Link） | 结账时按买家所在地另外加。**在 MP 负责税务的 80 多个国家**，由 Stripe 代收代缴；其他国家仍由 Graylum 负责（见下文"MP 不负责税务的国家"） |
| 中国大陆用户 → 微信 / 支付宝（单笔，现有） | Stripe 结账页，不开 MP | Graylum | 不另外加税 |
| 中国大陆用户 → 中国大陆银行卡订阅（新增） | Stripe 结账页，不开 MP | Graylum | 不另外加税；Owner 已咨询税务（第四节） |

- Waffo 只停用、不删：把 Waffo 银行卡的新购买开关关掉，代码、数据表、回调入口、每日对账都保留。
- 会员规则基本不变：首月 49、创始 496 锁价、升级、到期不续、积分发放、年付分 12 期都照旧，只是换由 Stripe 执行。具体对应关系见第三节。
- **要拆成 6 个 PR**，其中 4 个属于高风险（钱和数据库），需要 **2 个迁移编号**（向总控申请）。
- **正式环境需要 Owner 在 Stripe 后台做的事**列在第五节，每一项都要 Owner 自己操作或批准。

### 已定案的 2 件事（Owner 2026-10-12 均同意推荐项）

1. **微信/支付宝的 Gold 首期也改成"首月 49"（自然月）吗？** 现在钱包单笔的首期是 30 天（2026-10-10 决定），银行卡已改为自然月。两者不一致的话，价格页要分开写"首月"和"首 30 天"。
   - 推荐：**统一改成"首月 49 美元"（自然月）**，文案和计算都只有一种。钱包的普通 1 个月本来就是按自然月算的。
   - 可以直接复制的话：`同意微信/支付宝的 Gold 首期也改为"首月 49 美元"（自然月），和银行卡一致。`
2. **国际银行卡能不能买积分包？** 现在规定银行卡不能买积分包，因为 Waffo 只做订阅。MP 支持单笔付款（测试模式已验证能建会话），技术上可以开放。
   - 推荐：**开放**（仍然只限会员购买），积分包同样"税另计"。
   - 可以直接复制的话：`同意会员可以用国际银行卡（MP）购买积分包，税另计。`

## 二、架构

### 2.1 付款方式和路由

- 前端付款方式分两组（订阅页、积分包页、付费墙弹窗都一样）：
  - 「国际银行卡 / Apple Pay / Google Pay」→ 内部方法 `card`（MP）
  - 「中国大陆用户」分组，旁边写"仅限中国大陆用户"：`wechat_pay`、`alipay`（单笔，现有）、`card_cn`（中国大陆银行卡订阅，新增）
  - 默认选中哪一项，按 IP 国家（Vercel 请求头）和浏览器语言给出提示，用户可以改。服务端只认用户的选择，不用 IP 强制。
- `methodRouting.ts`：
  - `paymentMethodSchema` 增加 `card_cn`。
  - `paymentRoute()` 改为：`card` 买会员 → `{channel:'stripe', mode:'subscription', managedPayments:true}`；`card` 买积分包 → `{channel:'stripe', mode:'payment', managedPayments:true}`（Owner 已同意会员可以用国际银行卡买积分包）；`card_cn` 只用于会员订阅 → `{channel:'stripe', mode:'subscription', managedPayments:false}`；钱包不变。
  - `payment_method_routes` 设置增加 `card_cn.enabled`；Waffo 银行卡不再作为路由目标，但旧的 Waffo 订单照旧走 Waffo 续费、退款、对账（沿用 D17"旧订单原渠道"的规定）。
  - `PAY_WAFFO_LIVE_DISABLED`（只允许测试模式）这道闸保留，正式开卖另行批准。
- 数据库（迁移①）：
  - `pay_waffo_method_contract`（0204:168）：允许"`card` + `stripe` + 会员 + 订阅（自动续费）"和"`card` + `stripe` + 积分包 + 单笔（payment，不续费）"；`card_cn` 只允许"`stripe` + 会员 + 订阅"；旧的"`card` + `waffo` + 订阅"继续有效，用于已有的 Waffo 订单。
  - `payment_orders` 增加 `stripe_managed_payments boolean`（订阅和价格映射不用加：订阅一定来自某个订单）。下单时写入，付款后用 Stripe 返回的 `managed_payments.enabled` 核对，两者不一致就转人工。
  - `payment_provider_refs` 增加"一次性 / 订阅 / 积分包"区分字段，并允许保存首月优惠券。原因：同一个 Stripe 账户里会同时存在钱包单笔会员价和银行卡订阅价，按现在的唯一键会冲突，而且优惠券也没有地方存（实施时按代码核对发现，总控 2026-10-12 认可）。
  - `0211` 里 `pay_waffo_admit_purchase` 写死的 `card → waffo`（:570）改为按方法路由。资格判断（首月、创始名额、升级）整段复用，不另写一套。
- 复用的现有代码：
  - 下单和资格：继续走新的 `methodCheckout` 路径（条款版本、限流、首月和创始资格、名额预留都在这里）。旧的全局 D17 路径 `payments.ts createCheckoutSession` 保持停用，不复活。
  - 建结账会话：`stripeCheckoutIntent.ts` 的幂等派发和找回原会话逻辑都复用，只改生成请求的部分（见 2.2）。
  - 付款后：仍由 Stripe 回调入口 `apps/web/src/app/api/stripe/webhook/route.ts` 接收。**首次付款走 `pay_waffo_fulfill_payment`**，和微信/支付宝单笔用同一套，因为首月资格、创始名额从"预留"变成"已售"、发放窗口都在这套 SQL 里；**续费参照 `pay_waffo_renew_subscription` 另做一个 Stripe 版**。旧的 `stripeFulfillment.ts` 发放路径不复用（实施时按代码核对后修正，总控 2026-10-12 认可）。验证时实测确认，MP 订阅发出的都是标准事件。
  - 退款和对账：复用 PAY-COMMON 的人工退款审批和每日对账入口（04:00）。

### 2.2 `stripeCheckoutIntent.ts` 的改造点

- MP 请求（`card`）：
  - 去掉 `payment_method_types`，加上 `managed_payments: { enabled: true }`。
  - 不传 `custom_text`、`automatic_tax`、`tax_id_collection`、`customer_update`、`invoice_creation`、`subscription_data.invoice_settings`。其中 `custom_text` 和 `payment_method_types` 实测会被拒，其余按官方文档不传。
  - 首月 49：`discounts: [{ coupon: <首月优惠券> }]`。优惠券是 `amount_off=2000 USD, duration=once`，只用于 Gold 月付价格。现在 `:34` 遇到订阅打折就报错，要改为只放行这一种服务端选定的优惠。
- 大陆通道请求（`card_cn`）：`payment_method_types:['card']`，加 `billing_address_collection:'required'`，用来拿账单国家，不开 MP。
- 付款核对（`purchaseFacts.ts:56`、`stripePurchaseEvidence.ts`）：现在要求 `amount_total` 等于订单快照金额，MP 下这一项会多出税。改为核对"税前金额"（`amount_subtotal − amount_discount`）等于快照，税单独记到订单上（`total_details.amount_tax`）。价格的 `tax_behavior` 统一设为 `exclusive`，订单快照里也要记成 `exclusive`。
- 所有用于 MP 的产品都要设置税务编码 `txcd_10105001`（AI 即服务，个人使用），没有设置的直接拒绝建会话（实测 Stripe 会报错）。

### 2.3 判定大陆用户：兜底和误选的后果

| 情况 | 会发生什么 | 兜底 | 后果 |
|---|---|---|---|
| 大陆用户误选"国际银行卡" | MP 结账页在用户提交时报 "China is not currently supported."，**用户还停在 Stripe 页面，不会自动跳回我们这里** | 用户点 Stripe 页面的返回，会带着会话 ID 回到我们的取消地址。我们看到这个会话没有付款，就提示"如果你在中国大陆，请改选'中国大陆用户'"。我们拿不到 Stripe 拒绝的具体原因，所以只能这样笼统提示 | 没扣钱，只是多走一步 |
| 非大陆用户误选（或故意选）"中国大陆银行卡" | 付款成功，Graylum 当卖家，没有另外收税 | **按 Owner 决定，前期不做检查**，只靠页面上写明"仅限中国大陆用户"。可选：每日对账如果顺手就能列出"大陆通道、但账单国家不是 CN"的订单，就列出来供人工查看；不为此新建机制 | 拿欧盟、英国买家来说，Graylum 第一笔就要交增值税，金额算不清。这是 Owner 接受的风险，出了问题再调整 |
| 大陆用户用境外卡、账单地址填 CN | MP 拒绝（MP 按账单国家判断）；大陆通道可以付 | 不需要额外处理 | 正常 |
| 大陆用户在 MP 填了非 CN 的账单地址 | MP 付款成功，按那个国家加税，Stripe 当卖家 | 不处理。账单国家在 MP 负责税务的范围内时，不是 Graylum 的税务风险；不在范围内时，见下文"MP 不负责税务的国家" | 用户多付了那个国家的税，属于用户自己的选择 |

只看 IP 不可靠（有代理、出差），只看卡的发卡国家也不可靠（大陆用户常用香港卡）。所以以**用户自己的选择**为准。大陆通道建会话时仍然带上 `billing_address_collection:'required'`：结账页本来就要收卡的账单地址，这样订单上会留有账单国家，以后要查或者要调整时有数据可用，不增加流程。

### 2.4 MP 不负责税务的国家（审查发现，需要 Owner 知道）

MP 只在官方列出的 80 多个国家代收代缴税（具体国家清单以官方 [tax-compliance 页](https://docs.stripe.com/payments/managed-payments/tax-compliance) 为准，例如美国、加拿大、英国、欧盟、台湾、香港、日本、韩国在范围内；中国大陆不能用 MP 付款）。其他国家的买家用 MP 付款时，Stripe 仍然当卖家、处理付款和拒付，**但那个国家的销售税或增值税由 Graylum 负责**：要不要登记、收税、申报，都是我们的事。官方给的做法是开 Stripe Tax（在 MP 交易上不收计算费），用它监控各国门槛，到了门槛再登记。

按 Owner"前期不过度开发"的要求，方案只做下面两件事，不做按国家拦截：
1. **上线前**，在正式环境开通 Stripe Tax 的门槛监控（后台操作，不写代码，列入第五节需要 Owner 做的平台事项）；
2. **每日对账**里，如果顺手能列出"账单国家不在 MP 负责范围内"的订单，就列出来供人工查看；不为此新建机制。

如果 Owner 想彻底避免这部分风险，可以改成"只卖给 MP 负责税务的国家"：建会话前按用户选的国家拦截，但用户可以填别的国家，所以拦不严。这是产品决定，由总控向 Owner 确认，本方案默认不做。

## 三、规则怎么对应到 Stripe

| 规则 | 现在（Waffo） | 改为（Stripe MP / 大陆通道） |
|---|---|---|
| Gold 首月 49 | 30 天试用 + 49 | 一次性优惠券：首张发票 49，之后每月 69；第一期按自然月（已验证）。资格仍由 `pay_waffo_admit_purchase` 判断（任何渠道买过 Gold 就不再享受） |
| 创始 496/年锁价 | Waffo 创始订阅 | 单独一个"创始年付"价格 49600/年。续费沿用同一个价格对象，所以价格锁住（已验证第 365 天按 496 续费）。50 个名额的预留和计数沿用原逻辑。以后 Gold 调价时新建价格，不改旧的 |
| Pro→Gold 升级 | 新买一份 Gold + 取消 Pro 的续费 | **照旧**：新开一个 Gold 结账（MP 订阅只能通过结账页创建），付款确认后把 Pro 设为 `cancel_at_period_end`；48 小时边界、退款后恢复 Pro 剩余期限这些规则都不变。**不用** Stripe 的原地升级（虽然验证过可行），因为那样退款后没法恢复 Pro |
| 到期不续 | 期末停止 | `cancel_at_period_end=true`，到期后 Stripe 发 `customer.subscription.deleted`（已验证）。用户在 Link 网站上自己取消也会发同样的事件，我们照常处理 |
| 积分发放 | 每期一次、年付分 12 期 | 月付在每张 `invoice.paid` 时发一次；年付在首张发票时建立 12 期计划，由 03:00 的定时任务按月发放（`annualReleaseContract.ts` 要允许 `stripe` + `card` / `card_cn`） |
| 24 小时会员宽限 | 只适用于 Waffo 银行卡（0214） | 迁移②把条件扩展到 `stripe` + `card` / `card_cn`。到期后 24 小时内保留会员（不发积分、不放开积分包），等续费到账 |
| 创始 7 天资格宽限 | 续费失败后 7 天 | 不变：从 `invoice.payment_failed` 起算 7 天，期间续费成功就保住创始资格 |
| Stripe 重试设置 | — | 后台"收入恢复 → 重试"改为**自定义：失败后第 1、3、6 天各重试一次（在 Stripe 里填"距上次 1 天、2 天、3 天"），全部失败后取消订阅**。这样最后一次重试落在第 7 天之内，又不会早于 24 小时宽限就取消订阅。（沙盒当前设置是大约 25 天、2 次后取消，需要改） |
| 退款（我们发起） | 人工审批，7 天内、没用过，扣 6% | 规则不变，审批通过后用 Stripe 退款接口发一次部分退款。**待验证**：MP 部分退款时税怎么分（官方说退款会退还用户付的税）；实施时用测试时钟测一次 |
| Link 客服退款（60 天内）、48 小时不回复被代退 | 无 | 收到 `charge.refunded` 但我们这边没有对应的审批记录时，就当作"外部退款事实"：照退款规则收回这一期没用完的积分，结束这一期会员；不能退的部分 Graylum 承担，并记账 |
| 用户要求删除数据 | 无 | Stripe 取消订阅时会发 `customer.subscription.deleted`，按"到期不续"处理，不额外退款。这个用户在 Stripe 的客户信息被清空后，不能因为查不到资料就报错卡住 |
| 拒付 | Waffo 每天查询 | MP 下由 Stripe 代处理拒付。`charge.dispute.*` 事件的接收和冻结属于 PAY-DISPUTE-GUARD，本次只保证这些事件不报错（现在的代码没有处理它们）。大陆通道的拒付要我们自己处理，同样交给 PAY-DISPUTE-GUARD |
| 税另计的展示 | 不涉及 | 价格页、付费墙、个人中心订阅卡在价格旁写"税另计，结账时按所在地计算"（大陆通道和钱包写"不另收税"）。不能写预计税额。涉及的文件：`PricingSection.tsx`、`PricingPlans.tsx`、`PricingExtras.tsx`、`ReportPaywallDialog.tsx`、`SubscriptionCard.tsx`、`creditPackagePrice.tsx` |
| 账单商户名 | Waffo 控制 | MP 下显示 `LINK.COM* <账单描述>`，后台要把账单描述改成能认出 GRAYLUM 的写法 |

## 四、中国大陆普通 Stripe 卡订阅的税务风险（不下结论）

我不知道这条通道在中国以及在美国的税务处理是否合规，**需要税务顾问确认**。建议问的问题：

1. 美国怀俄明州 LLC 通过网站向中国大陆个人卖 AI 订阅服务（境外提供、境内消费的数字服务），在中国有没有增值税或其他税的纳税、扣缴或登记义务？如果有，由谁负责、按什么税率？境外卖家实际上有没有办法登记？
2. 如果中国大陆买家用银行卡付款时，发卡行或者买家自己代扣代缴，我们需要提供什么凭证（例如发票）？
3. 美国这边：这部分收入要按怎样的口径计入 LLC 的收入？有没有州销售税问题（买家不在美国，通常不涉及，但请确认）？
4. 卖给中国大陆买家的 AI 服务，有没有中国的跨境数据、内容或电信增值业务许可要求，会不会影响收款？（这超出税务范围，可能要问律师）
