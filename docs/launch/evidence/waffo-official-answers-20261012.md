# Waffo 官方答复（2026-10-12）与代码核对

来源：Owner 2026-10-12 从 Waffo 拿到的官方答复，由总控窗口转给 PAY-WAFFO 执行窗口。下面是答复要点（转述，不是逐字原文），
每条后面写本站代码的核对结论和这次的改动。

## 1. 测试模式的续费

**Waffo 要点：** 测试模式不能缩短订阅周期。后台有「模拟续费」，可以选成功或失败，每点一次推进一个周期；只能在后台手动点，没有 API。

**我们现在是否正确：** 代码不依赖缩短周期，所以没有要改的。续费发放、24 小时宽限、续费失败这三条路径，到现在只有自动测试，还没在 Waffo 上真正跑过。
下面「续费验收步骤」由 Owner 或 Codex 在 Waffo 后台手动点。

## 2. 结账会话没有幂等

**Waffo 要点：**
- 创建结账会话**没有幂等键**，重复调用会生成多个互相独立的会话。
- 超时后不能按我们的订单号查回会话，只能按 sessionId 查。
- 没付款的会话不产生订单、不扣款，默认 24 小时过期。
- 去重要在订单层用 `orderMerchantExternalId` 做；这个字段不唯一，平台不拦重复。

**核对结论：**
- 原代码注释写的「同一个幂等键重放会取回原会话（已实测）」**不对**。按官方答复，每次调用都会新建一个可付款的会话。
- **用户能不能拿到两个付款页面？** 不能。`pay_waffo_bind_checkout` 每个订单只绑定一个会话，第二个会被拒绝；页面地址也只在绑定成功后才返回给用户。
  所以就算 Waffo 那边多了会话，用户也只能看到其中一个。
- **改动：** 订单已经绑定过付款页面时，再点购买不会向 Waffo 新建会话，直接返回提示（409 CONFLICT）：原页面还能用，或等订单自动关闭后重买。
  原来的做法会白白新建一个会话，然后在绑定时报 503。只有「建会话的响应丢了、用户从没拿到页面地址」的订单，才会在结账窗口内重新建一个。
- **最坏情况（同一订单两笔首期付款都成功）：** 原代码会把第二笔当成「重复回调、已发放」直接放过，不退款、不停续费，每日对账也查不出来。
  **改动：** 回调时识别「订单已发放，但这是另一笔付款、属于另一个 Waffo 订阅」，把它记为 `duplicate_order_payment` 转人工（作为退款候选），
  并立即停止这个订阅的续费（沿用 #823 的先停续费、读回核实、再结束回调）。每日对账也会把这种付款列成 `paid_in_review` / `duplicate_order_payment` 的退款候选。
- **`expiresInSeconds=1800` 有没有生效：** 生效。证据有两条：
  - 我们只接受 Waffo 返回的过期时间不晚于 31 分钟的会话（`validateWaffoCheckoutSession`），#815 的真实结账通过了这道检查；
  - #802 浏览器观察到会话过期后页面显示「此结账链接已过期」，不能付款。
  所以「24 小时默认过期」只适用于没传这个参数的情况。即使哪天参数失效，40 分钟释放之后才到的付款，也会走迟到付款路径：转人工、作为退款候选、停止续费（#823），不会开通会员，也不会悄悄丢掉。

## 3. 查询和退款的时延

**Waffo 要点：** 查询接口没有延迟，延迟在写入一侧，也就是要等回调；退款通常 10–30 秒完成。

**我们现在是否正确：** 是。回调处理时会先按 paymentId 查一次付款；查不到就返回 503，让 Waffo 重新投递，不会猜。退款这次不涉及。

## 4. 回调的顺序、重复和失败

**Waffo 要点：** 回调不保证顺序，可能重复。同一事件最多投递 5 次，都失败就标为 failed，没有手动重发。投递按「webhook + 事件类型 + 事件 ID」唯一。

**核对结论：**
- **去重：** 是。`waffo_event_receipts` 有 `UNIQUE(merchant_namespace, mode, event_type, event_id)`，同一事件重复投递只会记一次；收据结案后再收到会直接忽略。
- **乱序：** 是。每次都按 paymentId 查权威付款，不靠回调里带的数据。续费按期号和期间起止判断，迟到的旧一期不会把当前期限往回改（数据库测试 `out-of-order-renewal-no-term-rewind`）。
- **5 次都失败之后：** 每日对账会扫 Waffo 的已付款记录，列出「已付款但没开通」（`paid_not_delivered`），订阅还在续费的会标 `renewalActive`。
  **改动：** 对账新增 `receipt_unprocessed`，把收到超过 24 小时还没处理完的回调收据列出来，覆盖「Waffo 已放弃投递」和「处理开关没开」两种情况。

## 5. 期号和账期

**Waffo 要点：** `Payment.periodNumber` 是这笔付款对应的期号。账期起止只在订阅单上，而且永远是当前这一期。

**我们现在是否正确：** 是。`readPaymentFacts` 只在付款的期号等于订阅单当前期号时，才采用订阅单上的起止；否则记为 `period_not_current` 转人工，不推算历史期。
每期起止在回调处理时就写进对应订单（`entitlement_start` / `entitlement_end`），以后不再拿当前账期去推算过去的期。

## 续费验收步骤（Owner 或 Codex 在 Waffo 后台操作）

**前提：**
- staging 已包含 #823（迁移 0214）和本 PR。
- 需要一个**还在自动续费**的 Waffo 测试订阅。#815 用过的那个订阅已经停止续费，不能用。新建订阅要用测试卡付一次款（测试模式，不扣真钱），由 Owner 或 Codex 按 #815 的方式完成。
- 每次只跑一个浏览器任务，不要并行。

**A. 模拟续费成功**
1. 记下测试账号当前会员订单的 `entitlement_end`、积分余额和 `user_subscriptions.current_period_end`。
2. 在 Waffo 后台对这个订阅点「模拟续费 → 成功」。
3. 预期：几十秒内收到回调。本站会新增一条续费订单（`status=completed`、`payment_status=paid`），
   它的起点等于上一期的 `entitlement_end`（首尾相接）；积分按套餐增加一次（Gold 加 8970）；`current_period_end` 往后推一期；回调收据标为 applied。
4. **要特别记下来的实测项：** 模拟续费给出的新一期起止，是从上一期到期日接着算，还是从「点按钮的时刻」算。
   如果是后者，本站会因为期间对不上把它判为 `RENEW_CONFLICT`、转人工，不发积分。这只说明模拟和真实续费的规则不同，不能算失败；
   请把付款的 `periodNumber` 和订阅单的 `currentPeriodStart/End` 原样记下，交给总控判断。

**B. 模拟续费失败**
1. 换一个还在续费的订阅（或在 A 之后接着用），在后台点「模拟续费 → 失败」。
2. 预期：本站不新增订单、不发积分。如果模拟把订阅推过了本站的已付期末，在已付期末之后 24 小时内仍是会员（不发积分、不能买积分包），
   24 小时后变成免费。如果模拟没有推过本站的已付期末，会员照常到原来的期末。
3. 记下 Waffo 订阅状态（`past_due`、`canceled` 等）和本站 `getEntitlements` 的结果。

**C. 通过 / 失败标准**
- A 第 3 步发放一次、首尾相接、不重复，算通过；如果发生 A 第 4 步说的情况，记录下来交总控判断，不算失败。
- B 不发积分、不多扣钱、宽限只在 24 小时以内，算通过。
- 不在范围：退款、真实到期日的自然续费（第一次在 2026-11-10）。
