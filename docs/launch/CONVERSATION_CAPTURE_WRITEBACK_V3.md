## 大白话摘要

右侧清单里，受保护的内容（用户自己填的或已确认的）不会被 AI 直接改，AI 只能挂一条「建议」等用户点「采用/忽略」。
现在有两个毛病：

1. **整理 AI 看不见已经挂着的旧建议。** 用户在旧建议基础上补一句，AI 只能凭空写一条新建议，把旧建议的内容盖掉。
2. **AI 没办法收回建议。** 用户说「那条不对、不要了」，旧建议还挂在那里。

上次评测 77/100 里，这两类各丢 10 题，另外 3 题是一句话里有两层意思时，被问到的那一栏漏了半句。

这次的做法：

- 让整理 AI 看到旧建议原文，新建议在旧建议基础上补，不再覆盖。
- 给整理 AI 加一个「撤回建议」动作。它只能清掉挂着的建议，**碰不到用户的正式内容**，由数据库保证。
- 补一条整理规则，让被问到的那一栏写完整。
- 右侧清单显示「导师已撤回这条建议」，用户点「知道了」就收起。
- 用同样的 100+12 道题复测，目标 90/100。预计实际花费约 0.15 美元，最坏情况也在剩余预算内。

不涉及价格、权益、主要流程或对外承诺，不需要 Owner 做新的产品决定。

## 目标、完成标准、不做什么

- 目标：解决上面 3 类失败，同一套 100 题达到 90/100，受保护字段被直接改动 0 次，格式错误不超过 1%。
- 完成标准：迁移、后端、整理规则、前端各自通过 CI 和独立审查；数据库按 ENGINEERING 要求验证；
  付费复测在最终代码上跑完并锁分；前端交 Codex 在 staging 用浏览器验收。
- 不做：不改金标、不删难题、不改模型、不改思考设置、不改 4096 输出上限、不改 Skill（不发 v10）、
  不改导师提示词、不改计费。不做建议历史列表，也不新建表。

## 现状（已核对 origin/staging `b9bf443b`）

- 建议存在 `artifact_rounds.steps[步骤].fieldMeta[字段].suggestion`（0182 `opc_capture_apply`），
  每个字段只有一条，新的整条替换旧的。
- 整理 AI 的输入来自会话冻结材料（`runtime_work_projection`），导师的输入也带这份材料。材料只带 `hasPendingSuggestion` 真假，
  **不带建议原文**；`captureOrganizerInput` 也没有建议原文。
- 整理输出协议只有 `patches`（写入或生成建议），没有撤回。
- 用户「采用/忽略」走 `opc_capture_resolve`，绑定执行编号加哈希，建议变了就报 `OPC_SUGGESTION_CHANGED`，
  前端已有「已过期」提示。`opc_query` 会隐藏来源对话已删除的建议。
- B 组剩下的 3 个非建议失败（C002、C008、C025）：一句话同时限定两个字段，限定只写进了相邻字段
  （offer/track），目标字段 goal/audience 缺了这部分。

## 最短正确做法（复用现有建议记录，不加表）

### 1. 整理 AI 看见旧建议（只改 API）

- 实施前核对发现：导师的输入里带着整份冻结材料（`hostTurnInput` 的 `scopeMaterial`）。如果把建议原文放进
  `runtime_work_projection`，导师的输入也会跟着变，评测冻结的导师回复就不能再用。所以**不改冻结材料**。
- 改为：`service.ts` 在本回合已经读到的草稿（`opc_query`）里本来就有建议原文，而且已经按「对话被删就隐藏」过滤过。
  只有冻结材料里这个字段的 `hasPendingSuggestion` 为真时，才把这条原文作为 `pendingSuggestion: {value, nature, basis}`
  放进**整理输入**。两边对不上（比如读取后恰好有新整理写入）就不放，整理行为和现在一样。
- 导师的 `captureHostContext` 和冻结材料都不变，导师输入逐字节不变。
- 输入上限沿用 24000 字符：先省略已确认步骤的值（现有做法），还超就拒绝（现有做法）。
  最坏情况是 14 个字段各带 400 字的值、说明和建议，估计在上限内，实施时用测试确认。
- 整理规则：受保护字段如果已有 `pendingSuggestion`，新建议要以它为基础合并成完整一条，
  保留其中的内容和限定，除非用户明确更正或否定。不能退回正式值后只写最新一句。

### 2. 最小撤回动作（迁移 + API + 规则）

整理输出加一个可选的顶层字段：`withdrawals: [{stepId, fieldId}]`，最多 12 条。
旧输出没有这个字段，行为不变；旧版 SQL 也会忽略它，所以上线顺序怎么排都兼容。

数据库（`opc_capture_apply`）按下面的规则执行，全部写死在 SQL 里，不靠模型自觉：

- 只改 `fieldMeta.suggestion`，**永远不读写 `information`**（正式值、状态、版本号都不动），
  所以从构造上不可能改到受保护或已确认的内容。
- 只有真正的用户发言回合才生效：开场和 `checklist_updated` 这类宿主事件里的撤回一律丢弃，记入 `discarded`。
- 只能撤回比本次执行**更早**的建议（用现有的 `seq` 时间加编号比较）。同一输出里如果又给同一字段生成了新建议，
  新建议保留，撤回记为 `superseded`。
- 被撤回的建议移到 `fieldMeta.withdrawnSuggestion`，内容是原建议加上撤回它的执行编号；`suggestion` 删除。
  于是 `hasPendingSuggestion` 自动变成假，导师也不会再提这条建议。
- 结果写进 `opc_capture` 的回执 `withdrawn: {步骤: [字段]}`，重复执行时原样返回（沿用现有幂等）。
- 不加版本号（现有建议写入也不加），所以不会让用户正在编辑的自动保存冲突。

整理规则：用户明确否定、收回或指出挂着的建议过时或错误，并且没有给出替代内容时，输出撤回；
给了替代内容就输出一条完整的新建议；用户要求保持当前正式值时也是撤回，不要把正式值再当成新建议挂一遍。
含糊的「算了」「好的」不能当撤回，没有挂着建议的字段也不能撤回。

### 3. 被问到的那栏写完整（只改规则）

在 `ORGANIZER_INSTRUCTIONS` 加一条通用规则：一个事实同时限定多个字段时（比如目标里的成交渠道、受众的需求场景），
每个被它限定的字段都要写进与本字段相关的那部分，不能只放进相邻字段。这条和现有的「不要整句复制进多个字段」不冲突：
复制的是限定，不是整句。
只写通用规则，不针对某道题措辞，防止只为了这 100 题调。改了以后 100 题全部重跑，能看到其他类别有没有退步。

### 4. 用户收起撤回提示（迁移 + API + 前端）

- `opc_capture_resolve` 增加 `dismiss` 动作，绑定 `withdrawnSuggestion` 的执行编号和哈希，只删除这条记录，
  不改正式值和版本号。`accept`/`ignore` 逻辑不变。
- 新建议到达同一字段时，自动清掉旧的 `withdrawnSuggestion`。
- `opc_query` 对 `withdrawnSuggestion` 套用和 `suggestion` 一样的过滤：来源对话已删除就不返回。

## 迁移

需要一个迁移：`0200_opc_suggestion_withdraw.sql`（总控分配；0198 已由 REPORT-MODEL #762 使用，0199 已分配给其他任务）。

- 只改 3 个函数：`opc_capture_apply`、`opc_capture_resolve`、`opc_query`。`runtime_work_projection` 不改（见上文第 1 点）。
  不改表结构，不改数据。
- 沿用 0195/0197 的做法：读取函数当前定义，含本迁移标记就跳过；没有标记就要求每个替换点恰好出现一次，
  替换后重建函数，对不上就停止。这样可以重复执行，改动只是几处插入，不复制整段函数。
- 新旧代码兼容：旧代码不会发 `withdrawals`，也不读 `pendingSuggestion`、`withdrawnSuggestion`；
  旧前端解析时会忽略不认识的字段（实施时用测试确认）。
- 恢复：如果要退回，执行一个恢复脚本，把这几处插入反向替换回去，重建这 3 个函数（脚本随 PR 提交，在本机演练）。
  已经写进去的 `withdrawnSuggestion` 是普通 JSON 键，退回后旧代码会忽略，不丢用户数据；
  已撤回的建议不会自动复原。这是预期行为，因为它本来就是被撤回的。
- 验证（ENGINEERING 要求）：同一位置连续执行两次，结构指纹不变；更新 `built-fingerprint.json`。
  SQL 集成测试覆盖下面这些情况：
  - 可见：`opc_query` 返回的建议原文进入整理输入；对话删除后不进入；导师输入不变。
  - 合并：新建议替换旧建议后，正式值不变。
  - 撤回：正常撤回；开场和宿主事件里的撤回被拒；撤回更晚的建议被拒；同字段同时有新建议时记为 superseded；
    受保护和已确认字段的正式值、状态、版本号逐字节不变；重复执行回执一致。
  - 收起：dismiss 正常；哈希不对报 `OPC_SUGGESTION_CHANGED`。
  - 并发：同时 dismiss 和 accept 时按现有锁顺序串行。
- 迁移由总控在 Owner 批准后应用到 staging；本窗口不远程执行。
- 实施时核对一项：注销执行器（0197）删除草稿时，会不会连带清掉 `withdrawnSuggestion` 里的对话派生文字。

## 风险

- 规则调优可能只对这 100 题有效：只写通用规则；三遍全量重跑，能看到其他类别有没有退步；专项 12 题另外检查。
- 3 题字段完整性和撤回边界取决于模型语义判断：可能到不了 90。到不了就如实报告失败的题和原因，不改金标或评分口径。
- 建议原文取自本回合的草稿读取，不在冻结材料里：读取和冻结之间如果恰好有新整理写入，整理 AI 可能看到旧一版的建议。
  后果只是新建议基于旧一版合并，仍然要用户点「采用」才生效；只在冻结材料显示有建议时才放原文，作为兜底。
- 撤回误判（把用户的含糊话当成撤回）：只清建议，不碰正式值，用户最多是少看到一条建议；
  撤回提示会显示原文，用户能看到发生了什么。
- 函数体很长（0182 原样复制再改）：靠 md5 校验、两次执行和集成测试兜底；审查只看差异部分。
- 迁移号可能和其他任务冲突：开工时以实际状态为准，并告诉总控。
