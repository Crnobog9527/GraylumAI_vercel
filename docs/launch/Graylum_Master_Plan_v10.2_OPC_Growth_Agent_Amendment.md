# Graylum Master Plan v10.2 — OPC 增长 Agent 产品修订

状态：Owner 于 2026-09-13 批准的产品修订。本文补充 `Graylum_Master_Plan_v10.1.md`；若旧文档关于聊天入口、项目结构、Skill 展示、上下文、联网路由、历史保留或多模型计费的描述与本文冲突，以本文为准。其余不冲突的支付、认证、安全、发布、验证和 Definition of Done 要求继续保留。

本文只定义产品 WHAT、实施顺序与验收边界，不授权功能实现、合并、远端数据库或供应商配置、真实模型调用、生产部署或其他外部效果。仓库执行仍以当前 `staging/AGENTS.md` 为准。

## 1. 锁定的产品定位

Graylum 是为 OPC（一人公司）打造的社交媒体运营增长型 Agent。产品不是一个允许用户无限堆积上下文的通用聊天框，而是围绕“账号定位—内容计划—单个选题创作—成果沉淀—数据复盘”组织工作的运营系统。

产品主路径：

```text
首页建立用户所属定位草稿与独立 Session
→ 按现有 Skill 完成六步定位与经营资料
→ 在草稿内生成第一周计划，确认定位版本与平台账号集合
→ 幂等创建平台账号项目及计划选题
→ 按日期展示选题
→ 进入单个选题的 Agent 工作空间
→ 调用 Skill、联网工具和连接器
→ 保存、确认、同步成果
→ 结合发布结果迭代下一轮
```

社交媒体项目与非社交媒体项目共用同一底层工作项机制：社交媒体项目中的工作项对用户显示为“选题”，非社交媒体项目中显示为“工作项”。

## 2. 首页六步定位是产品主入口

六步定位的业务内容、信息要求、步骤依赖和报告内容来自当前已发布的六步定位 Skill，不在页面代码中重新发明或写死。产品只改造交互机制：

- 使用独立、专注、有仪式感的六步定位页面；
- 通过导师式、苏格拉底式问答帮助小白表达真实经验、能力、目标和限制；
- 每次优先提出一个最有价值的问题，基于回答追问、澄清或举例；
- 追问围绕 Skill 声明的必需信息和完成条件，不允许无限追问；
- 每一步形成 AI 候选、可编辑工作稿和用户确认版本；
- 修改上游成果时，保留历史并只标记声明依赖的下游成果待复核；
- 支持中途退出、自动保存和继续完成。

首次定位不要求用户先有账号项目。第一轮模型调用或首次资料保存前，服务端先幂等建立用户所属的稳定定位草稿、独立 Session 和本轮 Skill revision 绑定；问答、步骤成果、确认版本与每次收费操作的运行单从产生起就有归属。定位草稿和项目内工作项是两种明确执行作用域，共用同一 Runtime、Session 适配、成果与账务机制，不创建占位账号项目，不通过缺少 project ID 绕过权限。草稿身份、恢复、作用域校验详见[架构规格第 2.3 节](tasks/V3-OPC-growth-agent-architecture.md#23-首次定位的前置归属)。

成熟账号用户可选择按同一 Skill 的标准结构手动填写或导入。导师问答与手动填写使用相同定位草稿机制，最终必须形成相同的六步成果、版本和账号经营资料，不维护两套业务结构。普通保存不触发模型费用。

六步正式版本及第一周计划先保存在定位草稿中；用户确认定位来源、具体平台账号和计划版本后，系统在一个数据库事务中幂等建立对应账号项目、选题及来源映射。第一周不写死为七条内容；数量、节奏和平台分配由六步成果及用户资源决定。重复确认或响应丢失后重试返回原映射，不重跑模型、不重复创建或扣费；过期版本、相同确认 ID 不同负载和现有账号定位冲突不得静默覆盖。详细规则见[架构规格第 5.2 节](tasks/V3-OPC-growth-agent-architecture.md#52-确认后的幂等承接)。

多平台账号仅引用用户明确确认的同一不可变定位来源及各自适用资料；原定位 Session、成果版本和费用保持原归属，不复制到多个项目。每个新选题使用新的独立 Session，各账号后续记忆和定位修订独立。中途退出不创建账号项目，重新登录后能继续原草稿；承接成功后仍能按原身份找回定位记录。

## 3. 项目、选题与记忆边界

一个平台上的一个运营账号对应一个社交媒体项目。不同平台、同平台不同账号及非社交媒体工作不得默认混用上下文。

每个选题或工作项拥有独立 Agent SDK Session；项目前定位草稿的独立 Session 按第 2 节保留，不改为项目公共聊天。项目公共记忆不是把项目内全部聊天反复塞入模型，而是由以下内容组成：

- 当前已确认的账号经营资料；
- 项目级已确认偏好、约束和决策；
- 可检索的成果索引；
- 必要时由管理员指定整理模型生成的有限摘要。

当前选题默认加载账号经营资料、选题简报、当前成果与该 Session 的相关历史。同项目其他选题成果通过受控工具按需读取；跨项目资料只有在用户明确指定目标后才允许定向读取。临时尝试、模型推测和用户已否定内容不得自动升级为项目事实。

账号经营资料由当前六步 Skill revision 从确认成果中提炼，并保留来源与版本。资料包含哪些维度由 Skill 声明，不把一套字段永久写死在页面和数据库业务代码中。

## 4. 导航、技能广场与 Agent 输入框

用户顶层导航锁定为：

```text
首页｜项目｜技能广场｜个人中心
```

“技能广场”保留为一级页面入口，并位于网站顶部导航栏。它用于发现、搜索、查看和进入可用 Skill；管理员对 Skill 的导入、发布、撤销和模型绑定继续使用受控后台。技能广场与输入框中的 Skill 菜单互补：前者负责发现与了解，后者负责在当前工作项内快速调用最近使用或已可用的 Skill。

连接器不设置一级导航页面。文件、连接器、Skill、模型选择和 Gold 多模型能力集成到 Agent 输入框：

- `＋`：文件、图片、连接器和最近使用来源；
- Skill 菜单及 `/`：手动选择 Skill；
- Agent：可根据用户意图自动选择允许的 Skill；
- 模型选择：仅影响普通 Agent 对话；
- 多模型智囊团：Gold 用户可开启，模型组合由管理员配置；
- 管理连接器：使用输入框弹窗或抽屉完成授权、断开、权限与默认目标管理。

连接器首批重点包括飞书、Notion 和 Slack。面向中国大陆用户，飞书多维表格应优先完成读取指定资料、字段映射、写入已确认成果和幂等更新闭环。

## 5. 统一 Agent Runtime 与模型职责

全站最终只保留一个基于官方 Agent SDK 的统一 Agent Runtime。普通对话、Skill、联网搜索、项目资料读取、连接器和多模型能力不得长期运行在彼此重复的编排与计费系统中。

模型职责锁定为：

| 场景 | 模型决定者 |
| --- | --- |
| 普通 Agent 对话与工作 | 用户从允许模型中选择 |
| Skill 执行 | 管理员在 Skill 配置中绑定，用户不可覆盖 |
| 信息汇总、Session 压缩和项目资料整理 | 管理员指定独立整理模型 |
| 多模型智囊团的参与模型、分析模型和外层模型 | 管理员配置；Gold 用户只决定是否开启 |

Agent 判断是否需要调用 Skill、搜索、项目资料或连接器；服务器负责权限、工具白名单、预算、身份和外部写操作。用户明确禁止联网时不得搜索；用户明确要求最新资料时必须调用允许的搜索工具或明确说明不可用。旧关键词任务分类、便宜/高级模型自动切换和正则联网判断在统一 Runtime 验收后删除。

Agent SDK Session 负责当前定位草稿或工作项的对话历史；Graylum 继续负责执行作用域、项目身份、账号定位、成果版本、权限、预算、工具和连接器。旧手写滑动窗口与上下文拼接器在新 Session 路径完成迁移和回归后删除。

## 6. Gold 多模型智囊团

“多模型智囊团”是当前产品工作名，可在营销阶段更名。它可用于所有允许的 Skill 或纯提示词任务，不限定六步定位。

启用后，多组管理员配置的模型在隔离上下文中处理同一份已冻结输入，用户可查看各模型原稿和最终综合稿。Fusion 或其他多模型能力必须满足：

1. 各参与模型真实获得同一 Skill 方法身份、必要资料和成果版本；
2. 发布、写入飞书、发邮件、付款等外部动作不得随模型数量重复执行；
3. 参与模型、分析模型、外层模型和工具调用的全部真实成本都进入同一计费运行单；
4. 部分模型失败、分析失败或实际参与数量不足时必须如实展示；
5. 只有完成官方成本回执、Graylum 账务和 OpenRouter 账户实际变化的真实小额对账后，才允许向 Gold 用户开放生产计费。

多模型数量越多不等于结果越好；管理员可按任务类型设置组合、输出上限和单次最高预算。

## 7. Provider-authoritative 原子计费

现有积分余额、积分流水及原子预扣/结算/退费能力继续作为唯一钱路，不建设第二套余额。新架构在其上增加“计费运行单”和“供应商成本收据”：

- 一次用户收费操作对应一个计费运行单，固定绑定用户、定位草稿或项目工作项作用域，以及对应 Session；
- 每次真实供应商调用保存唯一 generation/response 身份、具体模型、官方成本、usage、工具成本和状态；
- 调用前只做保守积分预留；
- 调用完成后使用供应商官方实际成本结算；
- 多次调用的精确成本先汇总，再应用该运行单冻结的积分兑换比例和商业倍率，最后只进位一次；
- 金额使用精确十进制或固定精度整数，不用 JavaScript 浮点数作为财务真值；
- 最终数据库事务一次完成余额差额、积分流水、账务历史、使用记录与运行单终态；
- generation 身份、运行单终态和预扣处理必须有数据库唯一约束和幂等语义。

一次六步定位可包含多张按操作结算的运行单，不等最后创建项目才结算。草稿向一个或多个账号项目承接只新增来源关联，不能改写历史账务身份；已结算记录保持不变，待核实调用继续按原 request/generation 恢复，不因刷新、确认或承接再收费。

普通独立模型调用可逐项保存官方成本后汇总。Fusion 若官方只提供整次请求的权威总成本，则按该总成本一次结算，不自行猜测各内部模型成本。

成本回执暂缺但供应商可能已执行时，运行单进入 `cost_pending` 或 `unknown`，按原 generation 身份查询远端状态；不得盲目重试、估算后冒充正式账单，或同时退费和补扣。

默认产品规则：

- 因 Graylum 或供应商故障未交付可用结果：用户全额退还，已发生供应商成本由 Graylum 承担；
- 用户在真实调用发出后主动取消：按官方已发生成本结算；
- Fusion 部分模型失败但交付可用综合结果：按官方实际总成本结算，并展示实际参与状态。

## 8. 历史数据与删除策略

取消按 Free、Pro、Gold 会员等级自动删除或隐藏用户项目、选题、聊天和成果历史。未来实现应删除会员历史保留天数设置、自动对话清理服务、清理 API、定时任务及其测试和诊断。

仍保留用户主动删除、账号注销、法律要求删除、OAuth 撤销、临时上传缓存和安全日志生命周期。完整历史长期保存不代表每次都发给模型；Session 与项目上下文仍受上下文预算、选择和整理规则限制。

## 9. UI、路由与设计规范

核心页面族：

- 首页：六步定位主入口、成熟账号导入、非社媒项目入口、最近项目和本周工作；
- 项目：账号项目与非社媒项目列表；
- 六步定位：独立导师式页面；
- 项目详情：账号经营资料、定位版本、本周选题和状态；
- 选题/工作项：Agent 工作空间、成果、资料、来源和版本；
- 技能广场：顶部导航一级页面；
- 个人中心：账户、积分、会员和基础设置。

连接器管理使用工作空间内弹窗或抽屉，不进入顶层导航。旧 `/chat`、旧功能广场和旧工作台在新路由完成迁移前保留兼容跳转；确认深链接、恢复和数据归属后再删除旧页面。

新页面必须使用现有 Graylum 设计 token 和深色金色视觉体系，覆盖桌面、平板和移动端；具备键盘操作、焦点状态、合理触控尺寸，以及加载、空数据、失败、断线恢复和权限不足状态。参考外部产品只借鉴信息架构与交互逻辑，不复制其品牌、视觉资产或受保护实现。

## 10. 实施顺序

本修订锁定以下顺序，但不自动选择或授权任何后续 Launch 实现任务：

1. 文档同步与冲突旧规格关闭；
2. 统一计费运行单、官方成本收据、精确金额与原子最终结算；
3. 统一 Agent Runtime、持久化 SDK Session、模型职责和受控工具边界；地基同时覆盖项目前定位草稿与项目工作项两种作用域；
4. 跑通“零项目新用户→定位草稿及恢复→六步定位与计划确认→账号项目和计划选题→单个选题→一个 Skill→保存与恢复”的第一条纵向链路，并验证多平台承接不复制费用或 Session；
5. 完成新导航、技能广场、项目路由和输入框内 Skill/连接器交互；
6. 完成飞书多维表格首个双向连接器闭环；
7. 完成 Gold 多模型智囊团和真实小额成本对账；
8. 确认全部新入口迁移后，删除旧模型路由、旧上下文、旧搜索判断、旧聊天执行入口、旧页面、会员历史自动清理和重复执行器。

不得先大面积删除旧代码再补新入口，也不得让新旧两套运行时长期并存。每一批均需精确候选验证、必要的非生产数据库/供应商验证、独立语义审查和 Owner 产品验收。

## 11. 当前边界

截至本文建立时，PR #414 已合并的 Agent SDK 切片、成果承接和计量身份是可复用基础，但不代表全站统一 Agent Runtime、持久 Session、Fusion、连接器、新 UI 或 provider-authoritative 聚合结算已经完成。

本文不启动第一项代码任务。完成文档候选的检查与独立审查后，由 Owner 决定是否合并；合并后再明确选择首个实现范围。
