# PAY-COMMON PR-4B1：人工审批与积分包退款

风险 high：现金退款、积分回收、权限与数据库事务。依据 PR-4、PR-4A、本次 Owner 的 4B 授权。
0184 已随 #710 合并；本片从 staging 54158452 同步，使用为 #711 预留的 0185。

## 串行范围

按已授权的执行类型拆分，本片完成积分包普通退款的管理员服务：
既有 admin 权限下查询、预览、批准、拒绝、执行和核对。绑定同主体 billing 工单，
记录理由类别、费用法律依据引用、资格与金额版本；不从工单正文推导财务授权。
工单操作 UI 仍按 PR-4 方案归 4C，本片不增加用户自助入口。

后续串行片必须完成订阅首购/创始、升级恢复原 Pro、功能缩减/无故终止的执行、
管理员代建例外工单、同违规身份换号限制证明及成本报表。
本片没有实现这些执行类型，不可标为完整 4B 或 PR-4 验收。
成本报表继续按 Owner 2026-10-07 已定口径：单列退款手续费收入，显示扣退款后的净收入，
名义积分收入不能作为现金；该决定已获授权，后续不用再询问。

## 实现与复用

- 订单内增加 refund_approval，存最少的审批/执行事实，无工单正文、附件或用户联系信息。
  原订单 metadata 会被既有履约写入；独立的受限列避免其覆盖审批身份。
  0161 已将 authenticated 整表 SELECT 收紧为旧字段白名单；本片审批列仅服务端可读，不扩大客户端字段权限。
  不新建表、账本、队列、调度器或通用退款平台；订单和原 credit_transactions 仍是权威。
- 0185 使用既有 profile → order 锁序；完整检查本账户历史消费和全部在途预留，
  包括付款前启动的预留。未知负向账本保守待核对，不按净消费放行。
- 普通积分包只接受有冻结购买快照、完整发放流水、原付款映射的已付订单。
  Stripe 已捕获的原交易/余额交易时间是付款证据；以关联工单提交时间判 168 小时。
- 预览版本绑定原现金、法律依据、金额、工单与主体。并发批准共用一个身份；
  执行原子重查，先落固定幂等键并完整收回本包及赠送积分，再请求原渠道净额退款。
  保留其他来源余额，不以 94% 现金比例回收积分，不伪造 fullRefund。
- 只接受原 Stripe 商户和 test 模式，不跟随当前销售渠道；不支持 Waffo 或 live。
- 超时/本地写失败保留原意图和回收记录。完整查找原退款后，20 小时内仅可重发相同键和参数；
  数据库再次核验管理员与执行身份。超过窗口、查找不完整或存在其他退款时只核对，不再发款。
  依据 [Stripe 幂等文档](https://docs.stripe.com/api/idempotent_requests)：键至少保留 24 小时。
- 成功/待处理/失败结果必须匹配同订单、意图、原付款、charge、币种、金额、商户及模式。
  成功只生效一次；确认失败恢复一次积分；未知不能释放。
- webhook 复用 stripeFulfillment 核对入口。携带审批身份的事件从 Stripe 重查后写原意图；
  无匹配身份的外部事件保留人工核对事实，不二次收回已保留的积分。
- 已修复 4A P2：保留已发积分的功能缩减时间退款不依赖完整消费证据；
  未用已购积分退款仍须核对消费与结算。本片只修资格，不执行该例外。

## Validation handoff

以下为主窗口后续 Stripe 测试模式步骤，本窗口实际渠道测试全部 NOT_RUN。
须先取得迁移应用批准，使用包含本片代码和 0185 的 staging 部署；只用独立测试主体及测试订单。
本片提供 admin 服务契约，工单 UI 未完成，不能把服务验证当作后台浏览器验收。

1. 在现有客服入口创建 billing 工单，管理员关联同一主体的已付积分包订单。
   通过 admin.previewPackageRefund 查看基数/费用/净额及 versionHash；
   feeEvidence 只放已确认法律依据的引用，不放工单原文或个人资料。
2. admin.decidePackageRefund 批准该版本。另一管理员同版本批准应返回相同意图；
   非管理员、跨主体工单、伪造金额或陈旧预览必须拒绝。
   不符合资格的工单通过 admin.rejectPackageRefund 留拒绝理由，无需调用 Stripe。
3. admin.executePackageRefund 使用返回的意图。确认原交易只退净额，
   整包及赠送积分一次回收、其他来源不变。法律不允许收费时费用为 0。
4. 批准后发生任何消费或出现未决预留、拒付或既有退款，再执行应拒绝且零新增退款。
5. 重复执行/两个管理员同时执行，只允许一笔退款和一次回收。
   重送 refund.updated、charge.refunded；核对先到和乱序通知，余额及现金不得重复。
6. 模拟请求超时或数据库结果写失败，用 admin.reconcilePackageRefund 查原交易；
   不创建新意图。20 小时外不得再次创建退款。确认失败仅恢复一次积分。
7. admin.getPackageRefundStatus 查看状态。unknown/review_required 不能报完成；
   外部不匹配退款须人工核对，不删除审批记录、不手工伪造 succeeded。
8. 留脱敏的测试订单/退款关联、现金基数/费用/净额、前后积分与重复请求结果。
   不公开邮箱、账号、密码、完整供应商对象或客户内容。

本机恢复：未存在审批记录时可验证结构回滚；已有审批/执行则 rollback 明确拒绝，
必须保留账务并向前修复。撤回代码不等于撤销已发送的退款。
