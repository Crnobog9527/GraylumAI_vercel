# AGENT-CORE R14：评审修订稿同步回字段（宿主接口）

风险：high（正式定位版本、确认字段、删除边界）。范围按 `AGENT_CORE_CLOSEOUT.md` R14 和 Master Plan 第 3.3 节；
总控-7 派发，迁移编号 0223 由总控分配。

## 要做到什么

Master Plan 第 3.3 节："评审修订稿被采用时，列出它和各步已确认字段的差异；用户确认后同步更新字段并生成新的确认版本；
不确认时修订稿只作为报告文本保存，页面标明'选题和写作仍使用原定位'。"

R14 只交付宿主接口，不依赖评审功能本身。FUSION-REVIEW 以后只调用这个接口。

## 怎样算做完

- 给定一份修订稿，接口列出它和当前正式版本已确认字段的差异（只列有变化的字段，带步骤名、字段名、原值、新值）。
- 用户确认后，一次事务完成：生成新的定位确认版本，字段改成修订稿的值，报告正文用修订稿全文；
  业务的当前定位指向新版本，所以下游选题和写作读到新字段。
- 用户不确认时，字段和正式版本都不变；修订稿全文作为这一版报告的附带文本保存，读取时带
  `fieldsSynced=false`，页面据此标明"选题和写作仍使用原定位"。
- 用固定修订稿样本在本地数据库测试里验收：差异、确认同步、不确认、重复提交、并发、越权、过期版本、删除和注销。
- 不调用模型，不收费。

## 不做什么

- 不做评审功能（FUSION-REVIEW），也不在这里从修订稿正文里"读出"字段值，原因见下一节。
- 不做前端界面。现在还没有评审功能，页面上没有地方会产生修订稿；差异对比和确认按钮等 FUSION-REVIEW 接入时
  由 Claude 前端另开 PR 做，浏览器验收随那个 PR。
- 不改账号策略（account strategy）草稿的修改流程，这类草稿调用本接口直接拒绝。
- 不改已有的确认、发布、删除函数的行为；只在发布里加一条只有本接口能走的修订稿分支。

## 关键设计

### 1. 修订稿必须带上字段值

修订稿正文是自由文本，13 个部分和各步字段不是一一对应。从正文里读出字段值需要再调一次模型，会产生新费用和新的
失败情况。所以接口要求修订稿的提供方把**建议的字段值**和正文一起交进来：

```
revision = {
  body,                                   // 修订稿全文，按这一轮冻结的报告模板校验（段落、上限）
  fields: { [stepId]: { [fieldId]: value } } // 只需给出修订稿想改的字段，值 ≤ 400 字
}
```

评审的汇总模型写修订稿时顺带输出这些字段值（FUSION-REVIEW 的要求，写进它的方案）。字段 id 必须是这一轮冻结的
Skill 流程里声明过的，否则拒绝。

### 2. 三个动作（一个 RPC：`report_revision`，仅服务角色可调用，身份来自已验证登录）

| 动作 | 输入 | 结果 |
| --- | --- | --- |
| `propose` | `draftId, requestId, sourceVersionId, revision` | 登记修订稿（不可变记录），返回差异和 `diffHash` |
| `apply` | `draftId, requestId(=propose 的), expectedDiffHash` | 生成新确认版本，返回新版本和 `next`（第一周选题） |
| `decline` | `draftId, requestId(=propose 的)` | 字段不变，修订稿只作报告文本，返回 `fieldsSynced=false` |
| `read` | `draftId, requestId` | 当前状态（待决定 / 已同步 / 只作文本）和差异 |

- `sourceVersionId` 必须是项目当前的正式版本，而且是 R5 定稿出来的（有 `generatedReport`）。不是当前版本就拒绝，
  要求重新生成差异。
- 同一 `requestId` 重复提交返回同一结果；同编号换参数拒绝。`apply` 和 `decline` 只能二选一，做过一个就不能再做另一个。
- 差异只列有变化的字段。状态不是"已确认"（例如暂缓确认）的原字段，被修订稿改了值也列出来，同步后改为已确认。

### 3. 确认同步怎么做

在项目锁内，一次事务：

1. 重新核对：草稿属于本人、当前正式版本没变、差异和 `expectedDiffHash` 一致、来源没被删除。
2. 复用现有 `opc_revise` 从当前正式版本开一个新的草稿轮次（和用户手动"回头修改"是同一条路）。
3. 写入变化的字段：值用修订稿的，状态"已确认"，`fieldMeta.source='revision'`；按现有规则重建该步正文
   （和 0135 同一个拼法）。
4. 按依赖顺序把所有步骤重新确认。用户确认的是整份修订稿，所以被连带标成"需要复核"的后续步骤也在这一次确认里一起
   确认，不再要求逐步复核。（这是对 3.2 节"回头修改后逐步复核"的例外，只适用于整份修订稿被确认的情况；
   如果总控或 Owner 认为后续步骤仍应逐步复核，改成只同步、不发布，留在草稿里让导师带着复核。）
5. 发布：走现有发布，报告正文用修订稿全文。R5 的发布要求一个属于这一轮的报告生成执行；这里新增一条分支：
   只有本函数在同一事务里设置的标记存在时，才接受"修订稿"作为报告来源，其他调用方传同样的参数也会被拒绝。
   `generatedReport` 记 `source='review_revision'`、修订稿编号、正文和校验值、`fieldsSynced=true`。
6. 业务当前定位随现有发布逻辑指向新版本。已经开始的第一周选题工作区沿用现有规则（来源变了要重新开始）。

### 4. 不确认

只把修订稿记录标为"只作文本"。正式版本、字段、业务当前定位都不动。R5 的报告读取在这一版上附带最新的
"只作文本"修订稿（正文、时间、`fieldsSynced=false`），页面据此显示提示。

### 5. 删除和注销

修订稿存在现有 `artifact_requests` 里，载荷带项目、轮次和来源版本的编号，现有删除（单条删除来源版本、删除成果）和
注销会把它擦掉，不新建表、不改删除函数。删除测试覆盖。
