## 1. 对标流程（D15 + R11）

**门槛口径**（来自已发布 Skill 和 Master Plan 第 3.7 节的已定规则）：粉丝 1 万–20 万、30 天内更新、候选 8–12 个、每个账号 20–30 条作品、至少 3 个合格，这些是**产品规则，写成服务端常量，不进后台配置**，要改须 Owner 新决定；只有"近期起号快"的 N、K 这类实现参数可在后台调。
一个对标账号算**合格**，必须同时满足：平台在"已验证可用"清单里；账号资料和最近作品都是真实取到的；
粉丝数 1 万–20 万；最近 30 天内有更新（用取到的绝对发布时间判断，拿不到发布时间的平台不进清单）。
**凑够 3 个合格账号才能生成报告，不提供"跳过"。**

### 1.1 用户已有对标

1. 用户在对话里给账号主页链接或平台 + 账号名。
2. 模型调用一次 `benchmark_fetch`，来源写成用户的这条消息（第 2.1 节，宿主核对每个账号原文确实出现在用户消息里），代码逐个取数。宿主按规则表选 TikHub 线路，取账号资料 + 最近 20–30 条作品。
3. 代码算指标、判合格、写进对标表（第 1.4 节）。不合格时在对话里说明哪一条不满足（例如"粉丝 35 万，超过 20 万上限，只作参考"）。

### 1.2 用户没有对标

1. 模型根据前面收集的定位信息生成 3–5 个关键词，调用 `propose_keywords` 发出**选择卡**（第 1.6 节），
   用户可以勾选、改字、补充，提交后宿主保存一条"已确认关键词"记录，内容是用户最终提交的关键词原文。
2. **宿主强制"先确认再搜"**：`benchmark_discover` 必须带这条记录的 `keywordConfirmationId`，
   宿主核对它属于本会话、本用户，且这次要搜的关键词与记录里的完全一致（精确比对，不用正则猜意图）。
   核对不过直接返回 `not_confirmed`，不发出请求、不收费。
3. `benchmark_discover` 是一次模型调用、由**代码**执行整段发现流程（避免模型逐个调用撞上每轮上限）：
   - 每个关键词在每个选定平台取近期作品 20–30 条；
   - 按作者聚合、去重，取出现次数和互动靠前的作者，补取账号资料；
   - 整段有独立的子调用上限（初值 25 = 5 个关键词 × 2 个平台 + 15 个作者资料；上限受第 2.1 节"运行单总数 ≤ 32"约束），
     每个子调用仍在同一运行单上**逐次冻结、逐次结算**；余额不够或到上限时停在当前位置，返回 `partial` 和已取到的部分。
   - **每个子调用发出前先落盘**：稳定编号（发现流程编号 + 序号 + 请求内容哈希），沿用 0065 已有的状态名
     `prepared → dispatched → succeeded / failed / unknown`，发出前写成 `dispatched` 才发请求（复用 `research_operations` 和 `research_transition`，不改状态集合）。
     进程中途崩溃后按游标续跑：`succeeded` 直接复用证据不重发；`prepared` 可以发；`dispatched` 但没有结果的记为 `unknown`，
     **不重发**，按第 3.4 节等对账。`benchmark_fetch` 用同样的做法。补测试：在第 k 个子调用发出后模拟崩溃，续跑不重复收费、不丢已取到的证据。
   - **每个子调用一个研究计划、一个操作**（RT-3b #997/#1005 交接细化）：`research_plans.max_operations` 限 1–20（0065），
     每次通过 `research_runtime_plan_create` 创建即绑定回答，共用发现流程编号，子调用使用稳定编号；不改 0065 的上限。
     已发送的操作恢复时不重发。跨回答恢复未发送计划时，先取消并确认尚未发送，再争用同一个稳定后继编号，不重绑旧回答的账务。
     补测试：完整 25 次子调用、跨轮续跑和取消时的派发竞争。
   - **遇到结果未知不卡住整单**：`bill2_payg_claim` 不允许运行单上有未结算调用时再发新调用（0162 约 283 行），
     现有 `research_transition` 遇到未知会取消该计划。这两条规则都不改，做法是：
     - 未知的子调用**对用户当场结算为 0**（`settled_at` 照常写入，按第 3.3 节"用户结算"和"供应商成本待确认"分开记），
       供应商成本另记"待确认"和上限，等第 3.4 节对账。这样运行单不会被这笔卡住，后面的子调用和解读用的模型调用都能照常进行，
       会话也不会停在"执行中"。
     - 未知那一项不重发、不计入候选；它所在的计划按现有规则取消，剩下的子调用在同一运行单上换一个新计划继续（同一发现流程编号，已完成的证据复用）。
     - 依据第 9 节决定 2（Owner 2026-10-13 选 A：未知不向用户收费）。
     - 补测试：第 k 个子调用未知后，本批其余子调用和最后的模型解读照常完成、用户看到 `partial` 说明、会话被释放；未知项不重发；
       供应商成本报表里这笔是"待确认"。
4. **代码**分三类：
   - 头部参考：粉丝超过 20 万。展示，但不计入"合格"。
   - 同量级可模仿：粉丝 1 万–20 万，30 天内有更新。
   - 近期起号快：在"同量级可模仿"的门槛内，再满足"最早一条可取作品在 N 天内、或近期作品播放中位数 ≥ 粉丝数 × K"（N、K 后台配置，初值由 RT-4 用实测数据定，写进 PR）。
   - **30 天活跃度只在 `benchmark_fetch` 取到最近作品后判定**；发现阶段的关键词命中只用于找到账号，标记“活跃度待取数确认”，不能因命中作品较旧而排除。Owner 2026-10-18 明确要求此阶段划分，以避免 `postsAnalyzed=1` 的搜索命中误杀仍活跃账号。取数后按最近 30 天内有更新判定资格；粉丝不到 1 万的账号仍剔除。
   - 取数（`benchmark_fetch`）后至少分析到 20 条作品才算合格；只有供应商确认这个账号总共就这么多作品（新号，不到 20 条）时例外，按实际条数照常判定。
     Owner 2026-10-16 原话："同意 RT-4b 作品条数选 A"（RT-4b，[#1015](https://github.com/Crnobog9527/GraylumAI_vercel/pull/1015)）。
     发现阶段的候选筛选只有搜索结果里的几条作品，不受这一条限制。
5. 宿主把 8–12 个候选用**选择卡**（多选）展示，请用户挑 3–5 个；提交后同样保存为宿主记录。
   **可选的候选（不含头部参考）不到 8 个时不发卡**（Master Plan 第 3.7 节要求展示 8–12 个）：返回 `partial`，说明找到了几个、差几个，
   由模型请用户换关键词重新发现或贴链接（不跳过）。
   **候选资格没查完就续跑，不急着发卡**：有的平台每个作者要多查一次（例如 B 站粉丝数要另调关系接口，每个作者 2 次），
   一批上限内可能凑不满 8 个。这时 `benchmark_discover` 返回 `partial` + `continue:true` + 同一个 `discoveryId`，
   模型下一回合用 `discoveryId` 再调一次，按游标继续查剩下的作者（已完成的复用，用新运行单和新计划）；
   可选候选达到 8 个才发卡（最多展示 12 个）；作者都查完仍不到 8 个时不发卡，按上一条返回 `partial`。
   补测试：两个平台都是 B 站时，续跑一次后凑满 8 个候选，全程不重复收费。
   头部参考只作展示，不能被选为对标（卡片里标"只作参考、不计入"，不可勾选）。
   **补选**：如果选中的账号取数失败或最终不合格、合格数不到 3，模型可以调用 `propose_more_candidates`（不调用供应商、不收费），
   宿主从这次发现流程**已保存的候选证据**里去掉已选过的，生成一张新的补选卡；每张补选卡同样只能确认一次。
   `benchmark_fetch` 接受同一次发现流程下任何一张已确认卡里的账号。候选用完时再请用户贴链接或换关键词重新发现。
6. 模型调用一次 `benchmark_fetch`（带候选确认编号，第 2.1 节），由代码逐个取选中账号的资料和最近 20–30 条作品；不在确认记录里的账号一律被拒；
   **同一会话里每个"平台 + 规范化账号"只付费取一次**，不管来源是候选确认还是用户消息：取数成功后记下，
   之后再查这个账号（换来源、换工具调用编号、换回合都一样）直接复用证据、不发请求、不收费；
   要重新取（刷新）必须由用户在界面上点"刷新"产生新的授权，才算一次新的收费：
   点击走一个需要登录的服务端接口，生成一条**刷新授权记录**（用户、会话、平台、规范化账号、生成时间、是否已用），
   `benchmark_fetch` 以 `{kind:"refresh", refreshId}` 引用，宿主核对本人、本会话、账号一致且未用过，取数成功后标为已用（只能用一次）。
   RT-3 做记录表、接口和校验（并接入内容删除和注销），RT-5 做按钮；测试：已用的刷新授权再用被拒、别人的被拒、账号不一致被拒。
   补测试：候选确认和用户消息两种来源各自重复提交、以及两种来源交叉查同一账号，都不会再收费。
   代码算指标、写对标表。

### 1.3 取不到时（R11：不跳过）

- 工具返回结构化的"取不到"（第 2.3 节），模型必须如实说"这个账号 / 这个平台暂时取不到数据"，
  并请用户**粘贴另一个账号链接**。不给示例账号，不凭记忆写账号名或数字。
- 合格数不到 3 时，宿主拒绝生成报告（第 1.5 节），对话里告诉用户还差几个、可以怎么找（换关键词、贴链接）。
- 清单外的平台（目前 Instagram、YouTube 因为拿不到可靠发布时间不在清单里；Facebook 等 Bright Data 接入前也不在）
  直接告诉用户"暂不支持这个平台的对标"，请用户换一个已支持平台的账号。

### 1.4 对标表：数字只能来自取数结果

- 新增宿主自有的对标表（RT-4 迁移；理由：原始证据已在 `research_operations`，但"数字栏目只能由代码写、模型不能写"需要逐列的写入约束和逐行删除，放在 jsonb 结果里做不到），一行一个账号：平台、账号标识、粉丝数、近 N 条作品的播放中位数、
  互动率、更新频率、最近一次更新时间、分类、是否合格，以及每个数字对应的**证据编号**（第 4 节）。
- 这些数字栏目只由代码根据证据计算写入；模型没有写这些栏目的工具或接口。模型只能写"解读"文字栏。
- 字段缺失写"未提供"，不当 0 参与计算（例如小红书没有浏览量，就不算播放中位数，只算能算的）。
- 报告里的对标数字从这张表读取，不从模型输出读取。网上找到的案例（`web_search`）在报告里注明
  "来自网络，真实性待考证，仅供参考"，不计入合格对标。

### 1.5 报告门槛放在哪

工程规范第 6 节要求宿主不写死某个 Skill 的步骤。所以门槛做成**通用能力**：
Skill 在 `workflow.yaml` 里声明"生成报告前要求对标表至少 N 个合格账号"（定位 Skill 写 3；宿主对"对标"这类声明强制不低于产品规则的 3 个，Skill 写得更低也按 3 执行），
宿主在报告生成入口（REPORT-GEN / POSITIONING-GATE 的同一检查点）按声明执行。
**定位报告不依赖声明**：只要是定位范围（positioning scope）的报告，宿主一律强制"对标表至少 3 个合格账号"，Skill 漏写或写低都按 3 执行；只统计**本次定位会话 / 草稿**下、由本会话的执行产生的合格行（按规范化账号去重），
其他会话或以前流程的行不算；
其他 Skill 没声明的不受影响。补测试：去掉声明的定位 Skill 版本，合格数不到 3 时报告照样被拒；另一个已完成会话里有 3 个合格行时，新会话的报告仍被拒。

### 1.6 选择卡（新的宿主契约）

现有提问卡（`questionCardSchema`）只允许 2–5 个选项、只记录一个 `optionIndex`，
表达不了"多选 + 改字 + 补充"，也装不下 8–12 个候选。所以新增一种**选择卡**，不改提问卡：

- 卡片内容由宿主生成并保存：卡片编号、会话、类型（`keywords` / `candidates`）、选项列表（关键词最多 5 个，候选最多 12 个，
  候选选项带账号标识和证据编号）、最少 / 最多可选数、是否允许补充。
- 用户提交，两种卡规则不同：
  - **关键词卡**：选中的选项编号 + 改过的文字 + 补充的条目（每条长度有上限）；
  - **候选卡（含补选卡）**：**只能勾选**，不允许改字、不允许补充。每个选项有不可变的选项编号，绑定宿主生成时的
    `（平台, 规范化账号, 证据编号）`；提交只收选项编号，宿主按编号取回这组信息，带改字或补充条目的提交整体被拒。
    想加卡片外的账号只能走"贴主页链接"的路径（第 1.1 节）。
  宿主校验数量和长度，保存为一条**确认记录**（确认编号、卡片编号、最终条目、提交时间）。同一卡片只能确认一次，重复提交返回原记录（幂等）。
  补测试：候选卡带改字或补充被拒；`benchmark_fetch` 只认确认记录里由选项编号取回的账号。
- 工具只认确认记录，不认模型自己转述的内容。
- RT-3 做契约、存储和校验；RT-5 做界面；测试覆盖：关键词卡的多选、改字、补充，超数量被拒、重复提交、
  用确认记录以外的关键词调用被拒、别人的或别的会话的确认编号被拒；补选卡不含已选账号和头部参考、生成补选卡不发起供应商请求、补选后的账号能被取数。
- **存储用一张专门的表**（RT-3 迁移）。理由：`propose_keywords` 这次工具调用在卡片展示之前就已经完成，
  而 `runtime_tool`（0205）不允许写入第二个不同的结果，运行单关闭后也不允许再完成，用户之后的确认放不进去；
  把它改成可变会破坏工具记录的冻结和重放。表的约束：
  - 每行一张卡：用户、会话、卡片编号（唯一）、类型、宿主生成的选项、数量和长度限制、创建时的运行单；
  - 确认字段（最终条目原文、确认编号、确认时间）只能从空写一次，用户只能确认自己会话里的卡，
    重复提交相同内容返回原记录，不同内容被拒；
  - 接入内容删除（删会话、删回答）和账号注销，补对应测试。

    规范化成 `（平台, 账号标识）`，要求这次的 `platform` 和完整账号标识都与解析结果完全一致。只认链接，不认消息里的子串；

    测试：子串（如单个字母）、平台不一致（X 链接里的账号拿去查 TikTok）、链接格式不在已验证平台里，都被拒且不发请求；
  - 核对不过返回 `not_confirmed`，**不发出请求、不收费、不进对标表**。只有带合格来源取到的数据才能写进对标表。
  - 测试：未选中的候选、模型自己编的账号、别的会话 / 别的用户的确认编号或消息编号都被拒，且没有发出请求。
- **每轮工具调用次数**：定位导师回合目前把 `maxToolCalls` 冻结为 1（`admission.ts:338-339`），`MAX_AGENT_TOOLS` 只限制请求里出现几个工具。

  但工具返回后模型还要再跑一轮来解读，RT-3 要把对应回合的 `maxToolCalls` / `maxTurns` 和冻结的模型调用次数一起调整，
  并测试：一次取 3–5 个账号、取完后模型继续回答、两轮模型调用都正确冻结结算。
- **运行单的调用总数和费用上限要包含供应商子调用**：`bill2_payg_claim` 到了运行单的 `max_calls` 就拒绝（0162 约 286 行），
  定位入口现在只给 1–2 次（`opc/service.ts:225`）。RT-2 / RT-3 要让冻结的运行单上限 = 模型调用次数 + 本回合工具允许的全部子调用
  （`benchmark_discover` 最多 25 次；`benchmark_fetch` 每个账号最多 3 次（资料、作品、B 站另加关系接口）× 5 个 = 15 次），
  调用策略和费用上限同样按这个总数冻结。
  - 现有数据库校验不允许运行单超过 32 次调用（0162 约 527 行）。定位页面总是带 `organizeAfter:true`，

    发现流程 25 + 3 = 28，不改 32 这个上限。后台配置的子调用上限超过这个差值时整份配置被拒。
  - 测试：开着整理的完整发现回合（3 次模型调用 + 25 次子调用）能走完并结算；第 26 次子调用被拒并返回 `partial`，
    之后的解读和整理调用仍然能执行。
- 工具描述写清：查询词只写关键词、公开链接或公开账号名，不要写用户的个人信息或对话原文（第 4 节）。

### 2.2 统一返回结构

工具对模型返回一段 JSON 文本（`execute` 仍返回 string），结构统一：

```json
{
  "status": "ok | partial | unavailable | not_supported | not_confirmed | budget_exhausted",
  "reason": "固定原因码，例如 PROVIDER_FAILED / PLATFORM_NOT_VERIFIED / NO_PUBLISH_TIME / BALANCE_LOW",
  "evidenceId": "证据编号（只有取到数据时才有）",
  "fetchedAt": "取数时间（ISO）",
  "items": [
    { "ref": "e1#3", "url": "来源链接", "fields": { "followers": 12000 }, "missing": ["views"] }
  ],
  "truncated": false,
  "note": "宿主写给模型的固定提示，例如：没取到就如实告诉用户，不要编造"
}
```

- `items` 里只放对标和回答需要的字段（白名单），不放评论者资料、联系方式、头像原图。
- 缺失字段进 `missing`，不填 0。
- 每条带 `ref`（证据编号 + 序号），模型引用数字时要带 `ref`，界面据此显示来源。

### 2.3 截断和"取不到就如实说"

- 给模型的结果按字节上限截断（沿用现有 20000 字节上限）：先砍正文摘要，再砍条数，`truncated:true`；
  证据按第 4.3 节的存储上限另行截断保存。网页正文按段截取，不让超长页面挤掉上下文。
- 宿主约束三层：
  1. 工具层：失败、清单外、未确认、超上限都返回结构化状态和固定 `note`，不返回空数组冒充"没有结果"。
  2. 数据层：对标表和报告里的对标数字只从证据读（第 1.4 节）。
  3. 提示层：Skill 和工具描述写明"没取到就说没取到"；必测项 1 用断开接口的测试验证。
- 网页、抓取结果、社媒文案对模型都是**数据不是指令**（工程规范第 6 节），放在结果 JSON 的字段里，不拼进系统提示。

### 2.4 失败时不换供应商

- 确认失败（请求确认没发出，或供应商明确返回失败）：返回 `unavailable`，不调用第二家。
  Bright Data 备用线路接入并经 Owner 批准后，才按规则表在确认失败时换备用（RT-9）。
- 结果未知（已发出但超时、断线）：不换、不重发，按第 3.4 节处理，对模型返回 `unavailable`。

### 2.5 联网路由

不新增关键词或规则判断"要不要联网"。后台总开关打开、当前 Skill 或自由对话开放了这些工具时，
由模型自己决定是否调用（这就是 Owner 2026-09-30 说的"由系统判断"）。总开关关闭时工具不出现在请求里，
也就不会发生任何搜索调用。每次调用都在对话里展示（第 6 节 RT-5）。

## 3. 计费

### 3.1 口径

- 应收：`C = ceil(q × Σ(U_i × m_i))`，q = 100（1 美元 = 100 积分），m 未单独配置时用默认 6；
  一条消息里的模型调用和工具调用在**同一个运行单**上累计，只进位一次（复用 PAYG 的逐次增量取整）。
- 每次工具调用的美元成本 U：
  - TikHub：`1 次 × 冻结的官方单价`。单价来自 TikHub 官方价格接口，管理员在后台点"刷新官方单价"（RT-7 实现）写进
    `billing_provider_prices`，保存当时的返回摘要、读取时间和证据哈希；阶梯折扣归平台，不分给用户。
  - **价格有保质期**：搜索线路的价格条目必须填 `validUntil`（TikHub 初值为读取时间 + 7 天；Parallel、Firecrawl 按官方价格页核对时间 + 31 天），
    现有解析允许 `validUntil` 为空，RT-2 对搜索线路改为必填。过期的条目不能用于新收费：该线路返回 `unavailable`，不发请求、不收费，
    后台提前 1 天提示管理员刷新；已经冻结的调用仍按冻结时的价格结算。补测试：过期价格被拒、刷新后恢复。
  - Parallel：`响应里的 usage（如 sku_search=1）× 后台配置的单价`。
  - Firecrawl：`响应里的点数 × 后台配置的每点单价`。官方文档目前的抓取响应结构里没写 `creditsUsed`，
    RESEARCH-0 实测见过；RT-1 用录制的真实响应确认字段位置，确认不了就不能开放这条线路。
- 价格配置在发起收费时冻结（记配置版本），后台改价只影响之后的新调用。
- 精确十进制计算；用量只取适配器校验过的官方字段；负数、非有限值、格式错误一律拒绝。

### 3.2 冻结和结算（接入 BILL-PAYG）

1. 调用前：按"这条线路一次调用的用量上限 × 冻结单价 × m"算出冻结额（用量上限见第 3.5 节），走 `bill2_payg_claim`，
   冻结 `H = min(冻结额, 可用余额)`。余额低于启动门槛 L 时，对话里明确提示充值（沿用 PAYG 的等待充值），不静默失败。
2. 调用后：按实际用量结算，走 `bill2_payg_finalize` 的增量取整；超出冻结额的部分平台承担（第 26 项）。
3. 消费记录：这类调用的扣费说明改成"联网搜索 / 社媒数据查询"，不再沿用写死的"AI call consumption"。

**需要的数据库改动（RT-2 迁移）**：`bill2_payg_nominal` 和报价校验目前只认 token。
新增一种"工具调用"名义成本分支（按次、按用量 × 单价两种），报价必须引用 `billing_provider_prices` 的条目；
`bill2_calls` 增加调用类别（模型 / 工具）；启动门槛 L 增加按"线路 + 用途"的配置项。
不新建账本、不新建队列。

### 3.3 几种结果怎么算

| 情况 | 用户扣费 | 平台记账 |
| --- | --- | --- |
| 成功，有用量 | 按实际用量 | 实际成本 |
| 成功，但这次缺少用量字段 | 0（没有官方用量依据，不按估算向用户收费）；**这次调用对用户照常结算为 0**，运行单不被卡住，后面的子调用和模型调用照常进行 | 供应商成本单独记"待确认"（null / `cost_pending`，与用户结算分开），单次上限只作为另记的"可能负担"，对账拿到官方用量后再补实际成本；记异常并报警；同一线路反复出现时停掉该线路并报告（AGENTS 第 5 节） |
| 确认没发出 | 0，释放冻结 | 0 |
| 供应商明确返回失败，且不收费（如非 200） | 0 | 0 |
| 返回 200 但内容是上游报错（TikHub 小红书文档写明会收费） | 0（用户没拿到数据） | 平台承担这次成本，按冻结单价记 |
| 结果未知（超时、断线） | 见第 3.4 节 | 不当 0 |

### 3.4 结果未知

- 不重发、不换供应商，记录未知证据（复用 `unknownEvidence` 和恢复流程）。
- 用户那边的冻结：按决定 2（已选 A），这次调用对用户当场结算为 0，**同时释放这次的冻结**，用户的积分不再被锁；
  供应商成本单独记"待确认"和上限（第 3.3 节），不占用户余额。
- 这三家都没有"按请求编号查这次收没收费"的接口，恢复只能靠对账：TikHub 每日用量接口、
  Parallel / Firecrawl 后台用量，按线路和时间窗口比对。
- **未知的成本不能当 0，也不能把上限当成实际成本**：按 V3-BILL-2 契约，成本保持"待确认"（null / `cost_pending`），冻结时的单次上限另记为"可能负担"，两者分开；对账拿到官方用量后补记实际成本，供应商成本报表只统计已确认的部分，另列"待确认"笔数和上限合计。
- **向用户收不收**：Owner 2026-10-13 决定（第 9 节 9.2 选 A）用户没拿到数据就不向用户收费，
  这笔由平台承担，成本按上一条记"待确认"（与"确认失败由平台承担"一致，也避免"付了钱没拿到东西"）。
  单次成本在 0.001–0.01 美元量级，同一问题反复出现时按 AGENTS 第 5 节停掉线路报告，不适用 5 美元损失线。

### 3.5 每条线路的单次用量上限

- `research_tools_config` 的规则表每条线路必须配 `maxUnitsPerCall`（没配的线路不能启用），和报价一起冻结。
- 适配器按上限**约束请求本身**，让实际用量不会超过它：
  - TikHub：按次计价，上限 1；
  - Parallel：固定 `max_results` 和模式，上限按官方 SKU 计算（快速 / 高级各 1 次）；
  - Firecrawl：只取 markdown 正文，不开结构化 JSON（贵 5 倍），不解析 PDF（PDF 每页另加点数），
    单页、不跟随站内链接；上限按这组参数定（初值 1，RT-7 实测确认）；遇到 PDF 链接直接返回 `not_supported`，不发请求。
- 响应用量超过上限：这次按实际用量记成本，超出冻结额的部分平台承担（第 26 项），记异常日志并报警；**该线路立即自动停用**（不再接新调用，fail closed），直到管理员重新核对上限或适配器后在后台重新打开；补测试；
  缺用量字段：不向用户收费，平台承担，成本记"待确认"（第 3.3 节）。

### 3.6 要同步改的契约

V3-BILL-2 第 3.1 节写着"不能用使用次数或标价代替官方成本"。RT-2 同步写入两个已定例外：
按"官方用量 × 冻结单价"、按次线路按"1 次 × 冻结官方单价"。实施说明里旧的"保底积分"写法已由
第 32–34 项取代，本 PR 已一并改掉（见实施说明的计费段）。
"结果未知时对用户按 0 结算并释放冻结"的搜索例外（第 9.2 节 A）已写入 V3-BILL-2 第 0.3 节和第 6 节终结表；RT-2 按它实现并补集成测试
（超时后用户积分不再被锁、同一运行单的后续调用能继续、供应商成本是 `cost_pending`、模型调用仍按原契约保留预留；注销路径 `bill2_erasure_closed` 和自动核对停止后的恢复路径同样按这个例外释放，DATA-ERASURE 第 3.2 节已同步，补注销时有未知搜索调用的测试）。

### 4.2 搜索词里有没有用户内容

- 会有：关键词由模型根据用户的定位信息生成，会带出用户的行业、主题；`web_fetch` 的链接可能是用户贴的。
- 控制办法：参数长度限制（关键词 ≤ 40 字、查询 ≤ 200 字）；工具描述要求只写关键词、公开链接、公开账号名；
  关键词路径要用户先确认（第 1.2 节），用户能看到要发出去的是什么；不把对话原文、文件内容发给供应商。
- 不用正则过滤个人信息（不可靠，也违反工程规范第 6 节）；PII-REGEX 任务的通用检查上线后再接入。

### 4.3 证据存储和注销

### RT-3b PR-2 边界（2026-10-16，迁移 0267）

- 消息入口 `opc.mentorTurnStream` / `prepareStep` 接受可选 `researchRefreshId`：宿主按登录用户、草稿会话读 0263 刷新授权
  （别人的、别的会话的、来源回答已删除的、已用过的一律拒绝，错误码 `OPC_RESEARCH_REFRESH_INVALID`；研究工具总开关关闭时
  `OPC_RESEARCH_REFRESH_UNAVAILABLE`），通过后作为 `hostTurnContext.researchRefresh` 冻结进该轮上下文交给模型；
  不进 `runtime_admission_replay` 的请求身份。`benchmark_fetch` 以 `{kind:"refresh",refreshId}` 再次核验并一次性消耗。
- PAYG 每次调用最多 9 个工具定义（SQL 报价校验、`PAYG_MAX_TOOLS`、host profile 2–9、`MAX_AGENT_TOOLS`）；
  已冻结的 run 仍按自己的 maxTools。9 个工具定义合计约 7.4 KB，`maxSchemaBytes` 16384 不变。
- `research_call` 结束事件带 `credits`（本次子调用的用户积分，取整前十进制；读不到为 null）；
  `research.toolCharges` / `research.evidence` 每行返回子调用自己的 `query` / `platform` / `dataKind`，0267 之前的行为 null。
- 证据派发顺序改为：建计划并预留 → 关联 BILL2 调用 → BILL2 派发 → 研究侧派发 → 供应商。未发送时取消该操作；
  "已派发、无结果、无 BILL2 关联"的操作由 `research_runtime_close_unsent` 收口为已取消，发现流程换稳定后继编号（#1005 P2）。
- **仍未接入真实定位回合**：冻结供应商价格进 run（`frozenCallPolicy` 增加 `research-tool-v1`）、准入里按开关给定位导师回合
  加研究工具和子调用次数、`execute.ts` 组装工具、`AGENT_TOOL_NAMES` / `providerRequest` 白名单、流事件队列。另开 PR 做，
  前端挂载在它之后。
