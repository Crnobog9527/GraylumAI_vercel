- 上线后，扫描件 PDF 的页和 Word 里的图片**全部改用 AI 识别**。后台加一个「识别方式」开关（浏览器 / AI；两个 PR 和模型都就位后由管理员切到 AI，之后一直用 AI），

## 1. 识别方式开关

- 后台「资料库」设置加一项「识别方式」：`browser` / `ai`，存 `system_settings.library_recognition_mode`，**没有这一行时按 `browser`**。后端先上、前端后上的过渡期里，旧页面只会提交浏览器识别结果，按 `browser` 才不会把识别卡住；
  等第 2.1 节的模型选好、前端也上线后，管理员再把它设为 `ai`（发布清单里的一步，第 5 节），之后上线环境就一直是 AI。
  不需要迁移。原有总开关 `library_scan_recognition_enabled` 不变：关掉时两种方式都不识别。
- 同一个开关管**扫描件 PDF 的页和 Word 里的图片**（Owner 2026-10-18 原话「Word 里的图片也改用 AI 识别，按实际花费扣积分」，
  取代 Master Plan 第 2.1 节 2026-10-10 条目「Word 图片是否也用 AI 扣费需 Owner 另行决定」）。Word 里的普通插图、截图也会被识别并扣费。
- 后台把方式设为 `ai` 时，必须已经选好「资料库文字识别模型」（第 2.1 节），否则保存设置被拒；不会出现「开了 AI 但没有模型」的状态。
- 切换后剩下的页按新方式继续，已经完成的页不重做；切换那一刻正在处理的那一页怎么办见下一条。
- **每一页都按当时的方式走，由服务器把关**：待识别列表带上当前方式，浏览器每处理完一页都重新读一次；服务器在保存浏览器识别结果时，
  如果当前方式是 `ai` 就拒绝保存（单元保持原状，之后走 AI），领取 AI 识别时如果当前方式是 `browser` 就拒绝。所以：
  - 从 `ai` 切到 `browser`：已经发出的 AI 调用照常完成和结算；
  - 从 `browser` 切到 `ai`：正在浏览器里识别的那一页，结果会被拒绝保存，这一页改由 AI 重做（浏览器识别不花钱，丢掉没有损失；这一页和其他页一样按 AI 扣费。切换只在上线时做一次）。
  PaddleOCR 代码和测速页保留，切回 `browser` 不用重新部署。

### 2.2 每页成本和积分（现有公式）

现有公式：**积分 = ceil(成本美元 × credits_per_usd × 倍率)**；staging 现在 `billing_credits_per_usd = 100`、`billing_token_price_multiplier = 6`，即每 1 美元成本扣 600 积分，每次调用单独进位。

以 Claude Haiku 5.5 / GPT-6 Luna 的标价、一页 1,600×1,131 像素为例：

| | 输入 / 输出 token | 成本 | 积分 |
| --- | --- | --- | --- |
| 实际（估算）：图片约 2,400 + 提示约 600；输出约 1,500（一页中文约 1,500 字） | 3,000 / 1,500 | 约 0.00105 美元 | ceil(0.63) = **1** |
| 冻结上限：图片 token 上限 20,678（0286 公式）+ 文字和模板约 3,000；输出上限 4,096 | 23,678 / 4,096 | 约 0.0044 美元 | ceil(2.65) = **3** |

Qwen3-VL 约为「实际 1 积分、冻结 4 积分」。实际 token 以实测为准，结算按 OpenRouter 返回的官方用量。

### 2.3 冻结和结算（复用 #1042 / 0286，不另建计费）

- **每页一个 BILL2 运行单、一次调用**，计费范围 `{kind:'library_document', documentId}`，用途 `library_ocr`；运行单 ID 写进识别单元的 `bill2_request_id`，用来防重复和对账。
- 调用报价用现有 `runtimePaygCall(request, 'library_ocr', policy, rules, epoch)`：一个 user 消息，内容为「识别提示文字 + 一张内嵌 JPEG」；
  0286 算出 T（输入上限）和 U（金额上限），冻结 `ceil(U × 100 × 6)` 积分，余额不够就不发起。
- 输出上限 4,096 tokens；发给 OpenRouter 的 `provider.max_price` 照 0286 带上。结算按官方用量，多退少补，不超过冻结上限；
  实际超过 T 时照旧标 `budget_conflict` 并停这条线路。
- 新增的只有：`runtime/paygHostPolicy.ts` 里 `library_ocr` 的路线报价和请求格式、后台模型设置项。

## 4. 流程和各种异常

### 4.1 一页怎么走

不新建队列、调度器或后台服务：和现在一样，**只在用户开着资料库页面时由浏览器一页一页推进**（LIB_DOCS_PLAN 第 4.4 节原设计）。
服务器仍然不打开 PDF 和 Word（安全规则不变），页面图片由浏览器画出来。

1. 浏览器在识别沙箱里把这一页画成 JPEG（长边 ≤ 1,600 像素、≤ 600,000 字节；Word 图片同样缩放并重新编码），交回页面。沙箱仍然断网，图片由页面发给服务器。
2. 页面调 `library.recognizeWithAi({documentId, kind, position, image})`，一次一页。
3. 服务端：查总开关和识别方式 → 核对 JPEG 文件头和大小（不解码）→ 限流 → **领取**（账号锁和文档锁下）：
   - 这个账号已经有一个 AI 识别调用没结束，就返回「稍后再试」、不发起。判断同时看两样，任一存在就算占用：**这个账号处于 `running`、领取不到 5 分钟（租期）的识别单元**，
     和 **BILL2 里这个账号用途 `library_ocr`、还没结算或退回的运行单**。领取在同一个事务里把单元改成 `running` 并写入预先生成的运行单 ID 后才放开账号锁，
     所以第二个客户端拿到锁时一定能看到这个占用，即使运行单还没建成；单元带着运行单 ID，删除文档时会被保留（`library_delete` 只删没有运行单 ID 的单元），
     所以文档中途被删后租期照样生效（卡住的运行单由恢复批次结清后才放开）；
   - 这一单元已经 `running` / `settling` / `complete`，直接返回现状，不发第二次；
   - 只有「可以再试」的单元能被领取（第 4.3 节）：`pending`、`paused`，或者 `failed` 且标为可重试、已发出的 AI 调用不到 2 次；
     领取时把单元改为 `running`、AI 调用次数加一、写入新的运行单 ID（上一个运行单此时一定已经结清，因为 `running` / `settling` 的单元不能再领），按输出上限先占空间。
4. BILL2 冻结 → 调模型。
5. 拿到文字：在文档锁下按 0287 的规则切段、插到这一页该在的位置、内容版本加一，单元 `complete`，然后结算。
   保存以服务器当时的内容版本为准（不拿浏览器发起时的版本去比），所以不会出现「付了钱却因为版本过期存不进去」。
   没有存下文字（模型返回空文字或文字超出上限）：单元 `failed`，这一次的费用按第 4.5 节**退回**——付了钱却没拿到文字，不让用户承担。

**账号级只允许一页同时识别**由第 3 步的服务器领取保证，不靠浏览器：同一账号在不同浏览器、不同设备同时打开资料库，也只有一页在调模型，
其他客户端拿到「稍后再试」后等一会儿再领下一页；删除正在识别的文档后马上去领别的文档，也会拿到「稍后再试」。租期过了还没结束的调用交给恢复批次（第 4.5 节）。

### 4.2 Vercel 运行时间

- 一次请求只识别一页、只有一次模型调用，通常 5–20 秒。tRPC 路由 `maxDuration = 300` 秒；单次模型调用超时设 90 秒，留足收尾时间。
- 请求体最大约 0.8 MB（data URL 上限 819,223 字节），在 Vercel 请求体上限（4.5 MB）以内。
- 不需要服务器分批：「分批」就是浏览器一页一页发，每个账号同时最多 1 页。

### 4.3 失败和重试

| 情况 | 单元状态 | 扣费 | 之后 |
| --- | --- | --- | --- |
| 发起前失败（校验、限流、冻结失败、路线不可用） | 回到原状态，调用次数不加 | 不扣，冻结立即释放 | 浏览器稍后重试这一页；同一轮里连续 2 次发起前失败就跳过它，下次打开资料库再试 |
| 已发出、模型报错（402 额度不足、路线拒绝等） | `failed`，可重试 | 按 BILL2 现有规则（402 不计费，#627） | 调用次数不到 2 次的，下次打开资料库会再试；到 2 次就不再试 |
| 已发出、超时或函数被杀，结果不知道 | `settling` | 冻结保留 | 恢复批次按运行单 ID 查官方费用并结算；文字拿不回来，属于**系统原因**，按第 4.5 节退回一次，单元回到 `pending` |
| 模型返回空文字 | `failed`，不可重试 | 结算后退回一次（没拿到文字） | 列表里这一页显示识别失败（现有状态文字），不再自动发起 |
| 文字太长、超出单个文档分段上限 | `failed`，不可重试 | 结算后退回一次（没存下文字） | 和浏览器识别同一规则（`LIBRARY_TEXT_LIMIT`），不再自动发起 |

服务器**不自动重发**已经发出的调用（结果不明确时不能盲目重试）。

**怎么区分能不能再试**：识别单元加两列，`ai_attempts`（这一单元已经发出的 AI 调用次数，领取时加一）和 `retryable`（失败时由服务器写：模型报错为可重试，空文字和超长为不可重试；
浏览器方式下失败的单元切到 AI 方式时算可重试、次数为 0）。待识别列表和领取用同一个条件：**`ai_attempts < 2`**，并且状态是 `pending`、`paused`，或 `failed` 且 `retryable`。
次数上限对所有状态都生效，包括超时后由恢复批次退回、回到 `pending` 的单元：恢复批次退回时如果这已经是第 2 次调用，单元直接改为 `failed`、不可重试，不再回到 `pending`。
所以一页最多发出 2 次付费调用，反复打开资料库、反复超时都不会无限发起。

**熔断（防止平台反复替用户承担损失）**：每次领取前，服务器从 BILL2 按用途 `library_ocr` 数最近**因线路故障**被退回的运行单（不新建表）。
只算「发出后结果不明、经恢复批次结算再退回」的运行单（BILL2 调用记录里已有恢复次数，大于 0 的才算）；模型正常返回但内容为空或超长而退回的不算，
所以文档里有几张没有文字的图标、插图，不会触发熔断：

- 全站最近 60 分钟退回 ≥ 5 次：暂停全站 AI 识别，新的领取一律返回「稍后再试」，单元保持原状态、调用次数不加、不扣费；
  每日对账报告列出，管理员处理（换模型、切回浏览器方式）后自动恢复，或 60 分钟窗口过去后自动恢复；
- 同一账号最近 24 小时退回 ≥ 3 次：这个账号当天不再领取新的 AI 识别，第二天自动恢复。

阈值是技术初值，放在后台设置里可改。这样某条线路持续超时时，最多损失几次调用就会停下，不会一页页、一份份文档地继续发。
内容为空或超长的退回另有一组上限（也是从 BILL2 数，不新建表），防止大量没有文字的图片让平台一直垫钱：

- 同一账号最近 24 小时这类退回 ≥ 20 次：这个账号当天不再领取新的 AI 识别，第二天自动恢复；
- 全站最近 24 小时这类退回的模型成本合计 ≥ 1 美元：暂停全站 AI 识别，每日对账报告列出，管理员处理后或 24 小时窗口过去后恢复。

两组上限触发时都一样：单元保持原状态、调用次数不加、不扣费。阈值是技术初值，后台可改。

### 4.4 余额不足、空间不足

冻结失败（余额不够这一页的上限）时不发起，单元标 `paused`，这份文档停在这一页之前，已识别的页保留，余额永远不为负；
页面显示现有那句「余额不足，已暂停识别；充值后打开资料库会自动继续」。充值后再打开资料库，自动从暂停的那页接着识别。
空间不够同样不发起、单元 `paused`，提示和浏览器识别现在一样。

### 4.5 中途删除、注销、退回

- **用户删除文档**：删除先拿文档锁，之后同一文档的新调用被计费范围拒绝（0286）。已发出的那一页结果丢弃、不保存，
  **照常按实际费用扣、不退**（Owner 2026-10-10 决定）。对账从 BILL2 按用途 `library_ocr` 找运行单。现有删除函数会**保留**还带着 `bill2_request_id` 的识别单元（`0203_library_documents.sql` 的 `library_delete`），
  而清理在这类单元还在时不会删掉文档和空间占用（`0207` 的 `library_cleanup_observe`）。所以：**运行单一结清（结算或退回），就清空这个单元的 `bill2_request_id`**；
  文档已经在删除中的，直接删掉这个单元。这样完成的页不会一直挡住以后的删除，被删文档的空间也能按现有清理流程释放。恢复批次结清运行单时做同一件事。
- **账号注销**：注销开始后不再发起；已发出的结果丢弃、**退回积分**（系统原因，Owner 2026-10-10）。计费记录本来就没有图片和文字（0286）。
  **现有 BILL2 做不到这一步，要在本任务的迁移里补**：注销开始后到账的回执，`bill2_record` → `bill2_payg_finalize` 发现 `bill2_erasure_closed`，
  用 `bill2_cancel` 以 `cancelled` 结案并按实际费用结算；而 `bill2_payg_compensate` 只退 `confirmed_failure` 的运行单，`bill2_close` 也不允许改已结案的结果。
  所以只包一层 `bill2_payg_compensate` 不够。做法：新迁移加一个只给 `library_ocr` 用的「注销退回」函数，在 `bill2_payg_finalize` 因注销以 `cancelled` 结案的**同一个事务里**
  按这次实际扣的积分退回一次（以运行单 ID 防重复，退回记录进现有积分流水和注销保留的财务投影，不含图片和文字）；
  注销完成证明要等账号下所有 `library_ocr` 运行单都结案并退回之后才能通过。集成测试覆盖「已发出、回执到达前开始注销」和「回执先到、之后注销」两种顺序。
- **系统原因退回**（进程崩溃、超时拿不到文字、模型返回空文字或文字超限没存下、注销清理）：按运行单 ID 只退一次。包一层现有 `bill2_payg_compensate`，加「这个运行单已退过」的判断，不另写退款逻辑。
- **领取后没发出去的调用**：领取（单元改为 `running`、次数加一、写入运行单 ID）之后、BILL2 发出调用之前函数就结束了的，恢复批次在租期（5 分钟）过后处理：
  运行单没建成，或者建成了但没发出（用现有 `bill2_revoke_unstarted_dispatch` 撤销、冻结全额释放），就把单元改回领取前的状态、**次数减回去**、清空运行单 ID。
  这一页没有产生费用，之后照常再领；被删文档的单元则直接删掉，不挡清理。
- **恢复批次**：接进已有的资料库清理 cron `api/cron/library-cleanup`（LIB_DOCS_PLAN 第 3 节第 7 点本来就让它负责识别对账；staging 每天一次，上线升级 Vercel Pro 后每 5 分钟），用户打开资料库时也对本人未结的运行单跑一次，页面不会一直停在「识别中」。
  限时运行，没跑完的留到下次；仍查不到费用的交给现有「卡住调用」流程由管理员处理。
- **会员退款**：识别扣的积分和对话一样，按现有退款规则处理，不加特殊规则。

## 6. 不做什么

- 不做「浏览器太慢就提示」、不做确认框、不让用户选择识别方式（Owner 2026-10-18）。
- 不在服务器上打开 PDF 或 Word；不用 OpenRouter 的整份 PDF 文件解析（`file-parser` / `mistral-ocr` 的解析费是否出现在用量里没有核实，没法冻结和结算）。
- 不建服务器队列、定时识别或后台常驻任务；用户不开页面就不识别。
- 不重做已经完成的页；不让 Agent 看图片；不识别资料库里单独上传的图片文件。
