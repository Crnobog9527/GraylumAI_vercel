# PAY-FAILOVER：人工双向切换与 Waffo 一次性应急收款

## 目标、完成标准与边界

依据 Owner 在 [#1234 批准评论](https://github.com/Crnobog9527/GraylumAI_vercel/issues/1234#issuecomment-6317561158)、MASTER_PLAN 2.1 2026-10-21 决定及当前任务：Stripe 永远主用；管理员一键将新购买切至 Waffo，并可切回。Waffo 的会员月付/年付、创始 496 美元、Pro/Gold 会员积分包均为一次性付款，银行卡也不产生自动续费。期限、升级、50 个共享创始名额、Gold 首购资格、退款和积分规则保持现行钱包契约。

完成标准：最终版本的代码、迁移 0332、数据库/集成和浏览器沙盒实测、CI 17/17、安全及独立机器人审查没有 P0/P1、未解决意见为 0。总控负责上库和合并；浏览器只承认包含本改动的环境，不把本地 fixture 当商户收款验收。

不做：自动故障切换、旧订阅迁移、未知付款跨渠道重扣、真钱、正式凭据或设置、任何分支部署。0332 只追加，不覆盖历史迁移或删除财务事实。本分支自动部署明确关闭。

## 实现契约

- 新开关为 `payment_method_routes.newPurchaseChannel`，缺省 `stripe`。与付款方式共用版本锁；专用 `pay_failover_set_channel` 只允许有效管理员、写审计、并发旧版本拒绝。通用设置保存不能绕过。旧 `payment_new_purchase_channel` 仍是旧接口配置，不代表此开关，后台入口已替换。
- 先确认当前新购渠道，再只构造对应 provider。Waffo 不要求 Stripe 在线；会员与创始名额从本地账务和部署模式读取。正式模式仍要求已有生产环境绑定与付款准入，不填任何正式配置。
- Waffo 只接受一次性商品映射。建结账页前核对商品、店铺、币种、实际价格和税类；请求 `withTrial:false`，以官方 `priceSnapshot` 锁定订单含税实付金额，不创建外部订阅。本站内部会员期限记录不等于供应商自动续费。
- 新商品复用 `payment_provider_refs`、订单快照及积分来源。会员映射 `price_usage=one_time`，包为 `package` 和 Pro/Gold tier；按冻结金额结算，不用原订阅 PROD 代替。清单见 [测试商品与验收前提](./PAY_FAILOVER_PRODUCTS.md)。
- 复用 #1233 / 0330 的同等级提前续买和改年付规则：从原已付到期日接续，未来期限不提前发积分；年付按原规则分期发放。源会员可为 Stripe 钱包或 Waffo 一次性，目标可双向切换。自动续费 Stripe 源的跨等级升级仍须先核实原订阅，Stripe 无法核实时安全拒绝该升级；普通应急新购买不受此依赖影响。
- 收款事实不要求 Waffo 订阅期号：强核原付款、店铺、模式、订单和金额，`provider_payment_method` 首次记真实 `card`/`alipay`，不覆盖原请求方式。未知实际方式保留现金、转人工，不猜成银行卡、不发权益。未知商品、期限或拒付也保留原款核对。
- 回调及每日查单复用幂等履约；切回 Stripe 后仍回收 Waffo 原订单。未知新 Waffo 付款不能按本地超时释放；完整查询原业务号，供应商订单全部终态取消且无成功或处理中付款，才可确认未付款。无匹配、查询失败、未绑定结账页或不完整结果保持阻塞。这个保护落实当前 Owner“查清前不换渠道重扣”的要求。
- 退款按原订单渠道分发，复用原审批、积分保留及结果 RPC。Waffo 工单批准不代表现金已退；查到独立成功退款并核对原 PAY、金额与累计退款后才收口。未知执行不再派发，不释放保留积分，每日继续查。失败或证据不足转人工；供应商失败可能需要后续人工重提，当前没有“绝不迟到成功”的证据，因此不自动恢复保留积分或重发。数据库模拟失败收口不代表供应商失败退款已验收。没有把“提交申请”写成退款成功。
- 拒付保留 Waffo 原生编号及实际金额；未知金额/币种照实留空并标记待核对，复用原来源冻结。部分拒付不伪造为全额。已完成全额或部分退款的原单仍记录后来拒付，保持原来源已收口状态，不重复回收权益或积分。Stripe 的自动处置只读取 Stripe 拒付；Waffo 不猜结案或自动解冻。
- 注销保留并验证新的付款请求封套、含税金额、原商品/订单归属和历史财务事实。既有 Stripe/Waffo 订阅留在原渠道，不迁移、不改扣款方式。升级后的原 Stripe 停续费请求与新权益同事务持久化，失败由原回收任务继续确认。

## 验证与外部前提

本地数据库与集成：双向切换、权限拒绝、版本并发与审计；并发/重复/迟到回调、失败与到期、不明付款禁止重新建单；共享创始池不超卖；会员接续、未来年付发放；原渠道会员/积分包退款收口；实际与未知拒付冻结；注销归属及旧订阅兼容。支付宝只用明确模拟事实覆盖。

staging 浏览器（当前 NOT_RUN）：总控确认 0330/0331/0332 依赖并完成正常上库、合并后的 staging 部署，确认一次性测试商品映射，再使用指定角色的 opaque storageState：

1. 管理员读取原版本与 Stripe 状态，切 Waffo、重读确认，保存审计证据。
2. 测试卡购买一次性会员；分开核对供应商现金、本站订单、内部期限、没有外部续费、积分与发放来源。
3. 同账号购买会员价积分包，分别核对实付金额和新增积分。
4. 经后台工单审批、执行原 Waffo 渠道退款，查到成功现金结果后核对积分、权益和后续发放收口。
5. 切回 Stripe 并重读；验证 Stripe 新购正常、原 Waffo 订单与退款依旧按原渠道处理。额外覆盖开着的旧结账页及迟到回调，不重扣。

测试模式 Waffo 不展示支付宝/微信，不把它算作失败代码或已通过支付宝验收。不部署任何分支；代码未进入 staging 时不能替代验证。

上线后（独立授权）：Owner 批准具体最小金额、笔数和费用后，支付宝真实付款并原渠道退款，核对现金、方式、本站权益积分和最终退款。当前不执行；正式商户审核、商品及凭据由 Owner 另行办理。

## 上库、切换与恢复

0332 必须在 0329/0330 和 #1237 的0331之后应用。Owner本轮将PAY-FAILOVER从0331改号为0332；先等#1237合并，再同步staging、重建指纹并重新验证。总控先核对前置迁移与最终检查、机器人覆盖和未解决意见，再上库、合并并完成上述 staging 验收。默认保持 Stripe；验收不等于批准正式应急启用。

应急与恢复均使用后台“新购买应急渠道”的版本锁操作，不手改旧全局设置。切回 Stripe 只影响新订单；保留 Waffo 回调、查单、退款和原账事实。出现不明付款先核对原订单，不删除映射或迁移旧订阅。出问题采用前向修复，不能用回滚历史约束覆盖已收 Waffo 一次性订单。
