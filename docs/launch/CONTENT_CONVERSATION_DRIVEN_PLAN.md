## 0. 结论摘要

Owner 定下的方向（第 45 项原话，摘录）：

> 定位之后的选题和创作改为自由对话加轻引导，按意图加载平台技能；一个窗口只做一个选题，选题窗口可以随时回来继续；
> 在选题窗口里聊其他选题时，模型提醒不要混用并提供新开窗口的入口，用户坚持也照常回答，但右侧只整理本窗口的选题；
> 自由对话要整理成纪要式记录，但不是每轮都整理，右侧侧边栏可以增加一个「整理纪要」按钮……
> 用户在聊天框里发送了"帮我整理一下聊天纪要"，也可以触发这个整理功能。是否保存到资料库由用户决定。

推荐做法，一句话：**不新建表、不新建会话类型，把现有的三种会话改成同一种对话界面。** 具体是：

1. **三种窗口都已经存在，只换交互**（第 2 节）：
   - **选题讨论窗口**：就是现有的选题工作区（`opc_topic_workspaces`，每个定位草稿一个，绑定确认过的定位版本和方法 Skill）。
     改成边写边显示的对话，候选选题以卡片出现在对话里，点"采用"或用文字明确采用。
   - **选题窗口**（一个选题一个窗口）：就是现有的"已承接选题"会话。每采用一个选题，`opc_handoff` 已经会给它开一个独立的
     `work_item` 会话。"一窗口一选题"不用新做，只需把窗口里的固定按钮流程换成对话。
   - **自由对话**：现有的自由对话会话（`opc_free_conversations`）。
2. **按意图加载 Skill**：复用 Runtime 里已有、但还没有界面在用的 `selection.kind:'auto'` 意图匹配（`runtime/matching.ts`），
   加一个"当前在用的 Skill"作为默认值，避免每轮来回切换（第 3 节）。
3. **视频线去掉固定按钮**：`[OPC_SCRIPT_V1]`、`[OPC_VIDEO_PACKAGE_V1]` 这些宿主写死的指令、四选一卡片、正文关键词匹配都删掉。
   口播稿、分镜、剪辑建议改成平台 Skill，由意图加载；用户说"存成口播稿 / 分镜"或点回复下面的保存按钮，才存进资料库（第 4 节）。
4. **"整理纪要"**：右侧按钮和聊天里的请求走**同一条路**——一次单独的整理执行，复用现有的 organizer 角色，
   结果存在这次执行的结果里，不建表（第 5 节）。
   - "提醒用户去点按钮"只靠系统提示词；
   - "聊天里请求整理"推荐用一个只发信号的工具 `request_minutes`，而不是让对话模型自己在正文里写纪要。理由见第 5.3 节。
5. **一窗口一选题的提醒**只靠系统提示词，加上选题窗口里一个固定的"新开一个选题"入口；不做硬拦截（第 6 节）。
6. **流式**：三种窗口的对话都按 #604 的统一机制边写边显示；#604 首版留给本方案的 T3 缓冲入口（runtime 页、选题页）在这里收掉（第 7 节）。
7. **计费**：每轮一笔运行单，意图匹配、正文、整理各是其中一次调用；纪要整理是单独一笔；全部按 BILL-PAYG 逐次冻结和结算（第 8 节）。
8. **和 #588 的关系**：#588 已合并（`4d805783`），管的是**带步骤 Skill（定位）每轮自动整理**进 Skill 清单字段；本方案管的是
   **定位之后**的窗口和手动纪要。两者共用右侧面板的外壳，数据和整理路径分开，不互相取代（第 9 节）。

## 2. 窗口和用户流程

### 2.1 三种窗口

| 窗口 | 现有载体 | 加载的 Skill | 右侧 | 整理方式 |
| --- | --- | --- | --- | --- |
| 定位（不在本方案） | 定位草稿会话 | 定位方法 Skill（带步骤） | Skill 清单 + 进度 | 每轮自动（#588） |
| 选题讨论 | `opc_topic_workspaces` 绑定的会话 | 方法 Skill 的选题资源（现状）；其他按意图 | 候选选题和已采用列表 | 不需要纪要（候选卡片本身就是结构化结果） |
| 选题窗口 | `opc_handoff` 建的 `work_item` 会话 | 按意图：口播稿、分镜、剪辑建议、图文等平台 Skill；默认是窗口自己的 Skill | 本选题的简报、已保存稿件、"整理本选题"按钮 | 手动 |
| 自由对话 | 自由会话 | 按意图；没匹配到就普通对话 | "整理纪要"按钮和纪要 | 手动 |

### 2.2 选题讨论窗口

1. 入口不变：定位确认后"继续生成第一周选题"（v11 第 5.1 节：用户明确同意才启动），以及"做一批新选题"。
2. 打开后是和其他窗口一样的对话界面。Agent 读当前定位，信息够就直接提几条候选，不够才问；用户可以随便聊、改方向、要更多。
3. 候选选题以卡片出现在 Agent 回复里（标题、简报、类型：文章 / 图文 / 视频 / 未知），正文边写边显示，卡片在这一轮写完后出现（第 7 节）。
4. 采用：点卡片上的"采用"，或者用文字明确说"就做第 2 和第 4 个"。现有的 `adoption-consent` 规则不变：模型提出的采用动作
   必须和用户自己那句话对得上才执行；含糊的话不算。
5. 采用后，每个选题出现"进入这个选题"的入口，进去就是它自己的选题窗口。

### 2.3 选题窗口（一个选题一个窗口）

1. 从选题讨论窗口、左侧栏的选题列表或资料库进入；随时可以回来继续，历史和右侧内容都在（会话本来就是持久的）。
2. Agent 先开口：根据本选题的简报和已有稿件，说现在到哪一步、建议下一步做什么（例如"要不要先写一版口播稿？"），
   **不替用户开始写**——继续讨论不等于授权生成（v11 第 5.1、5.3 节）。原来 `&continue=1` 自动发送的引导由这次开场取代。
3. 用户说"帮我写个口播稿""这段改短一点""出分镜"，系统按意图加载对应的平台 Skill（第 3 节），按 Skill 的方法来写和改。
4. 用户满意某一版时，说"就用这版作为口播稿"或点回复下面的"存为口播稿"，才保存（第 4 节）。
5. 聊到别的选题时，Agent 提醒并给出新开窗口的入口；用户坚持也照常回答（第 6 节）。
6. 右侧"整理本选题"按钮：把这个窗口里关于**本选题**的讨论整理成简报更新、已定内容和待办；用户决定要不要存进资料库（第 5 节）。

### 2.4 自由对话

1. 和现在一样新建、继续；按意图加载 Skill，没匹配上就普通对话。
2. 右侧新增面板：一个"整理纪要"按钮，下面显示最近一次纪要。
3. 不会每轮自动整理。聊了几轮、Agent 觉得有值得留下的结论时，在回复末尾提醒一句"需要的话可以点右侧「整理纪要」"；
   不点就不整理。
4. 用户在聊天框里说"帮我整理一下聊天纪要"，效果和点按钮一样（第 5.3 节）。
5. 纪要出来后，用户可以复制、导出 Markdown；存进资料库见第 5.5 节（Owner 已定 Q1）。

### 2.5 两个通用定义（全文统一按此读）

- **对话执行**：冻结角色为 `ordinary` 或 `skill` 的执行（含自动匹配后激活 Skill 的执行）。冻结角色为 `organizer` 的纪要 / 整理执行**不是**对话执行。
  凡是"从最新一次执行读取"的地方——当前 Skill（第 3.1 节）、待确认提议（第 3.5 节）、纪要请求信号（第 5.3 节）、
  可保存回复编号表（第 4.3 节）——一律指**本会话最新一次已完成、且可用的对话执行**，纪要执行不参与排序，也不会让前面的提议或信号失效。
- **可用**：一律用现有的检查判断，不另写一套。执行是否可用看 `runtime_history_available`（0158；内部经 `runtime_billing_allowed`
  对这次执行和全部祖先跑 `runtime_context_allowed` 依赖链）；内容版本是否可用看 `opc_content_allowed`（0128，递归检查内容、选题、
  来源定位和生成执行）。页面读到的执行一律来自已按可用性遮蔽的 `runtime_view`。不可用的执行不提供当前 Skill、提议、信号、编号或纪要正文。

## 3. 按意图加载 Skill

### 3.1 用现有的意图匹配

- 复用 `selection.kind:'auto'`：每轮先做一次匹配调用（计费阶段 `skill_matching`，输入只有用户这句话和候选 Skill 的公开名称、简介），
  选中就激活这个 Skill，没选中（`{"key":null}`）就按普通对话回答。现有的保护保留：候选只来自用户可见的、已启用的模块，
  Skill 简介和用户原话都当数据、不当指令。
- **匹配之前先过滤掉带步骤的 Skill**（审查 P1）：现在 `discoverRuntimeCandidates` 会把 `requiresTask` 的模块也放进候选，
  `matchingInput` 又不带这个标记；匹配器选中它时，付费的匹配调用已经发生，`activateRuntimeCandidate` 才抛
  `RUNTIME_SKILL_TASK_REQUIRED`。改为在组装候选时就去掉 `requiresTask` 的候选，只把剩下的交给匹配器；候选为空时不发匹配调用，
  直接按当前 / 默认 Skill 或普通对话处理。这和 PAYWALL 的入口规则一致（Master Plan 第 7.1 节 PAYWALL 行："新对话入口和以后的
  按意图选 Skill 不加载带步骤的 Skill"）：带步骤的 Skill（定位等）只从自己的入口开始。
- 需要补的一点：**当前在用的 Skill**。匹配输入里加上这个窗口上一轮实际用的 Skill（从本会话最新一次已完成、可用的对话执行的冻结记录读，第 2.5 节，不信浏览器），
  规则是"用户没有明确换一类任务就保持当前 Skill"。这样"改短一点""第二段再口语化些"不会被匹配成普通对话。
  这是 `matchingInput` 和 `MATCH_INSTRUCTIONS` 的小改动，不新建机制；窗口的 Skill 也不再只记在 localStorage。
- 选题窗口的默认 Skill（`runtime.choices` 的 `defaultSkill`）只在它不带步骤时才作为没有任何匹配时的保底；否则退回普通对话。
  推导"当前 Skill"和"默认 Skill"时同样排除带步骤的 Skill：`opc_handoff` 复制过来的默认 Skill 就是定位方法（带步骤），
  它不能作为内容窗口的按意图默认值。这种情况下保底改为普通对话，选题窗口里的写稿靠平台 Skill（第 3.4 节）。
  现有选题窗口靠定位方法 Skill + `[OPC_SCRIPT_V1]` 写口播稿的做法，随 P1-B 删除固定流程一起停用；
  所以 P1-B 必须在首批平台 Skill 发布之后才上线，否则选题窗口会失去写稿能力（第 10 节前置已改）。
- 用户能看到当前用的是哪个 Skill（输入框上方一个小标签，例如"口播稿"），可以点掉回到普通对话；这只是显示和一次性覆盖，
  不是让用户挑 Skill 的菜单。

### 3.2 为什么不用其他做法

| 做法 | 结论 |
| --- | --- |
| 让对话模型自己调用一个"加载 Skill"工具 | 要先发一次请求才知道加载什么，再发第二次正文请求，等于两次对话模型调用；还要扩工具白名单。现有匹配调用输入很小、更便宜 |
| 宿主用关键词判断 | 就是现在视频页的正则，Owner 这次决定要去掉的正是这种写死的流程 |
| 页面上给 Skill 下拉菜单让用户选 | 不是"按意图"；新手也不知道选哪个 |

### 3.3 首字延迟

匹配调用在正文调用之前，会推迟第一个字。实施 PR 用 AC-0 的计时记录测"匹配耗时"：

- 如果加上匹配后首字中位数仍在 v12 第 3.5 节的 3 秒内，就保持现状（匹配用对话模型）；
- 否则改为用后台的整理模型做匹配（它更快更便宜），这是实施时的技术选择，不需要 Owner 决定；
- 还可以在"当前 Skill 存在、而且这句话很短"时跳过匹配直接沿用——这条只在实测证明需要时才加。

### 3.4 平台 Skill 是前提

- 仓库里没有口播稿、分镜、剪辑建议、图文这些平台 Skill；Skill 是数据库里发布的模块（`skills`、`skill_revisions`、
  `skill_packages`）。现在的口播稿靠定位方法 Skill 加宿主写死的 `[OPC_SCRIPT_V1]`，分镜和剪辑靠宿主写死的
  `[OPC_VIDEO_PACKAGE_V1]` JSON 指令。
- 本方案把这些宿主指令里的写作要求搬进平台 Skill 包。v11 第 5.3 节的产品规则（分镜对应口播段落、画面、时长；
  剪辑说明开头、节奏、字幕、声音；给新手可执行的方案；不做图片视频生成和真实剪辑）写进 Skill，不写进页面。
- 首批 Skill 的范围和由谁写已由 Owner 定为 Q2（第 14 节）。平台 Skill 发布之前，按意图匹配没有可选对象，
  选题窗口退回普通对话（窗口默认的定位方法 Skill 带步骤，不能作为默认，第 3.1 节）；所以 P1-B 以首批平台 Skill 已在 staging 发布为前提，
  在那之前旧页面和旧流程照常运行。

### 3.5 Agent 提议下一步、用户只回"好"（审查 P1）

匹配器只看到用户这句话和当前 Skill，看不到 Agent 上一条的提议；只按"没明确切换就保持当前 Skill"，用户回"好"会留在口播稿 Skill
或退回普通对话，选不中分镜。做法是**提议由服务端冻结、确认优先由服务端直接处理**：

- **提议是结构化的**：Agent 要提议换到另一个 Skill 时（例如写完口播稿问"要不要基于这版出分镜？"），在正文之后调用信号工具
  `offer_skill({candidate})`，本轮结束（和 `ask_question` 一样用 `stopAtToolNames`）。`candidate` 只能是这一轮冻结候选表里的一个
  （已经去掉带步骤的 Skill，第 3.1 节）。宿主把它记成这次执行的**待确认提议**（执行结果里，不建表），页面在回复下面显示两个按钮：
  "好，生成分镜" / "先不用"。
- **点按钮：服务端直接处理，不发匹配调用。** 按钮请求带着提议所在的执行 id；服务端核对它是本会话**最新一次已完成、可用的对话执行**（第 2.5 节，纪要执行不算）、
  带待确认提议、还没被回应过，然后用提议里冻结的 `{moduleId, revisionId}` 直接以 `selection.kind:'skill'` 准入。省一次匹配调用，结果确定。
- **打字回"好""可以"**：下一轮准入时，服务端从本会话最新一次已完成、可用的对话执行读出待确认提议（第 2.5 节，不信浏览器），作为 `pendingOffer`
  一起放进匹配输入，匹配说明加一条：用户这句话是在同意这个提议时选它，在拒绝或说别的时按原规则。含糊的话（"嗯""再说吧"）不算同意，
  匹配器返回保持当前 Skill，Agent 再问一次。
- **提议的消耗和拒绝要在服务端可查**（第三轮审查 P2）。已完成执行的结果不能改，所以不靠"给提议打标记"：
  - **消耗规则**：一条提议只有在它所在的执行仍是本会话**最新的一次对话执行**（第 2.5 节，不计纪要执行）、而且仍可用时才有效。
    用户收到提议后先点"整理纪要"，提议仍然有效。之后任何一次对话执行被准入（不论它最后完成、失败还是停止），
    提议就视为已消耗——这是从执行顺序推出来的，不需要写入，刷新后也一样；
  - **"先不用"按钮**：等于用户发出"先不用"这句话，作为一轮普通对话准入，请求 id 由提议所在执行 id 确定性推出，
    冻结 `offerResponse:'declined'`。重复点击、刷新后再点都命中同一次执行，不会发两次；这一轮被准入的同时提议就按上一条规则消耗，
    Agent 简短回应后继续当前话题。这一轮照常计费（它是一次正常对话回复），不另设免费路径。**已定**：Owner 2026-10-04「同意：点"先不用"按一次普通对话计费。」
    （[#621 评论 5971624534](https://github.com/Crnobog9527/GraylumAI_vercel/pull/621#issuecomment-5971624534)）；
  - **"好"按钮**：同理冻结 `offerResponse:'accepted'`，请求 id 同样确定；准入前核对提议仍有效，已被拒绝或已消耗就返回明确的拒绝，
    页面刷新按钮状态；
  - 打字回复时，`pendingOffer` 只在提议仍有效时才放进匹配输入；已消耗或已拒绝的提议不会再出现，之后回"好"按普通规则匹配，不会切换。
- 生成本身仍要用户明确同意：点"好"或回"好"之后的那一轮才写分镜；`offer_skill` 只是提议，不触发生成。

## 4. 视频线和保存

### 4.1 去掉的东西

`[OPC_SCRIPT_V1]`、`[OPC_VIDEO_PACKAGE_V1]`、`[OPC_WORK_CONTINUE_V1]` 三个前缀、四选一卡片、关键词正则、
`runVideo` 的整条链（`prepareVideoMaterial` → `checkVideoExecution` → 视频包 JSON → `saveVideoResults`）、
`displayReply` 里的视频包和选题 JSON 解析。

### 4.2 保留的规则（v11 第 5.3 节，原样适用）

- 口播稿定稿只表示口播稿完成，不授权生成分镜或剪辑；
- 分镜要基于明确版本的口播稿，剪辑建议要基于明确版本的分镜；
- 改了口播稿后，旧分镜和剪辑标成"不再匹配当前口播稿"，不自动重新生成；
- 只有用户明确同意才生成。对话驱动之后，"明确同意"就是用户自己说"出分镜"或者点了对应建议——
  Agent 主动问"要不要基于这版出分镜？"时，用户回答"好"也算；"嗯""再说吧"不算。怎么保证"好"能加载分镜 Skill，见第 3.5 节。

### 4.3 保存怎么做

- 每条 Agent 回复下面，按这个窗口的内容类型显示保存按钮（视频：存为口播稿 / 分镜 / 剪辑建议；文章和图文：存为正文；
  都可以：存为简报）。按钮天然带着它所在那条回复的执行 id。
- 用户文字说"把第二稿存成口播稿"时，保存发生在**新的一轮**里，而 `opc_content_from_execution` 需要明确的 `p_execution_id`，
  只带 kind 的信号确定不了是哪一条回复（审查 P1）。做法：
  - 宿主在每轮的冻结上下文里附上本会话最近 10 条已完成、可用的对话执行回复（第 2.5 节；纪要执行和不可用的执行不编号）的**短编号**（`r1`…`r10`，从新到旧）和开头 60 字，
    编号到执行 id 的映射冻结在这一轮的执行记录里；
  - 信号工具 `save_content` 的参数是 `{kind, target}`，`target` 必须是这张表里的一个短编号；不在表里、或者用户的话指代不明时，
    Agent 应该先问"是哪一版"，不调用工具；
  - 宿主收到信号后，用这一轮冻结的映射把 `target` 换成执行 id，再在服务端核对它属于本会话、已完成、历史可读；
    然后页面弹出和按钮相同的确认，**确认框里显示被选中那条回复的开头和时间**，用户看清楚再点；
  - 确认请求携带的是这个执行 id，不是"最新一条"。
  这里保留一次点击，因为保存会生成不可改的版本，并影响后续分镜是否匹配。
- 写入复用 `opc_content_from_execution`：从本会话已完成执行的正文保存，冻结 `execution_id`。需要改的是它的**函数体**：
  - 允许 `storyboard`、`editing` 两种 kind（现在只有 brief、script）；
  - **来源版本由生成它的那次执行冻结的材料决定，不由浏览器传**（审查 P1）。只校验传入的 `source_content_id` 不够：
    用口播稿 v1 生成的分镜，在 v2 成为当前版本后经 `rN` 引用旧回复保存，会被当成基于 v2。
  - **在准入时从 `opc_content_versions` 推导，只有一个权威来源**（第三轮审查 P1）。不改 `runtime_scope_material` 的各个写入方：
    除了 `opc_content_from_execution`，`opc_content_manual_save`（手动定稿）和 `opc_library_edit`（改标题、简介等条目信息）
    也会追加最新材料，但只写正文或条目信息；如果靠材料带 id，用户手动定稿或改条目之后，下一次执行冻结的材料里就没有口播稿和分镜的 id，
    衍生内容的保存会被误拒；以后再加写入方也容易漏。做法：
    - **读用户内容一律复用现有的可用性检查**（第四轮审查 P1）：不用 service-role 直接查 `opc_content_versions`，否则会读到
      已撤销、已不可用的执行留下的正文，绕过 `opc_library` / `runtime_view` 的遮蔽。选择当前版本和读取正文都经过
      `opc_content_allowed`（0128，递归检查内容、选题、来源定位版本和生成执行的 `runtime_history_available`）。
      做法是一个新的只读 SECURITY DEFINER 函数（或在现有读取函数里加分支），只返回本人本选题**通过 `opc_content_allowed` 的**
      最新定稿 `script` 和最新 `storyboard`；不新建表；
    - **每轮只冻结版本身份，不带正文**（第四轮审查 P1）：选题会话每次准入时，把上面得到的两个版本 id 冻结进执行载荷
      （`contentSources:{scriptId, storyboardId}`，和 `scopeMaterial` 一样随执行冻结）。普通提问、改稿、闲聊都不额外注入正文，
      长内容不会挤占普通对话的输入预算；
    - **只有选中的衍生操作才注入对应的那一份正文**：平台 Skill 在 `workflow.yaml` 里用一个可选字段声明自己需要的来源
      （`contentSource: script` 或 `storyboard`；`skills/workflowManifest.ts` 现在不允许未声明字段，P1-A 一并扩展，旧包没有这个字段即不需要来源）。
      本轮最终选中的 Skill 声明了来源时，执行器按冻结的那个 id、再经一次 `opc_content_allowed` 读出正文注入本轮输入，
      并把实际注入的版本 id 记进执行检查点（`injectedSource`）；没声明来源的 Skill 和普通对话不注入；
    - **注入的来源接进现有依赖链**（第七轮审查 P1）：只记在检查点里不够——来源在衍生内容生成之后被撤销，衍生回复仍会留在 `runtime_view`
      里，后续对话的历史也会用到它。复用 0131 `runtime_context_allowed` 已有的依赖检查：它现在对 `read_source` 工具结果里的
      `dependencies` 逐个跑 `opc_source_allowed`，来源被撤销就让这次执行"不可用"；而 `runtime_history_available` 经
      `runtime_billing_allowed` 对执行本身和全部祖先都跑这条检查，所以不可用会自动传到之后所有依赖它的历史。
      P1-A 只在这条检查里加一个分支：执行记录里有 `injectedSource` 时，对它跑 `opc_content_allowed`（0128，本身又会递归检查来源内容的
      生成执行），不通过就按同样方式判为不可用。不新建依赖表，不另写可用性函数；

    - **放不下只拒绝这次衍生操作**：注入后超过该用途的 `inputBytes` 时，这一轮不发正文调用，以固定提示结束
      （"口播稿太长，无法基于全文生成分镜，请先精简或分段"），普通对话不受影响。按钮直接准入的路径（第 3.5 节）在准入时就知道选中的 Skill，
      在任何计费之前检查；按意图匹配的路径是匹配之后才知道，这时只有那次小的匹配调用已经结算；
    - 冻结的来源当时不可用（已撤销）时视为没有来源，衍生操作同样以固定提示结束；
    - **剪辑建议只能基于和当前口播稿匹配的分镜**（第五轮审查 P1）：口播稿 v2 定稿后，最新的分镜可能还是基于 v1 的。
      选中的 Skill 声明 `contentSource: storyboard` 时，派发正文调用之前先核对：冻结的 `storyboardId` 那份分镜的
      `source_content_id` 必须等于同一次冻结的 `scriptId`。不相等（或当前没有定稿口播稿）就不派发，以固定提示结束：
      "当前分镜基于旧版口播稿，请先更新分镜，再生成剪辑建议"。正文调用不发生、不收费；按钮路径在准入时检查，任何计费之前就拒绝；
      按意图匹配的路径和上一条一样，只有那次小的匹配调用已经结算；
    - `runtime_scope_material` 的写入方和内容都不改；材料照旧提供选题简报等上下文。
  - 保存 `storyboard` 时，来源 = 生成执行检查点里的 `injectedSource`（口播稿）；保存 `editing` 时，来源 = `injectedSource`（分镜）。
    没有 `injectedSource` 的执行（没注入来源、普通对话、旧执行）的回复不能存为分镜或剪辑建议；保存时对来源再做一次 `opc_content_allowed`；
  - 来源不是当前最新版本时，**照实保存并标明**：`source_content_id` 写冻结的旧版本，资料库和右侧显示"基于口播稿 v1，
    当前是 v2，不再匹配"；保存确认框里提前提示这一点。不把它当成基于当前版本，也不拦住用户留存旧版；
  - 浏览器仍可以传 `source_content_id`，但必须和冻结来源相等，不相等就拒绝（`OPC_CONTENT_SOURCE`）；
  - 其余检查（同一会话、执行已完成、历史可读、版本号、请求重放）不变。
- 这样"分镜和口播稿是否匹配"由数据库里冻结的来源和 `source_content_id` 链判断，不再需要 `opc_video_material_bindings` 这一层。
  旧绑定表和 `opc_video_results_from_execution` 保留，只读，供已有数据显示；随 LEGACY-CLOSE 再决定是否删。

### 4.4 为什么不新建表

- 考虑过：新建"窗口 Skill 状态表"、"纪要表"、"内容草稿表"。
- 都不需要：窗口就是现有会话；当前 Skill 从已完成执行的冻结记录读；稿件已有 `opc_content_versions`；
  纪要是一次整理执行的结果（第 5 节）。数据库改动只有函数：P1-A 改 `opc_content_from_execution` 的函数体（签名不变）；
  P2-A 改历史插入点和 `runtime_view` 的函数体，并加一个只读的纪要列表函数（第 5.1 节）。

## 5. 整理纪要

### 5.1 用现有的独立整理执行

- 点按钮 = 在本会话发起一次 `selection.kind:'organizer'` 的执行。它已经会：用后台配置的整理模型；读本会话历史
  （受 `organize` 用途的 `inputBytes` 限制，超出时裁掉最早部分，符合第 31 项"不做整段摘要替换原始记录"——纪要是另存的一份，
  原始对话一字不改）；按 BILL-PAYG 计费；可以重放和恢复。
- 宿主给整理执行加一段固定的纪要说明（作为 `additionalInstructions`），按窗口类型二选一：
  - **自由对话**：会议纪要格式——讨论了什么、定了什么（只写用户明确同意的）、还没定的问题、下一步；每条注明
    "用户说的 / Agent 建议的"，不编造用户没说过的事实、数字和经历。
  - **选题窗口**："整理本选题"——只整理和本选题有关的内容：简报需要更新的地方、已经定下的稿件要点、待办；
    和本选题无关的讨论直接略过（第 6 节"右侧只整理本窗口的选题"）。
- 这两段是宿主的通用格式，不是某个 Skill 的步骤或问题，不违反"页面和数据库不写死 Skill"。以后如果想让 Skill 自定义纪要格式，
  沿用 AGENT-CORE 规划的"`workflow.yaml` 可选整理模板"，不在本方案做。
- 纪要存在这次整理执行的结果里（`runtime_executions.result`）。右侧显示本会话**最近一次完成且可用的**纪要；
  更早的纪要在右侧"历史纪要"里按时间列出，都只读。
- **纪要不进对话历史**（审查 P1）：`selection.kind:'organizer'` 走普通执行器，会把整理器的输入和输出写进
  `runtime_session_history`。不处理的话，之后的对话和下一次整理都会把旧纪要当成对话内容，越整理越偏。做法是复用已有的
  `internal_control` 标记：
  - `runtime_session_history.internal_control` 已经存在（0106:48），所有历史选择都已经按 `NOT h.internal_control` 过滤
    （0106:226、0158:187、0158:231 等），现在用来排除匹配调用的内部轮次（0158:273，`e.payload ? 'matching' AND p_batch=0`）；
  - P2-A 改写这个插入点的函数体：冻结角色为 `organizer` 的执行，**全部批次**都写成 `internal_control=true`。
    于是纪要执行的输入、输出不出现在任何对话历史投影里，下一次整理读到的也只有原始对话；
  - 判断依据只用执行冻结的 `payload->>'role'`，不看内容；旧的整理执行（如果 staging 上有）不回写，P2-A 的测试说明这一点。
- **刷新后能找到纪要**（审查 P2）：现在的 `runtime_view` 只投影 `body`、`summary` 等，没有执行角色，页面刷新后分不出哪条是纪要。
  P2-A 在服务端加一个判别字段：`runtime_view` 的执行投影带上冻结的 `role`（只读，取自 `payload->>'role'`），
  纪要列表**从已经按可用性过滤的 `runtime_view` 投影推导**（第四轮审查 P1）：只取其中 `role='organizer'` 的已完成执行，
  正文用 `runtime_view` 已经遮蔽过的值；如果实施时为了分页另写一个只读函数，就对每一条用 `runtime_history_available`（批量用
  `runtime_history_availability`）过滤或遮蔽，不可用的只显示"这份纪要已不可用"，不返回正文。不只按所有者、会话、角色和完成状态筛选。
  右侧面板用它，不靠浏览器记忆。都是改现有函数体或新增只读函数，不建表；进同一个迁移。

### 5.2 不复用 #588 的 `opc_capture_apply`

`opc_capture_apply` 解决的是"按 Skill 清单的字段逐项写入，并保护用户改过的字段"。纪要没有字段清单，是一整段文字，
每次整理都生成新的一份、不覆盖旧的，也就没有"覆盖用户修改"的问题。硬套进去要给自由对话造一份假的字段清单，
反而违背 #588 第 3.1 节"清单是 Skill 声明的"。所以纪要走独立整理执行，#588 的写入函数只服务定位。

### 5.3 聊天里请求整理：系统提示词还是工具

Owner 问"判断……应该要通过系统提示词来实现是吗？"。分两件事回答：

1. **"聊得有价值时提醒用户去点按钮"——是，只用系统提示词。** 提醒只是正文里的一句话，宿主不需要知道。
   规则写进自由对话和选题窗口的固定说明：有了明确结论或材料积累到值得留下时，在回复末尾提醒一次；
   最近十轮里已经提醒过就不再提；不替用户整理、不说"已整理"。
2. **"用户在聊天里说'帮我整理一下纪要'"——推荐系统提示词加一个只发信号的工具，不推荐只靠系统提示词。**

| 做法 | 结果 | 结论 |
| --- | --- | --- |
| A. 只靠系统提示词：对话模型直接在回复里写纪要 | 纪要是一条普通回复，进不了右侧；用的是对话模型和对话的上下文规则，和按钮出来的不是同一份东西、格式和费用都不一样；用户以为"已整理"，右侧却是空的 | 不推荐 |
| B. 系统提示词 + 工具 `request_minutes`（推荐） | 对话模型识别到请求后，回一句"好的，我来整理"并调用这个工具，本轮结束（同 `ask_question` 的 `stopAtToolNames`）；工具没有参数、不读写数据，只是信号。页面收到信号后，自动发起和点按钮**完全相同**的整理执行 | 推荐：按钮和文字走同一条路，结果一致；也符合 D10"文字明确同意等同于点击" |
| C. 宿主关键词匹配"整理""纪要" | "这个整理一下思路"之类会误触发；"总结下我们聊的"又漏掉 | 不推荐 |

做法 B 的细节：

- 识别交给对话模型，系统提示词说明：只有用户明确要求整理或总结本次对话时才调用；用户只是说"整理一下这段文字"
  （要改写某段内容）不是纪要请求。
- 工具调用之后的那次整理执行用确定性的请求 id（由触发它的执行 id 推出），页面刷新或重连后重复发起会命中同一次执行、
  不会整理两次、不会收两次费。页面在整理执行开始前关掉的话，下次打开时右侧显示"上次请求的整理还没开始，点这里继续"，
  不在服务端自动补做（不新建队列或定时任务，和 AGENT-CORE"整理的触发"一致）。
- **重开页面要能认出这个信号**（第五轮审查 P1）：0158 的 `runtime_view` 只投影 `body`、`summary`，没有已校验的工具调用，
  客户端分不出信号和普通文字，也拿不到触发执行 id，付费的识别轮就丢了。P2-A 在现有、已按可用性过滤的 `runtime_view` 执行投影里
  加一个 `signal` 字段：`{type, executionId}`，`type` 取 `request_minutes` / `offer_skill` / `save_content`，只来自这次执行
  经宿主校验后记录的信号工具调用（工具名在白名单里、参数通过校验），不解析正文；`offer_skill` 另带冻结的候选和回应状态，
  `save_content` 另带 `kind` 和换算后的目标。不可用的执行不投影信号（沿用 `runtime_view` 的遮蔽）。
  页面打开时：最新一次已完成、可用的对话执行（第 2.5 节）带 `request_minutes` 信号、而由它推出请求 id 的整理执行还不存在时，右侧显示"继续整理"；
  已存在就直接显示它的状态。`offer_skill` 的两个按钮、`save_content` 的确认框，刷新后也都从这个字段恢复。
- 需要扩的：工具白名单加 `request_minutes`（`bill2/openRouterAdapter.ts` 现在只放行 `read_source` 等少数工具），
  以及让非导师的对话轮次也能用"调用后结束本轮"。这是 Runtime 工具面的改动，按 high 处理（第 10 节 P2-A）。
- 如果实施时发现非导师轮次加工具会改动 #604 C0+C1 正在改的请求格式，P2-A 等 C0+C1 合并后再做，在此之前
  聊天请求先按做法 A 的退路处理：Agent 回复"请点右侧「整理纪要」"，不自己写纪要。

### 5.4 选题窗口里的"整理本选题"

和纪要同一条路，只是说明不同（5.1）。整理结果里的"简报更新"可以由用户点"存为简报"保存成新的简报版本

### 5.5 存进资料库

- **选题窗口**：存为简报 / 口播稿 / 分镜 / 剪辑建议，进入现有资料库的这个选题下（`opc_library` 已按选题组织）。
- **自由对话**：现在的资料库没有地方放"不属于任何选题的文字"（`opc.saveWorkResult` 要求 `workItemId`，自由对话会报
  `OPC_RESULT_DENIED`）。资料库上传"我的文档"（LIB-DOCS）会新建文件登记，那是正确的归宿。
  已定：**首版纪要只能复制和导出 Markdown，LIB-DOCS 上线后加"存到我的文档"**，不为纪要单独再造一个存储（Owner 已定 Q1）。
- 不管存不存，纪要本身一直留在会话里，随会话删除和账号注销一起清除（沿用 DATA-ERASURE 对 `runtime_executions` 的处理）。

## 6. 一窗口一选题：提醒，不拦截

- 选题窗口的固定说明里带上本选题的标题和简报（已在 `runtime_scope_material` 里，`opc_handoff` 和资料库编辑都会更新它）。
- 规则（系统提示词）：
  - 用户聊的是另一个选题（不是本选题的角度、标题或稿件的修改）时，先简短提醒"这个窗口是为「本选题」开的，
    新选题建议点上方「新开一个选题」，这样右侧和资料库不会混在一起"，然后**照常回答**；
  - 用户说"就在这里聊"或继续聊，不再重复提醒（同一个话题只提醒一次）；
  - 不拒绝、不拖延回答，不把新选题的内容写进本选题的稿件建议。
- "新开一个选题"是选题窗口顶部一个固定入口：跳到这个定位的选题讨论窗口，输入框预填"我想加一个新选题："，
  用户自己补完再发。不新增工具、不新建会话类型；新选题仍走选题讨论 → 采用 → 新窗口这条现有路径。
- 右侧只整理本选题，由 5.1 的"整理本选题"说明保证；保存按钮只写本选题（`opc_content_from_execution` 按会话绑定选题，
  写不到别的选题）。
- 不做硬拦截的原因：Owner 原话"用户坚持也照常回答"；硬拦截还需要宿主判断"是不是另一个选题"，只能靠关键词或额外模型调用，
  误拦的代价比偶尔混用大。

## 8. 计费、付费墙和限流

- **每轮一笔运行单**：匹配（如有）、正文、工具读取、搜索都是这笔运行单里的调用，按 BILL-PAYG 每次调用前冻结、调用后按名义费用结算，
  整笔最后只进位一次（第 26–27、41 项）。这和现在 `auto` 的计费方式一致，不新增计费路径。
- **纪要是单独一笔**：一次整理执行一笔运行单，一次整理调用。不做运行前费用预告（Owner 已定 Q3）。
- **"失败不收费"的范围**（审查 P1）：只适用于**确定没有产生费用**的情况——调用在派发给供应商之前就失败（准入、闸门、余额、配置），
  或者供应商明确返回了失败。请求**已经派发**之后超时、断线、没拿到回执的，结果是"未知"，不是失败：按 BILL-PAYG 的未知结果规则
  保留这次冻结，用原调用身份对账，不盲目重发、不盲目退款（第 26 项"未知结果保留冻结并按原身份核对"）。页面显示"整理结果暂时不确定，
  正在核对"，不提示"没有扣费"。核对确认没有费用才释放冻结；核对出费用就按名义费用结算，纪要正文能取回就显示。
  整理执行用确定性请求 id（第 5.3 节），用户再点一次按钮只会命中同一次执行，不会在核对前再派发一次。
- **余额不足**：按 BILL-PAYG，可用余额低于该用途的启动门槛 L 时，在调用之前停下、提示充值；充值后从断点继续。
  纪要整理如果因为余额停在调用之前，整理执行保持待继续，不会产生半份纪要。
- **付费墙**（第 50 项）：只有带步骤 Skill 的**报告**需要付费会员。选题、写稿、纪要都不是报告，免费用户可以用，照常扣积分。
  会员档位不影响用哪个模型；对话、匹配、整理的模型都按用途由后台配置；输入框模型位置只显示 Auto。
- **限流**（第 30、49 项）：每发一条消息算一次；点"整理纪要"也是一次新的模型执行，同样算一次，并经过 #594 的调用闸门和一键暂停。
  `request_minutes` 触发的整理是用户这一条消息引起的第二次执行，也算一次（推荐，避免绕过限流）。
- **提示缓存**：平台 Skill 正文是稳定前缀，沿用 #591 的缓存标记；匹配调用输入小，不单独处理。

## 11. 验收和必测

### 11.1 验收（staging，真实模型）

1. 定位确认后进入选题讨论，Agent 边写边出候选；用文字"就做第 2 个"采用，出现该选题的窗口入口。
2. 进入选题窗口，Agent 开场建议下一步但不擅自写稿；说"写口播稿"加载口播稿 Skill（输入框上方显示），边写边出；
   说"改短一点"仍用口播稿 Skill。
3. 点"存为口播稿"或说"把这版存成口播稿"并确认，资料库该选题下出现定稿口播稿；再说"出分镜"，分镜基于这版口播稿；
   改了口播稿并重新定稿后，旧分镜显示"不再匹配"。
4. 在选题窗口聊另一个选题：Agent 提醒一次并指向"新开一个选题"，用户坚持时照常回答；随后"整理本选题"的结果里没有另一个选题的内容。
5. 自由对话聊几轮有结论后，Agent 提醒一次去点「整理纪要」；不点就没有纪要；点了右侧出现纪要。
6. 在聊天里说"帮我整理一下聊天纪要"，右侧出现和按钮同格式的纪要；说"帮我把这段文字整理一下"不触发纪要。
7. 刷新、断网、重新登录后，三种窗口的对话、当前 Skill、纪要、已保存内容都能恢复；没有重复收费。
8. 余额低于门槛时，发消息和点整理都在调用之前停下并提示充值；充值后继续。

单元（进 CI）：

  `pendingOffer` 并选中被提议的 Skill；回"嗯""再说吧"→ 不切换；提议不在最新一次已完成、可用的对话执行上的、已被回应过的、或候选是带步骤 Skill 的都拒绝；
  隔一轮之后提议失效；

  匹配输入里没有 `pendingOffer`、不切换 Skill；提议之后用户发了别的消息，再点"好"被拒；纪要执行不消耗提议；
- 衍生内容来源（准入推导）：用户手动定稿口播稿（`opc_content_manual_save`）之后、以及编辑条目标题和简介（`opc_library_edit`）之后，

  选择当前版本和读取正文都经过 `opc_content_allowed`：来源执行被撤销或历史不可用后，不再被选为当前版本、不会被注入、不能作为保存来源；
  普通提问、改稿的执行载荷里只有版本 id、输入里没有口播稿和分镜正文；在口播稿和分镜都接近 2 万字的长内容选题里，普通提问仍正常完成；
  选中分镜 Skill 且注入后超出容量时，只这一轮以固定提示结束，下一轮普通提问正常；按钮路径在计费前就拒绝；
  只有带 `injectedSource` 的执行能存为分镜或剪辑建议；
- 依赖链：基于口播稿生成分镜之后，撤销口播稿的生成执行（或它的来源定位版本），这条分镜回复在 `runtime_view` 里被遮蔽、
  不能再保存、不进入之后任何对话执行的历史，基于它的剪辑建议执行同样不可用；没有 `injectedSource` 的执行行为不变（回归 0131 现有用例）；

  最新对话执行不可用时，它的提议、信号、当前 Skill 都不再生效；

  剪辑建议同理检查冻结的分镜来源；
- `save_content`：用户引用的**不是最新一条**回复（例如 `r3`）时保存的是 `r3` 对应的执行；`target` 不在这一轮冻结的表里时拒绝；
  映射里的执行属于别的会话、未完成或历史不可读时拒绝；确认请求带的执行 id 和映射不一致时拒绝；
- 纪要执行的全部历史批次 `internal_control=true`；之后的对话轮次和下一次整理的历史投影里都没有旧纪要的输入和输出；
  匹配调用原有的 `internal_control` 行为不变（回归 `runtime.integration.ts` 现有用例）；
- `runtime_view` 带出冻结的 `role`；纪要列表只返回本人本会话 `role='organizer'` 的已完成执行；页面刷新后右侧仍显示最近一次纪要；

  "request_minutes" 字样但没有真实工具调用时不投影信号；执行历史不可用后不投影信号；`offer_skill` 按钮和 `save_content` 确认框刷新后同样恢复；

### 11.3 付费小评测（E）

用真实模型在本机测三件只有模型能决定的事，先冻结请求、经总控核对后才发出，每条先预留再结算，费用未知即停、不重试、不补样：

| 项 | 样本 | 门槛 |
| --- | --- | --- |
| 意图匹配 | 40 句（换任务、继续改当前稿、普通提问、模糊请求各 10；其中 5 句是对上一轮提议只回"好""可以"，带 `pendingOffer`） | 正确 ≥ 36/40；"继续改当前稿"误切换 ≤ 1；只回"好"选中被提议 Skill 5/5 |
| 纪要请求识别 | 20 句（明确要纪要 10、改写某段文字等易混 10） | 漏判 ≤ 1、误判 ≤ 1 |
| 一窗口一选题提醒 | 10 个场景 × 3 轮 | 该提醒时提醒 ≥ 9/10；用户坚持后照常回答 10/10；同一话题重复提醒 ≤ 1 |

金额估算按 #582 的 Sonnet 每次约 0.11 美元上限：匹配和识别 60 次（输入小、输出极短，按每次 0.02 美元上限计约 1.2 美元），
提醒 30 次对话约 3.3 美元，另加 10 次纪要整理约 0.1 美元，**合计硬上限 5 美元**（Q4）。

## 13. 风险

1. **意图匹配推迟首字**：多一次调用。用第 3.3 节的计时和退路处理；最差情况是用整理模型匹配。
2. **匹配误切换**：用户在改稿时被切到别的 Skill。当前 Skill 提示 + 小评测门槛 + 用户可以点掉标签。
3. **平台 Skill 质量决定体验**：宿主不再写死写作要求后，口播稿、分镜质量全看 Skill 包。P1-S 要有 Owner 看过的样例；
   Skill 没发布前只能退回普通对话，所以 P1-B 以首批平台 Skill 已发布为前提，在那之前旧流程照常运行。
4. **纪要读不到很早的对话**：整理读历史受 `inputBytes` 限制，超长对话裁掉最早部分。纪要里注明"只整理了最近的部分"（宿主根据是否裁剪加一句），
   不做摘要压缩。
5. **工具面扩大**：三个信号工具都不直接读写数据库，参数只能取本轮冻结表里的编号，只让宿主弹出和按钮相同的动作；仍按 high 审查。
6. **共享文件拥挤**：`admission.ts`、`execute.ts`、`service.ts` 同时被 #604、PAYG、#588 B2 和本方案改。严格按第 9.3 节顺序，同一时间一个写入方。
7. **自由对话纪要暂时存不进资料库**（Q1 已定）：首版只能导出，用户可能期待能存。页面上写明"存到我的文档即将支持"之类的提示由前端决定，
   不承诺日期。
