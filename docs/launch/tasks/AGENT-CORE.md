## 实现机制（从规划正文移来）

| 项目 | 做法 |
| --- | --- |
| 提问卡 | 在现有 Runtime 里给 Agent 增加一个"提问"工具。锁定的 `@openai/agents` 0.18.0 支持"调用指定工具后结束本轮"（`stopAtToolNames`），项目代码从未用过，AC-0 先验证。现有请求适配器只放行 `read_source` 一个工具（`bill2/openRouterAdapter.ts`），需要扩展 |
| 文字确认 | 用户用文字明确同意时，Agent 调用"确认本步"工具，宿主做与点击相同的版本检查 |
| 读取 Skill 参考文件 | Agent 始终加载 `SKILL.md`，进入某一步时用只读工具读该步的参考文件。需要先读文件的一轮，第一次调用不出字，AC-0 要实测这种情况的首字时间 |
| 回复形式 | 直接输出自然语言并流式显示，不再要求导师输出 JSON |
| 推理设置 | 先完成 PR #446 作为止血，之后由 MODEL-REASONING 的后台配置取代代码里写死的对照表 |
| 整理结果的保存 | 仍按 Skill 在 `workflow.yaml` 里声明的信息字段保存，每个字段带来源和状态；下游（`opc_profile` 等）读取方式不变 |
| 整理格式 | `workflow.yaml` 新增可选的整理模板和报告模板路径；现有校验不允许未声明字段（`skills/workflowManifest.ts`），需要扩展；旧版本没有这些字段时用通用模板；定位 Skill 需要发布带模板路径的新版本，进行中的旧草稿继续用旧版本 |
| 整理的触发 | 回复完成后由页面发起一次单独的整理请求；页面关闭导致没发出时，下次打开会话或发送下一条消息时补做。不新建队列或定时任务 |
| Agent 读取资料 | 现有只读工具只列 40 条、按 ID 排序、读不到稿件和定稿；改为按时间列出并能读取已保存成果 |
| 上下文容量 | 自由对话入口整个请求上限 32,000 字节，定位入口 64,000 字节；加载完整 `SKILL.md`、文风画像前先复核 |
| 计费 | 每条消息一个计费运行单；整理调用在账单明细里单独列出 |

## 未定案：后台整理的并发机制

**状态：冻结，不再追加规则。** 2026-09-27 规划审查中，"整理在附属会话里异步运行、笔记带版本号冲突检测、跳过和合并排队任务、运行单延后结算、确认按钮等待整理"这一套机制，被连续多轮审查提出高优先级问题（见下方清单第 1–14 项）。按 Owner 的规则，停止在规划里继续补规则，改为在 AC-2 的实施方案里重新选型。

实施方案必须在下面两个方案中选一个，并写明理由。方案 B 会让用户连续发消息时等几秒，属于用户可见的体验变化，选择时请 Owner 确认：

| | 方案 A：附属会话异步整理 | 方案 B：同一执行里串行整理（推荐先评估） |
| --- | --- | --- |
| 做法 | 回复结束后，在挂在主会话下的附属会话里跑整理；输入框完全不锁 | 沿用现有"主回复 + 整理"在同一个执行里完成的做法；主回复一结束就流式显示完毕，用户可以打字，但下一条消息要等这次整理完成后才发出（通常几秒） |
| 需要改的 | 附属会话、运行单延后结算、笔记版本冲突、排队跳过、积压上限、确认等待与重绑，见下方清单 | 基本不改 Runtime 和 BILL2；只需把"整理结果写入"和"用户手动编辑"按版本号串行化 |
| 代价 | 复杂，钱路核心改动多，边界情况多 | 用户连续快速发消息时要等几秒 |

## 必测项清单（来自 2026-09-27 Codex 审查，PR #448）

选用方案 A 时，下列各项都要有自动测试；选用方案 B 时，逐项说明为什么不再适用，适用的仍要测。

1. 会话同一时间只允许一个执行：附属会话必须有自己的执行锁，不能被主会话占用或占用主会话。
2. 整理和 Fusion 的调用不能各开运行单导致多次预扣、多次取整；登记到触发它的消息的运行单或整组运行单。
3. 整理进行中用户手动改笔记：旧结果不能覆盖手动修改，也不能把基于旧笔记推出的内容写进未改动字段。
4. 两个整理先后完成顺序颠倒时，较新的对话轮次不能被丢掉。
5. 被跳过的排队整理不能导致某一轮对话永远没被整理。
6. 一条消息的运行单只预留一次整理调用；冲突时不能在原运行单上重复派发。
7. 被跳过、丢弃、超时或失败的整理，都要让对应运行单正常收尾、释放多余预扣。
8. 积压的未整理轮次超过整理模型上下文或运行单预算时，要有上限和分批处理。
9. 整理失败、超时或被丢弃时，确认按钮不能永远停在"整理中"，要给出重试或按当前笔记确认的出口。
10. 本步小结卡要绑定包含这一轮在内的笔记版本；正常情况下只需确认一次；被更新一轮的整理合并覆盖时也要能确认。
11. 确认时再次核对对话轮次和笔记版本，变化时刷新小结卡，确认后的整理不改动已确认内容。
12. 退款发生时存在未结算的整理调用：结算后金额守恒，不多退不少退（Fable 评估）。
13. 月度积分释放发生在预扣和结算之间时结算正确（Fable 评估）。
14. 模型没有调用提问工具、直接用文字提问时，按普通回复显示，流程继续。
15. 页面关闭导致整理请求没发出时，服务端按时限自动取消未派发的整理调用，结算那条消息并退回多余预扣；之后再整理算一次新的收费操作。
16. 数据使用同意：默认不参与；勾选后记录才可进入案例视图；撤回后尚未使用的记录移出；未同意用户的记录在服务端被过滤，不能通过接口读到。
17. 去除身份信息：已同意用户的对话里含有姓名、联系方式、账号或用户编号时，案例视图和相关接口都读不到这些原文，只能读到去除后的版本。
