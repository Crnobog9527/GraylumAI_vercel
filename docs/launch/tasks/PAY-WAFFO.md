  Gold 曾购 HMAC 事实扩展现摘要机制的 purpose 和有限留存；创始历史售出计数不随退出减少。
- 现有 provider refs 没有事件处理状态且不能表达“收到后尚未履约”；需最小 Waffo 事件收件记录，
  唯一键为 channel/store/mode/eventType/eventId，保存必要事实、摘要、处理结果及重试状态。
  它只证明接收/处理，钱和权益权威仍是订单/原账本；复用现有定时入口补偿，不新建消息系统。
- 现订单快照缺少独立的、可追加且关联后续自动续费的同意事实；优先按订单增加不可变 consent 记录，
  旧条款全文由版本库保留，付款证据按 N1 独立短期保存。若需独立表，只承载该最小关系，
  不搭通用审计平台；财务字段与可删除 IP/设备字段分开，避免扩大三年财务保留范围。

  旧 schema/代码兼容、幂等回放、权限拒绝路径和恢复都在 PR-1 证明。

### 5.3 验签、幂等、金额和乱序

按[官方回调协议](https://docs.waffo.ai/api-reference/webhooks)设计，实施时锁 SDK 版本验证：

1. 原始字节接收，解析 JSON 前验证 `X-Waffo-Signature`；RSA-SHA256 的签名输入为
   时间戳、点号、原始正文。使用官方验证器，明确绑定预期环境；再校验事件 mode、store 与订单命名空间。
   Waffo 用 prod、本地用 live，显式映射。公钥按环境共用，签名正确不证明属于本商户。
2. 当前协议重试复用原签名时间，按官方 45 分钟窗口验证（未来偏移同样限制），不能照搬 Stripe 的 5 分钟。
   过窗事件用受控权威查询对账，不能关验签。缺签名、篡改、错误环境拒绝且不产生业务写入。
3. 验签后先持久化最小事件事实再回复 2xx，目标 10 秒内；存储失败回非 2xx。
   已持久化但未完成的事件由原定时入口恢复；不得先回复后依赖进程内异步任务保证交付。
4. 三层去重：事件用带 eventType 的上述键（退款失败与成功可同 ID）；现金付款用命名空间+paymentId；
   权益用内部订阅/原付款/发放期/type。重复投递、并发处理、退款先到、返回页竞争都只生效一次。
5. `order.completed` 处理一次性付款；`subscription.payment_succeeded` 证明订阅实付。
   activated/renewed/recovered 只给生命周期证据，不能再发一次积分。
   periodNumber 会包含失败期、可缺失，不是付款成功次数或唯一键。
   按 orderId+periodNumber 关联付款和周期，缺失或不一致时查询权威对象；
   不以时间相近猜一笔账。迟到旧状态不得覆盖已退款/已终止状态。
6. 冻结服务端商品版本、资格、币种、税规则、应付金额；只认权威 chargedAmount。
   未提供实付金额不拿目录价补零或当已付；授权验卡的零金额不授予付费会员。
   税、实付、折扣、手续费、结算净额分别记录，不把供应商净结算当用户付款。
   微信换汇展示不重算 Graylum USD 权益，财务事实各自保留币种。
7. 下单/退款身份在本地先持久化，映射到商户订单/退款引用；外部引用是关联字段，
   **不假定它本身是供应商幂等保证**。SDK/服务端幂等范围、有效期、按引用查询能力须测试验证。
   超时、5xx、回写失败保持原意图和 review_required，先查原交易；不换 key、不换渠道、不盲重试。
8. 回调与消费、退款、年付 cron 按原锁序原子收敛；供应商网络调用不持数据库锁。
   注销主体只记原订单事实和核对事项，不恢复登录/使用权，不自动退现金。

## 7. 退款与凭证

产品依据 D7/D8、Y/AA/AB/AC/V；复用 refundPolicy/refundMoney，不建立第二套政策。

1. 客服工单提交，服务端绑定用户与订单；提交时间判断 168 小时窗口。
   首次会员（所有付款方式）、积分包和升级符合原规则；自动续费不适用普通退款。
   “没用过”是付款后全账户无任何消耗；有在途结算先核对，执行 claim 时再验，不只看页面预览。
2. 管理员预览列原付款、币种、已退、工单、消费证据、手续费允许依据、应退净额和权益处置，
   人工逐笔批准；权限在 API 和事务内检查。不得把前端按钮或 Waffo processing 当批准/完成。
3. 沿用小单位整数计算：可扣费时 fee=floor(basis×6/100)，net=basis−fee；
   法律禁止扣费为零，未知则 review_required，不任意调费率。
   例：已核定应退基数 USD 49.00，扣 2.94、退 46.06。税处理必须有权威证据，不从商品售价猜基数。
   6% 用户手续费与 Waffo 自身服务费分开记，不能二次从用户退款扣除供应商费。
4. claim 同事务固化执行身份、金额、审批、来源隔离/回收意图；网络调用前已可恢复。
   适配器将批准的净额以显示金额字符串和原币种提交到原 paymentId，保存原退款引用。
   提交 API 本身会直接启动处理，因此只能在 Graylum 批准之后调用。
5. processing 只表示在途；以 refund.succeeded 及权威记录核对净额、币种、原付款，
   完成既有原子账务收敛。失败恢复沿原来源及同一意图；结果未知保留核对状态和隔离，
   不换引用重退、不让无限自动重试与消费竞争。
6. 首购月付收回该付款发放的积分；年付 7 天内通常只发首月，回收原来源首月且停止未来 11 期；
   创始立即结束身份但名额不回池；升级扣回该 Gold 的 8,970，恢复 Pro 的原剩余期限；
   包退含其赠送积分，其他来源不动。功能缩减按时间退款保留已发积分并停未来发放；
   无正当理由终止账号还涉及未用已购积分，按已核定例外金额，不用总余额×退款比例。
7. 超 14 天法定/功能缩减等例外、已发生部分退款后的追加需求，Waffo API 可能拒绝：
   转原渠道人工工单并记录供应商处理证据；可执行能力未确认前属于上线阻塞，
   不能用“API 不支持”否定用户既有退款权利。通知晚到超过 14 天的普通合格申请也覆盖此路径。
8. 已拒付订单不再发现金退款；平台外部已发生退款仍必须入账核对，不因缺本地申请忽略。
   Waffo 自带门户如允许退款申请，需确认它不会绕过人工审批自动退现金；
   外部售后入口无法关闭时由 N3 明确运营衔接，Graylum 站内不新增退款按钮。

凭证复用订单展示入口；Stripe 旧单仍取 Stripe，Waffo 单展示原渠道的 MoR 凭证/安全门户。
所有获取先验归属；不把带会话令牌的门户链接持久化到公开日志/PR。
未取得凭证时明确“暂不可用”，不伪造 Graylum 发票，不因默认渠道变动跳错凭证。
