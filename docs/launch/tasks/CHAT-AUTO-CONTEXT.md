# CHAT-AUTO-CONTEXT：自由对话里 Agent 自己查资料库、读发布数据、查对标 — 实施方案

状态：**仅方案**（2026-10-17），还没有写代码。每个实施 PR 开工前按本文核对一次现有代码，有具体矛盾才改方案。

## 0. 为什么做、做到什么

**Owner 原话**（2026-10-17，落地页窗口）：

> 在正式环境的功能里，当用户新开一个窗口自由聊天跟 Agent 对话的时候，Agent 是不去加载他的资料库信息的吗？
> 就跟我们演示的一样，用户就说了一句："那我这周要拍什么？"那我们的 Agent 是不是不去自动加载资料库，不去自动抓数据，
> 然后就想怎么回答就怎么回答，是吗？

Owner 选的选项（原文）："Agent 在自由对话里自己决定检索资料库、读最近发布数据、刷新对标；对话里显示工作状态；
方案里写清调用规则、上限和积分。上线前完成，和落地页演示一致。"

**这条取代的旧规则**（实施时由规划同步 PR 写进 MASTER_PLAN 第 2.1 节，本 PR 不改 MASTER_PLAN）：

- MASTER_PLAN 第 5.3 节"检索（以后再做）：第一版……不做自动检索"、第 0 节"上线后：……资料库检索"、
  第 7.1 节 LIB-EXT 里的"全文检索"——自由对话的资料库自动检索提前到上线前。音频视频、看图、Drive/Notion 导入仍留在 LIB-EXT。
- `docs/launch/LIB_DOCS_PLAN.md` 第 313–314 行"只读本次明确引用的文档、不做自动检索"——改为"引用的文档 + 本回合宿主检索命中的文档"，
  模型仍然不能凭空猜文档编号（第 2.1 节）。

**做到什么**（用户视角）：用户在自由对话里问"那我这周要拍什么？"，Agent 不再空口回答，而是按需要：

1. 读已确认的定位（#830 已有，不变）；
2. 在资料库里查和问题相关的文档并分段读取；
3. 读用户自己最近发布的作品数据（有连接或导入时）；
4. 读定位时建立的对标表，需要最新数据时调用研究工具重新取对标账号的近期作品（扣积分）；
5. 对话里一行一行显示"正在查资料库 / 正在读你最近的作品数据 / 正在取对标账号数据"，完成后变成"读了 3 篇资料""未取到"等结果。

**怎样算做完**：上面 5 条在 staging 真实模型下走通，数字只来自工具结果；没数据时如实说；扣费逐条可见；
删除和注销把这些读取留下的正文清掉；落地页区域 6 的演示和产品实际行为一致（演示复用第 4 节的同一个展示组件）。

**不做什么**：

- 不做向量检索（pgvector / 向量化接口），不引入第二家存储或检索供应商（MASTER_PLAN 第 5.3、5.4 节的成本结论不变）。
- 不改定位导师回合（研究工具、选择卡、对标表照 RT-3b/RT-5/RT-6 现有设计）；不改 @ 引用的规则，只在旁边加"自动检索"。
- 自由对话里不发起对标发现流程（`propose_keywords`、`benchmark_discover`），不写对标表；找新对标仍走定位流程。
- 不改价格、积分公式、会员权益（第 9 节问题 3 除外，需 Owner 定）。不新增收费口径：资料库检索和读自己数据不收工具费，
  只有研究工具按现有 RESEARCH-TOOLS 口径逐条收费。
- 每周自动复盘、复盘报告仍归 PUBLISH-MONITOR PR-6。

### 2.1 资料库自动检索（`library_search`）

**检索办法**：在同一个 Supabase 库里给 `library_document_segments` 的 `title`、`body` 和 `library_documents.filename`
建 `pg_trgm` 三元组 GIN 索引，按"包含查询词"匹配（`ILIKE '%词%'`，走索引）并按命中词数和相似度排序。

- 为什么不用 Postgres 自带全文检索（tsvector）：默认分词不会切中文，中文要装分词扩展，Supabase 上不一定有；三元组按字匹配，中英文都能用，
  `pg_trgm` 是 Supabase 自带扩展。为什么不用向量：要多一家向量化调用和计费，已定上线后再看（MASTER_PLAN 第 5.3 节）。
- 查询：模型给 1–5 个关键词（每个 ≤ 40 字），宿主逐个匹配，最多返回 8 个命中段落，每段摘录前后 300 字以内；
  只查本人、`status='ready'`、`kind='document'` 的文档，和 0244 的权限一致（SECURITY DEFINER + `auth.uid()` 之外再按执行的 actor 校验）。
- 中文单字或两个字的查询三元组索引帮不上（三元组至少 3 个字符），这时只匹配文件名和段标题，不扫正文，避免全表扫描；写进工具描述和测试。
- 先确认 `pg_trgm` 在 staging 和正式库都可用（`list_extensions` 只读核对，正式库需 Owner 授权，放进 REL-1 清单）；不可用时退回"文件名 + 段标题"匹配，
  功能降级但不报错。

**和 @ 引用的关系**：

- @ 引用照 #1022 不变：用户点名的文档整篇可读、优先；@ 引用开关（`library_agent_read_enabled`）关着时，自动检索也不挂（读文档的底层是同一套）。
- 自动检索命中的文档在**搜索那一刻冻结**（`documentId + content_version`）进本次执行的可读清单，和 @ 引用共用 `runtime_library_read` 的读取次数和字节上限
  （每次执行 8 次 / 65536 B），不另开额度。模型只能读"@ 引用 + 本回合搜索命中"的文档，自己编的编号读不到（返回 `LIB_REFERENCE_READ_DENIED`，同 0262）。
- 存哪：沿用 `runtime_library_references`，加一列 `origin`（`reference` / `retrieved`），把 `ordinal` 上限从 5 放到 5 + 本回合检索命中上限（24）；
  不建新表。需要一个新迁移（编号向总控要）。
- 检索命中不出现在输入框的引用条里；对话里的工作状态显示"在资料库里找到 3 篇相关内容"，点开列出文件名（第 4 节）。

**删除和改版**（对齐 #1022）：

- 回答进行中文档被删：和 @ 引用一样，未结束的执行标 `source_deleted` 并取消，前端清掉半截回答并提示（UI-B 已做的 `LIB_SOURCE_DELETED`）。
  自动检索不另开宽松规则：用户删文档就是不想再被用，宁可这条回答重来。
- 回答结束后文档被删：`runtime_library_propagate` 清掉冻结的读取内容和会话历史里的那段文字，已经显示的回答保留（D7）。检索命中行和引用行一样处理。
- 改版（重新识别后 `content_version` 变了）：本回合不作废，读到 `source_changed`，模型如实说"这篇资料刚更新过，请再问一次"（决定 C）。
- 搜索结果里的摘录属于工具结果，存在 `runtime_tool_calls`，已被内容删除和注销覆盖（0201、0150）；`propagate` 要补上"清掉含已删文档摘录的检索结果"，补测试。

### 2.2 读最近发布的数据（`my_posts`）

- **依赖**：PUBLISH-MONITOR PR-3a #1032（0272，读取接口 `publishMonitor.data`、快照、30/90 天窗口）。#1032 合并前这个工具不挂。
  手动导入（#1039）和小红书/抖音本人账号（#1075 PR-4a、PR-4b）合并后，数据自然变多，工具不用改。
- **和 PUBLISH-MONITOR PR-6 的分工**：PR-6 写的是"复盘用的只读数据工具 + 对话复盘 + 每周自动复盘"。为了不做两遍，**本任务只做通用的只读工具 `my_posts`**
  （复用 #1032 的服务端读取函数，不直连表），PR-6 在它上面加复盘逻辑和对齐天数的计算。总控 2026-10-17 已确认这个分工（技术分工，不是产品决定）。
- **读什么**：最近 N 天（默认 14 天，最多到会员的数据窗口：Pro 30、Gold 90）每条作品的平台、发布时间、标题摘录（≤ 120 字）、
  最新一次快照的指标和取数日期，按发布时间倒序，最多 30 条；`missing_fields` 原样带上，不当 0。代码先算好每个平台的中位数，模型只解读。
- **不触发实时刷新**：工具只读已存数据，不调用 Post for Me 或 TikHub；最新程度写在结果里（"数据截至 10-16"）。要刷新由用户在作品数据页点"刷新"（PUBLISH-MONITOR 规则）。
- **没数据时怎么说**（工具返回固定状态码和 `note`，模型照说）：
  - `not_connected`：还没连接账号也没导入 → "我还看不到你发布的作品数据。你可以在『作品数据』里连接账号或导入表格，我就能按真实数据给建议。这次先按你的定位和资料来。"
  - `no_entitlement`：免费用户 → 按第 9 节问题 3 的决定；默认推荐"读自己的数据是 Pro/Gold 权益，这次先按定位和资料回答"，不弹付费墙。
  - `no_recent_posts`：连了但窗口内没作品 → 直说"最近 14 天没有新作品"。
  - `stale`：最近一次快照超过 3 天 → 照常给数据并说明日期。

### 2.3 研究工具放开到自由对话

#### 2.3.1 放开哪些、怎么接

- 放开 `GENERAL_RESEARCH_TOOLS`：`social_account`（查一个账号资料 + 近期作品）、`social_search`（按关键词查近期作品）、`web_search`、`web_fetch`。
  不放开 `propose_keywords`、`benchmark_discover`、`propose_more_candidates`、`benchmark_fetch`（对标流程专用，要选择卡确认）。
- **"刷新对标"在自由对话里的做法**：先用免费的 `my_benchmarks` 读对标表；模型判断需要最新作品时，对表里的账号调用 `social_account` 取近期作品。
  结果**不写回对标表**（对标表只认带授权来源的 `benchmark_fetch`），所以不需要刷新授权（`researchRefreshId`）；要正式刷新对标表仍在定位页点"刷新"。
  `social_account` 只能查：对标表里的账号、或用户在本会话消息里给出主页链接的账号（沿用 `benchmark_fetch` 的 `user_message` 链接解析规则），
  模型自己编的账号返回 `not_confirmed`、不发请求、不收费。`social_search` 的关键词不需要卡片确认（RESEARCH_TOOLS_PLAN 第 2.1 节自由对话设计），
  但工具描述要求只写关键词，不写用户个人信息。
- **代码改动**：`runtimeContext.ts:36, 61-67` 现在要求研究工具只配 `agent-turn-v5-stream` 和导师上下文；改为允许自由对话格式
  （`serial-tools-v6-reasoning`）挂通用研究工具，`researchAdmission.ts` 的准入（总开关、供应商开关、已验证平台、冻结价格、启动门槛、staging 窗口批准）原样复用，
  全有或全无。`admission.ts`、`execute.ts` 已在 500 行附近，先按工程规范第 3 节拆文件再加逻辑，拆分是行为不变的独立提交。

#### 2.3.2 每条回答的上限和积分

- 每条回答最多 **3 次**研究工具调用（导师回合是 1 次，因为对标批量都在一次调用里；自由对话要查几个不同的东西）。
- 子调用总数沿用后台 `maxSubcallsPerRound`（默认 12），按最坏情况折算后先检查（`social_account` = 3、`social_search` = 关键词数、`web_*` = 1），
  放不下返回 `budget_exhausted`、不发请求、不部分扣费；运行单总调用 ≤ 32 不变（12 次子调用 + 自由对话最多 3 次模型调用）。
- **扣费**：每次子调用按 `ceil(q × U × m)` 的口径逐次冻结、逐次结算，记在这条回答的同一运行单上、整单只取整一次（RESEARCH-TOOLS 第 3 节）；
  不事先显示预计消耗（D14），对话里每行显示结算后的"扣 X 积分"，消费记录里能看到每次搜索。
  大概量级（按官方单价估，不是承诺）：TikHub 每次子调用 0.001–0.01 美元 × 6 倍 × 100 ≈ 0.6–6 积分；一条回答用满 12 次子调用最多约 72 积分，另加模型费。
- **余额不足**：依赖 #1062。合并后子调用余额不足时整条回答暂停，用户充值后从断点继续、不重复收费；#1062 合并前不打开自由对话研究工具（否则是悄悄跳过）。
- **失败**：确认失败返回 `unavailable` 不换供应商；结果未知不重发、按 0 结算（RESEARCH-TOOLS 必测 2、12），工具状态显示"未取到"或"待核"。

## 4. 对话里的工作状态（纯展示组件）

- 新组件 `apps/web/src/components/chat-display/agent-work-status.tsx`：输入一组 `WorkItem { id, kind, state, label, detail?, credits? }`，
  `kind` = `library_search` / `library_read` / `positioning` / `my_posts` / `my_benchmarks` / `research`，`state` = `running` / `done` / `missing` / `pending`。
  只负责展示，不请求数据，和 #1063 的 chat-display 结构一致；样例数据放 `chat-display/fixtures/work-status.ts`，落地页区域 6 用同一份样例渲染。
- 文案（用户看的，不出现供应商名和美元）：进行中"正在查资料库…""正在读你最近的作品数据…""正在取对标账号的最新作品…"；
  完成后"在资料库里找到 3 篇相关内容""读了你最近 14 天的 6 条作品""未取到：还没有连接账号""扣 4 积分"。
- 研究工具这一行直接复用 `ResearchCallList` 的 `describeCall`（RT-5 已有的映射），不重写；新组件把它当作 `research` 类条目的展示。
- 数据来源：后端给非研究工具也发流事件。在 `AgentTurnEvent` 里加 `agent_tool` 事件（`callId`、`tool`、`state`、结果摘要，如命中篇数、作品条数、文件名列表），
