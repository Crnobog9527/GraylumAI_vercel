## 1. 产品边界与来源

飞书、Notion、Slack 等 MCP/连接器能力与 Post for Me 社媒发布/数据同步可以并存，不构成二选一，也不人为设定“先完成飞书才能接 Post for Me”的业务依赖。既有连接器验收目标保留；本次不擅自重排 Launch 图。共同依赖是已有 Runtime 的工具准入、身份、授权、预算与恢复能力，而不是某一家连接器先上线。

产品目标是同一个增长教练使用多种工具，不是每种工具再建一个 Agent。已有兼容 MCP 服务优先复用标准客户端与实际公开能力；只有协议、鉴权或业务语义不兼容的部分才做适配。MCP 可用不等于用户已授权、任意工具都允许执行或定时数据采集已经完成。

## 3. 管理职责和配置生效规则

### 3.1 管理员、用户、Agent 各管什么

- 管理员：可提供的服务/工具、已验证能力、套餐权益、角色绑定、平台容量、安全上限、启停与异常处理；不能代替用户授予其社媒或文档访问权限。
- 用户：连接自己的账号，指定读写目标，选择追踪范围、频率、月预算及自动/按需模式，确认对外发布或扩大授权。连接器仍在输入框抽屉/弹窗内管理，不新增用户顶层导航。
- Agent：根据任务提出所需工具和数据范围，解释缺失与结果；不决定供应商限流、不自定扣费、不取得管理员权限。
- 服务器：从可信身份推导目标连接和作用域，校验有效权限/能力/预算，冻结请求，排队执行并持久化结果。后台任务不需要唤醒大模型才能运行。

### 3.2 最小后台布局

保留现有后台和鉴权。只为目前缺失的服务配置提出一个 `/admin/integrations` 入口，内部用服务目录、能力/默认策略、连接健康三个视图管理 MCP 和 API 接入；不为每个平台另建一套后台。

| 现有或拟新增入口 | 要能控制/看到什么 | 实际消费点与验收重点 |
| --- | --- | --- |
| `/admin/models` + `/admin/settings` | 模型目录；普通对话候选、独立整理/提取、Gold 参与/综合角色与预算；Skill 模型在模块内指定 | 既有 Runtime admission/execution 从有效角色解析；不可用模型明确拒绝，普通选择不覆盖 Skill/整理角色；新设置不能绕过未开放协议 |
| `/admin/prompts` + `/admin/skills` | Skill 包/修订、步骤与逐题字段、资料映射、选题资源、发布/撤销状态 | 沿用现有 publication/loader/workflow/OPC 链；发布前验证必需字段与资源；既有草稿继续原 revision，不静默迁移或丢失字段 |
| 拟新增 `/admin/integrations` | 服务启停、MCP/API 类型、能力清单、读/写分级、已验证认证方式、凭据引用及状态、供应商限额、社媒默认同步策略 | 既有受控工具边界 + 后续社媒适配器/worker；所有入口同一准入；MCP 发现成功不授予读写全部账号权限 |
| `/admin/packages` | 套餐 AI/集成权益、单位权重、周期、额外额度商品、渠道商品映射和可购买状态 | 目录、订单履约、权益发放、任务预留/结算全部消费同一有效版本；不能只改前端功能文案 |
| `/admin/settings` 的输入能力分组 | 输入长度、附件类型/大小/数量、引用类型/数量、可用功能与说明 | #424 共用输入组件 + 各宿主提交 + 服务端解析/权限限制；返回服务端能力交集。设置开启但链路未实现时显示不可用及原因 |
| `/admin/finance` + `/admin/transactions` | Waffo/Stripe 原渠道订单、环境、订阅/退款/凭证状态，停止新销售与历史服务状态 | 公共支付/履约边界 + 原渠道适配器；不能通过改默认渠道改写历史归属，不能用通用“重试”再次收费 |
| `/admin/costs` | 用户额度消耗、真实供应商调用成本、待核实成本、社媒供应商月费/分摊、发布目的地量/同步页数 | BILL2/原流水/新集成计量的只读聚合；分摊不可冒充供应商单次回执，调用与运行单不得双计 |
| `/admin/diagnostics` | 按连接/任务/运行单查看排队、最近成功采样、429、授权失效、部分完成、unknown、费用状态 | 扩展现有诊断；受控暂停/恢复/核对作用于原任务。只读检查、会产生供应商请求的测试、外部写操作清楚分开 |
| `/admin/users` | 用户套餐/两类额度的只读概况、连接/任务状态及支持入口 | 复用现有用户管理；额度更正需原账务身份和原因，不能直接改余额或展示用户 OAuth 明文 |

这里的字段分组是工程设计，不声明对应数据库列、API 名称或页面已经存在。无需将所有可想象参数都暴露给 Owner；普通页面给出安全默认和明确状态，容量/批量/重试等放高级设置。

### 3.3 同一份有效配置，不做“假开关”

复用现有 settings/adminProcedure、模型和 Skill 配置基础；高风险配置使用类型校验、作用域和版本化写入，不把嵌套权限/密钥塞进当前通用标量设置。公开设置继续白名单投影，不向客户端返回供应商总密钥、完整连接配置或其他用户标识。

配置按实际需求分为：系统/环境与供应商账户上限、套餐权益版本、用户授权与预算、单次执行快照。有效权限取交集；供应商预算还要跨用户共享，不是给每个用户复制一份总额度。

保存须校验字段关系及模型/工具可用性，按预期版本更新，回读保存结果和实际生效范围。避免全表默认值覆盖其他管理员改动；失效或不存在的配置不静默当成功。执行端必须消费同一版本，缓存要有明确失效机制。

商业定价、模型、范围等变更作用于后续新请求/适用的新权益周期；已接受请求按冻结意图和报价恢复，不因刷新页面重新定价。紧急停用、撤权、安全拒绝在每次实际派发前重新检查，但不得篡改已发生调用、伪造失败退款或改写历史成本。缩紧上限不能静默突破原授权；排队超期需重新确认或释放可证明未执行部分。

## 4. Agent/MCP 与社媒服务如何共存

沿用统一 Runtime 的工具注册/执行机制。服务目录记录真实 transport、认证方式、允许的工具/schema、读写能力及费用类型。兼容服务优先使用 SDK，不逐家重写通用发现、调用和授权管理；同时不把“能列出工具”视为所有业务语义已验证。

现有 AgentKey 实现是特定契约，不可直接改地址就宣称支持飞书等任意服务。新增 MCP 接入须完成用户连接绑定、目标权限、超时/响应上限、敏感结果处理和撤权恢复；来源内容不能升级为系统指令，工具仅按需加载。HTTP/OAuth 和本地进程型服务按实际部署方式分别验证，不将开发机配置当托管网站能力。

Post for Me 官方目前也提供 MCP，但其指南描述的是本地运行、API key 和 code-mode 工具，不能据此承诺一个已可多租户托管的远程 OAuth 连接器。首轮社媒定时业务优先走可计量的固定服务端 API/SDK 适配；Agent 的相关工具也调用这个受控服务。日后使用 MCP 时仍不得绕过相同的权限、预算、队列和结果记录。工具 transport 不应成为两套业务权限。

尤其不能把全项目 Post for Me API key 对应的任意 SDK 执行权限交给最终用户 Agent。任务中的 account/post ID 必须映射到当前用户已授权连接；写操作冻结内容、目标、时间和确认身份。超时后先核对原发布结果，不自动换账号、换供应商或重发。飞书写入继续遵循其已确认目标和幂等语义，两者不互相授权。

## 5. 已批准的社媒同步规则与后台控制

### 5.1 采集与体验

Post for Me 负责平台接入、发布和读取；Graylum 负责选取范围、定时任务、观测历史、趋势和复盘。账号授权、读取指标权限、允许发布及日常自动同步同意分别表达；账号已连接不等于用户同意每种操作。

用户可选择账号/平台、作品发布时间范围、指定作品、自动或按需模式、频率与月预算。发布时间范围、统计覆盖期、实际采样时间分开保存。按发布时间筛选可由本地作品索引完成；只在平台真实支持的范围内导入/按 ID 重读，不承诺无限历史或统一日期查询参数。

初始推荐：近期 30 天作品每日采样；用户长期关注的老作品继续追踪；其他历史作品按需。30 天和频率为可调默认，不是永久硬编码或隐式减少用户已选范围。首次历史导入显示预估、范围/页数上限和进度，不能无预算扫描全部历史。

登录只检查新鲜度。写内容而不需新指标时不抓；复盘某作品时只更新必要范围。已有自动同意和预算时不反复询问；没有同意、扩大范围或增加预算时由服务器生成确定性预估并请求确认。已有数据先可见，更新不阻塞无关工作。

后台自动同步独立于用户在线和模型调用。模式为“小范围持续采样 + 任务需要时优先更新”，不是完全依赖登录采集，也不是每天完整刷新所有历史作品。

### 5.2 出站容量与公平调度

所有登录、页面、Agent、定时同步、历史导入以及适用的发布/账号管理调用共用供应商容量管理。进程内计数或现有按用户/IP 的入口限流不能替代它。

| 控制组 | 第一版含义 |
| --- | --- |
| 供应商硬上限 | 使用经确认的限流作用域；尚未确认时，Graylum 对该供应商的相关调用保守共用总桶，不靠多 API key 规避限制 |
| 初始运行配置 | 官网观测为 5 次/秒及 40 次/分钟；建议内部连续 1 秒最多 4 次、连续 60 秒最多 36 次，后台先不超过 28 次/分钟；均是可调参数，不是实测容量或响应 SLA |
| 并发与速率 | 两个独立限制；允许跨账号并行等待响应，但每个真实请求先通过秒/分钟预算；不能用并发数代替请求速率 |
| 优先级 | 用户当前发布/授权、当前复盘、定期采样、历史导入依次优先；等待老化与后台执行机会防止长期饿死；不可突破总上限 |
| 公平性 | 按用户/账号轮转分页或作品批次；同一游标链顺序推进，不让大账号一次占完队列 |
| 错峰 | 为账号分配相对稳定时段并小幅错峰；排队积压可见，不承诺容量不足时仍严格按点完成 |
| 去重 | 同用户/连接/授权范围、对象集合与新鲜度要求兼容的任务共用结果；派发前再次检查缓存；不跨租户共享私有指标 |
| 恢复 | 持久任务/游标/原请求身份、可恢复执行占用与幂等保存；重启不丢任务、不重复扣费；限流状态不可用时排队而非放开出站 |
| 429/错误 | 遵守作用域内 `Retry-After`，必要时带抖动退避；有尝试/时间上限，重试重新经过限流；发布等未知外部写结果先核对，不能套读取重试 |

新作品发现与已知作品指标更新分开。支持按 ID 的平台优先批量更新目标作品；一次 Feed 请求可携带指标时不拆成额外重复抓取。发布结果优先利用适用 Webhook；Webhook 来源验证、事件去重和关联校验必须完成，不假设所有平台会推送播放量变化。

### 5.3 历史真实性

保存平台/账号/作品、指标名称与语义、来源、统计截止时间（有则记录）、采样时间、完整性和缺失原因。只获得当前累计值时不能反推接入前每日增长；两次采样差不是当然的自然日指标，均值/比例也不能直接相减当增长量。

单个平台成功不代表全任务成功。缺测不写 0，旧数据不标“刚刚更新”；用户和 Agent 都能知道最后成功时间与覆盖范围。撤权、主动删除及平台/法律要求的生命周期单独落实，不因“长期教练记忆”无限保留不允许的数据。

## 6. AI 与集成权益：复用原钱路而非另造钱包

前台区分 AI 与集成用量，后台区分业务权益计量和外部真实成本。保留现有唯一资金/订单/余额/流水及 BILL2 安全语义；新增集成计数/权益余额不是第二套现金钱包、独立充值履约或供应商账本。

| 项目 | 记录与控制规则 |
| --- | --- |
| 套餐权益 | 结构化记录每周期集成额度、操作单位/权重、功能可用性和用户预算上限；未定义的套餐数额、售价、结转/到期规则保持待决定，不沿用示例成为售卖承诺 |
| 额外购买 | 复用公共商品/订单/履约及原渠道映射，冻结权益版本与发放来源；付款重放不能重复发额度。不得为了持续同步默认替用户付费购买或开自动扣款 |
| 发布计量 | 单独记录每个目标账号的发布结果和供应商计量来源；多平台发布不是天然一次采购用量；具体合同计数仍需确认 |
| 数据同步 | 记录任务、实际请求、有效结果/页、作品观测数及缓存命中；可按经确定的操作权重消耗集成额度，但不伪称供应商按同样次数收费 |
| 外部搜索 | 记录具体供应商/工具及实际单位，不与不同成本的 Feed 读取全部硬编码为相同价格 |
| 供应商成本 | 官方实际成本、未知成本、套餐固定费、内部分摊和估计分列；Post for Me 套餐分摊不能作为 BILL2 的单次官方回执。原 provider-authoritative 模型结算不变 |
| 自动/按需 | 两种方式均受同一额度与授权预算约束；缓存展示和 Agent 读取已有快照不再次购买或扣同步额度 |
| 预留与结果 | 任务准入先原子预留上限；按预先说明的可用交付单元处理结算，未执行部分可证明后释放；内部重试、任务恢复不重复向用户收费 |
| 部分/未知 | 分页任务的独立交付单位、部分完成展示和结算须在报价中明确，不偷偷改变既有“故障未交付可用结果全退”规则；未知派发不能直接当失败/零成本，保留原账务身份核对 |
| 额度耗尽 | 暂停新增外部同步，保留允许查看的历史及最后更新时间；购买/新周期后按原意图和当前授权恢复，不无限透支 |

自动同步不是聊天回合，不伪造 Session 或选题来挂账。实施时需将“用户所属账号/周期任务”的作用域明确接入现有身份与账务校验；当前源码不证明可以零改动沿用所有 BILL2 接口。兼容扩展不能重发历史权益、清空在途预留或建立旁路扣费。

管理后台的调价只影响适用的新请求/周期，旧报价、购买来源和已发生回执不可被修改。撤销/退款后的权益与在途预留保持原来源保护，不能在迟到结果或释放时恢复已退款额度。

## 7. #423 支付规划的后台接线

在现有套餐/财务/流水页扩展，不另建支付后台。现有 Stripe price 字段先保持历史兼容；新商品使用内部稳定商品身份，渠道映射按支付商、商户、测试/正式环境、对象类型和版本隔离。Waffo ID 不能填入 Stripe 专属字段。

后台区分“目录已配置”“测试验证通过”“允许新销售”“停止新销售但继续处理历史业务”。默认新销售渠道设置必须被公共 checkout 准入消费；渠道缺少有效映射、能力或启用条件时给出不可购买原因，不悄悄换一家收费。

订单、订阅、凭证、退款与未决交易始终按原渠道显示和处理。停止 Waffo 新销售不能顺便停其旧订单通知、退款或对账；保留 Stripe 历史服务不等于允许自动以 Stripe 直接收新单。

退款/取消等按钮读取具体原渠道支持范围与当前状态，区分查询、取消订阅、退款、站内权益处理及结果未知。金额/税额/支付额/费用/净额分列，未知交易先核对，不盲目重试或自动迁移订阅。全部沿用 #423 的共同履约、来源幂等、年付按月发放、重复购买防护和历史兼容要求；本规格不是启用渠道的批准。

## 8. #422/#424、模型与旧后台的接线

### 8.1 Skill、模型角色与 Gold

Skill 目录、发布/撤销、修订和模块展示沿用现有管理页面。补齐 #422 已能保存但不能充分编辑的字段，提交前检查 ID 唯一/稳定、资源存在、字段角色和账号资料映射；普通模块编辑不得删除未改动的 `information`/`planResources`。

把“配置资料”“候选修订”“已发布修订”和“当前草稿实际使用的修订”展示清楚。模型角色绑定不得与 Skill 版本被 UI 默默替换；旧草稿和未决请求仍能按原身份恢复。

普通对话由用户从允许目录选择；Skill 对话由管理员在模块中指定；整理和信息提取分别有明确角色与预算。复用已存在的整理模型设置，不把独立提取偷偷等同于导师输出补丁。若角色在某宿主尚未接通，显示未实现/不可用，不能通过后台选择一个模型就宣称它被调用。

Gold 的参与/综合模型、数量和预算纳入同一角色配置与原账务，不在用户端任意组合外部执行权限；仍保留原多模型隔离、全部成本归集及真实小额对账等验收要求。此处只补管理入口，不启动 Gold。

### 8.2 输入框及资料能力

#424 的 A 共用编辑器、B 真实引用、C 附件链路分别配置能力；类型、大小、数量、文本长度和实际模型输入预算由前后端共同执行。服务端能力接口返回“已实现且对该用户/宿主可用”的交集，而不是把所有计划按钮都展示为可运行。

草稿只是输入状态；执行时绑定原 Session/作用域、Skill revision、引用版本与已就绪附件。引用跨项目须明确授权而不改变工作归属。权限不足、已撤回、未就绪、无法解析的资料给出可见失败，不能只把文件名塞进提示词冒充读取。

配置收紧后，保留用户原草稿并说明限制，不静默截断或删除；旧已发请求仍按冻结内容恢复。晚到结果不清空新草稿。输入 UI、模型、Skill、连接器清单共享服务端有效能力，不各做一份缓存目录。

### 8.3 旧控制项和历史生命周期

保留现有仍被旧入口使用的必要兼容，不提前大面积删代码。迁移新入口时逐项标明哪些设置只控制旧聊天，哪些已经接到新 Runtime；确认新路径后再移除旧主力/辅助路由、重复搜索判断及失效提示字段，不能让两套设置长期争夺同一行为。

按会员等级删除历史的控制项、执行服务、API 与 cron 必须随已批准的历史策略一同退役，不能只藏按钮。社媒历史的合法保留/撤权处理另按来源规则执行，不复用会员保留天数。技术诊断清理、临时附件生命周期与用户成果历史不得混用。

## 9. 生效、运营和故障验收

沿用现有测试体系、Admin Settings Effect Matrix 和 `AGENTS.md` 的适用验证/独立审查要求。以下是相关功能的验收内容，不是新增审批流程或另一套审计台账：

1. 管理员改一项设置，保存、回读、服务端生效、用户端体现都可证明；普通用户直接调用管理 API 被拒绝，公开配置不含密钥/私有连接。并发编辑不覆盖其他人的新版本。
2. 相同模型/Skill/工具角色在 UI 与实际执行一致；未支持的协议和宿主限制不能靠开关绕过。Skill 修改保留旧版本、逐题字段及恢复身份。
3. MCP/社媒连接和对象均属于当前用户；跨用户 ID、撤权、额外权限、失效 schema 被拒绝。用户未同意发布时不发；未知发布结果不重复写。
4. 多进程/多用户总请求同时满足供应商秒/分钟限额；后台导入不阻塞小任务，交互峰值也不永久饿死每日采样；429、重启、重复点击和游标恢复不重复扣费。
5. 修改预算/频率后新任务应用新规则，原在途身份和账务不变；额度不足停止派发；月度补充/购买/退款重复事件均幂等。
6. 缓存复用、部分成功、无指标、累计值修订、数据延迟和缺测都如实呈现；成本未知不进“0 成本”，固定月费不与分摊重复相加。
7. 输入框按 #424 保留 IME、引用、附件、权限拒绝、真实读取、草稿/旧请求恢复；后台改变限制不破坏旧草稿和已执行请求。
8. 支付渠道停接新单后仍处理原历史订单/续费/退款/未决状态；商品映射、金额、权益版本和购买可用性一致，不跨渠道重试收费。
9. 诊断页面能沿原 connection/job/execution/run/call/订单身份定位失败；只读健康检查不暗中发模型请求、发布内容或退款。任何有外部效果的测试明确环境、目标和预算。
10. 原工作台纵向链路、唯一账务路径、历史恢复和仍适用的 Master Plan 验收继续保留；一页后台能保存不是整项功能完成。
