# V3 OPC 增长 Agent：产品链路、Runtime、计费与 UI 规格

状态：Owner 于 2026-09-13 批准的详细产品规格；2026-09-19 追加批准“SDK 原生会话管理 + 全入口权威经营上下文”方向（见文末该日条目，已并入第 4、5、6 节）。本文与 [Master Plan v10.2 OPC 修订](../Graylum_Master_Plan_v10.2_OPC_Growth_Agent_Amendment.md) 配套，补充既有 [V3 标准 Skill 规格](V3-standard-skills.md)。若旧规格关于全局聊天入口、独立工作台、项目边界、右侧步骤栏、连接器导航、上下文、智能路由、历史自动清理或多模型计费的描述与本文冲突，以本文为准；不冲突的 Skill 包、成果、版本、证据、权限和验证要求继续有效。

本文不证明功能已经实现，也不授权代码、数据库、供应商、合并或生产操作。

## 1. 产品原则

Graylum 的核心价值不是提供另一个通用聊天框，而是帮助 OPC 用户完成可持续的社交媒体增长工作：

1. 认识用户和账号；
2. 形成清晰定位与经营资料；
3. 生成可执行内容计划；
4. 围绕一个选题完成研究、脚本、标题、封面等成果；
5. 将成果保存、复用和同步到用户工作系统；
6. 根据真实发布结果迭代下一轮。

用户必须能清楚知道当前正在经营哪个账号、完成哪个选题。系统不以“容忍一个聊天窗口无限混入七八个任务”为主要设计目标，而是通过项目与工作项入口主动引导正确使用。

产品管理负担应尽量自动化，但工作归属、外部写操作、成本和影响范围必须可理解、可纠正。

## 2. 核心对象与关系

### 2.1 用户可见对象

| 对象 | 社交媒体场景 | 非社交媒体场景 |
| --- | --- | --- |
| 项目 | 一个具体平台上的一个运营账号 | 一个非社媒工作集合 |
| 工作项 | 选题 | 工作项 |
| Agent 工作空间 | 围绕该选题研究、创作和修改 | 围绕该任务工作 |
| 成果 | 研究、脚本、标题、封面、报告等 | 合同、方案、文档等 |

用户可见层不使用“conversation”作为主要业务名称。聊天只是工作项内部的 Agent 交互方式。

### 2.2 底层关系

```text
User
├── Positioning draft / 定位草稿（账号项目创建前）
│   ├── Independent Agent SDK Session
│   ├── Step artifacts, confirmations and positioning versions
│   ├── Billing runs and provider references
│   └── Confirmed handoff references to account projects
├── Social account project
│   ├── Confirmed positioning versions
│   ├── Account operating profile
│   ├── Work item / topic A
│   │   ├── Agent SDK Session
│   │   ├── Skill executions
│   │   ├── Artifacts and versions
│   │   └── Source / connector references
│   └── Work item / topic B
└── Non-social project
    └── Work item
        ├── Agent SDK Session
        └── Artifacts
```

一个工作项只能属于一个项目。每次执行必须绑定一个由服务端校验的明确作用域、稳定 Session、适用的 Skill revision、模型角色和计费运行单：项目内工作使用 `work_item` 作用域，首次定位使用下述 `positioning_draft` 作用域。迟到结果不得因为用户当前打开了其他草稿或工作项而改变归属。

### 2.3 首次定位的前置归属

定位草稿是同一用户下面的前置业务对象，不是占位账号项目，也不是另一套 Runtime、Session 或账务系统。以下名称表示归属契约，不强制新增同名表；实现应优先复用现有草稿、成果、Session 和调用身份机制。

| 执行作用域 | 必须绑定 | 项目与工作项规则 |
| --- | --- | --- |
| `positioning_draft` | 已认证 user ID、稳定 positioning draft ID、该草稿独立 session ID | 首次定位不要求 project/work item；只能执行该定位流程及其允许的研究、整理与计划生成 |
| `work_item` | 已认证 user ID、project ID、work item ID、该工作项独立 session ID | 四者的归属关系必须同时有效；不得因项目缺失而自动降级为定位草稿 |

用户从首页开始导师问答或手动填写时，服务端在第一轮模型调用和首次资料保存前，幂等建立用户所属的定位草稿及 Session 绑定，固定本轮 Skill revision。`/positioning/[runId]` 中的 `runId` 定位这个稳定草稿，不是某次计费运行单或供应商 generation ID。打开入口、重复提交同一开始请求、刷新和继续均读取同一草稿；明确“新建定位”才产生新的草稿身份。草稿建立失败时不发起模型调用或预扣。

问答、步骤状态、AI 候选、用户工作稿、确认快照、证据和六步正式版本从产生起都归属该草稿及其用户，不能暂存在无归属的全局聊天中。读取、编辑和恢复均校验所有权；未登录或其他用户不得凭 draft/session ID 访问。手动填写同样持久化，但普通保存不触发模型调用或模型费用。

每次收费操作在调用前绑定自己的 request ID、计费运行单、草稿作用域和 Session；一次六步旅程可包含多张运行单，不要求等全部六步完成才结算。已有答复、已结算费用和 `cost_pending/unknown` 调用均按原身份恢复；刷新、重新登录或返回草稿不重发模型请求、不重新预扣。

定位中途退出不创建账号项目，也不丢弃草稿。已有账号的定位补全或修订仍使用同一定位草稿机制，额外记录经授权的目标账号项目引用；这个引用不替代草稿归属、不更改当前正式定位，采用时仍须显式确认。该前置作用域不允许任意无定位社媒创作绕过项目准入。后续承接规则见第 5 节，取消会员自动清理不取消用户主动删除及相关隐私边界。

## 3. 六步定位 Skill 的产品化机制

### 3.1 业务内容来源

六步定位页面不得在前端源码中重新设计业务问题。以下内容均来自当前发布的六步定位 Skill revision：

- 步骤顺序与名称；
- 需要收集的信息；
- 必需与可选信息；
- 提问方向与解释素材；
- 步骤依赖；
- 完成条件；
- 成果约束；
- 研究或证据要求；
- 报告章节映射；
- 进入账号经营资料的映射。

当前 Skill 的六个业务阶段仍是需求确认、对标分析、账号定位、内容规划、运营建议和商业变现。这里只作为当前 revision 的例子，平台核心不得依赖固定六个字段或固定问题文案。

### 3.2 旧 Skill 指令的拆分

已有 Skill 中如果同时包含业务方法和旧聊天界面控制指令，例如一次展示多题、要求回复“继续”、使用旧斜杠命令或禁止自适应追问，应发布新的产品化 revision：

- 保留业务信息目标、分析方法、步骤顺序和交付物；
- 移除只适用于旧聊天界面的翻页和命令协议；
- 将需要收集的信息和完成条件表达为宿主可校验配置；
- 具体问法允许导师根据用户回答自适应，但不得改变业务目标或私自新增一套定位方法。

### 3.3 导师式问答状态机

每一步按以下机制运行：

```text
载入 Skill 步骤要求
→ 读取已确认资料和本步已知信息
→ 找出最高价值缺口
→ 一次提出一个主要问题
→ 根据回答归纳、澄清、举例或追问
→ 将有依据的归纳以待核对状态填入本步结构化表单
→ 用户直接核对、修改或继续对话
→ 满足完成条件后确认本步表单
→ 进入下一步
```

信息项至少支持：

- `unknown`：尚未知；
- `unclear`：已回答但不足以形成可靠结论；
- `provisional`：可形成暂定判断；
- `confirmed`：用户已确认；
- `deferred`：用户明确暂时不知道并接受局限。

模型不能仅凭“我还想了解更多”无限追问。每一步由 Skill 声明必要信息和停止条件；必需信息已确认或明确延期后，右侧结构化表单就是本步可编辑成果，不再要求用户触发第二次整理或抄写到另一份工作稿。

### 3.4 苏格拉底式提问要求

导师优先从用户能够回答的具体经历、真实例子和选择开始，不先要求小白解释抽象术语。例如，Skill 需要“差异化价值”时，可先问用户最近被谁找来解决过什么问题，再逐步归纳，而不是直接要求用户给出“核心竞争力”。

每轮应做到：

- 先理解和复述关键事实；
- 只提出一个主要问题，必要时附少量示例；
- 解释该问题为什么影响定位；
- 对矛盾回答进行澄清；
- 区分事实、愿望、假设和待验证判断；
- 不把模型推测自动写成用户事实。

### 3.5 成果与版本

每一步对用户保持一个结构化成果表单：用户可直接填写，导师也可依据对话把建议写成 `provisional` 或 `unclear`，但不得自动标记为用户已确认。表单普通编辑自动保存并显示正在保存、已保存、失败与重试状态；中文输入法组合阶段不得提前提交。

用户点击确认本步骤时，系统把当前表单按 Skill 字段顺序冻结为不可变确认快照。后台仍可保留模型回复、来源、历史候选和版本证据用于追溯，但不得让迟到候选覆盖当前表单，也不得在用户界面要求再生成或编辑一份重复成果。修改上游确认时创建新版本，保留旧快照，并按 Skill 声明的依赖仅标记受影响步骤待复核。六步正式定位版本在定位草稿作用域内、且仅在该 revision 要求的确认条件全部满足后原子生成，不以已有账号项目为前提。成为某个账号项目的当前正式定位还须完成第 5 节的明确采用。

### 3.6 成熟账号手动入口

成熟用户可选择“我已有明确定位”，按当前 Skill revision 的标准信息结构填写、导入或粘贴资料。系统仍需：

- 逐项标记来源和确认状态；
- 提醒关键缺口或冲突；
- 生成同样的六步成果版本；
- 生成同样的账号经营资料；
- 不因入口不同建立第二套项目或报告结构。

无论从导师入口还是手动入口进入，步骤页都保持同一结构：上方为步骤导航，下方左侧为贯穿全部步骤的同一个导师 Session、同一条完整对话，右侧为当前步骤表单。切换步骤只更换表单和导师当前关注的信息目标，不过滤、重置或另建聊天记录；后续问题继续使用前面全部可用历史。导师主动从当前最高价值缺口开始提问，用户不需要先点击“请导师帮助”。手动入口只表示用户可能已有较完整材料，不关闭导师对话，也不改变自动保存与确认机制。

## 4. 账号经营资料与项目公共记忆

### 4.1 账号经营资料

六步正式版本完成后，由 Skill 声明的映射生成精简账号经营资料。当前可能涵盖目标、受众、价值、差异化、内容方向、表达风格、资源限制、运营规则和变现路径，但具体字段不永久写死。

每个资料字段必须保存：

- 来源步骤和确认版本；
- 是事实、用户决定、暂定假设还是未知；
- 更新时间；
- 当前是否有效；
- 被哪一版资料取代。

完整六步报告用于查看和导出；账号经营资料用于后续 Agent 工作；原确认成果用于追溯依据。三者不得互相冒充。

### 4.2 项目公共记忆

同项目工作项共享的是精炼、可追踪的项目资料，不是所有聊天全文。默认可用内容：

- 当前正式账号经营资料；
- 项目级用户确认偏好；
- 项目重要决定与限制；
- 成果索引；
- 管理员整理模型生成的有预算摘要。

其他工作项的完整正文只有在当前任务需要时通过工具读取。摘要更新应由明确事件触发，例如确认定位、完成成果或纠正偏好，不要求每条消息额外调用整理模型。

### 4.3 跨项目引用

跨项目不默认共享记忆。用户可在当前工作项中明确指定另一个项目、选题、报告或成果，Agent 通过受控读取工具获取准确版本。工具必须校验用户归属和权限，不允许模型凭任意 ID 浏览其他项目。

### 4.4 用户个人素材库入口（2026-09-19 批准方向）

用户需要一个属于自己的素材与成果入口，无需重做定位即可回看：

- 定位历史与版本 → 平台 → 具体账号 → 选题 → 完整成果 / 工作 Session。

该入口只读取已有的、归属明确的业务对象及其投影（`opc.list` / `opc.read`、已确认版本、账号经营资料、选题与工作项、工作 Session 结果），不新建并行的内容数据库、向量库或文件上传/RAG 平台。列表、详情与按 ID 直达都必须按 actor 归属与来源撤回状态校验，用户 A 不得读到用户 B 的内容。长文成果以已保存、可版本化的成果形式呈现，不得塞进 400 字信息字段或计划 `brief`。

## 5. 第一周选题与项目创建

### 5.1 草稿内计划与确认

六步正式版本完成后，系统先询问用户是否生成第一周选题，再进入正常的 Agent 工作聊天。生成计划需要用户明确同意，确认定位本身不等于同意生成：

1. 最后一道定位确认成功后，弹出对话框询问是否生成第一周选题；选“稍后”不生成、不花费、不创建项目；
2. 用户明确同意后，进入正常的 Agent 工作聊天，按授权的不可变定位版本引用加载已确认定位，并调用相应选题 Skill；
3. 生成走一条可恢复的选题请求身份（原始 request/execution/billing）；用户在此工作空间中核对、修改并采纳选题；
4. 采纳后按第 5.2 节幂等创建或采用项目与工作项；
5. 选题确认与“生成对应的完整文章/口播稿”是两个可见的独立动作，不得在一次定位完成时静默生成七篇脚本或产生未确认费用；
6. 日期在 UI 中作为周/日分组，不实现通用文件系统；不得创建外部账号或对外发布。

草稿内的计划编辑器不再是定位完成后的默认承载界面；已存在的历史计划信封与已付费执行仍必须可恢复，不因界面变化而丢失。

同一平台可存在多个账号项目。项目身份必须包含平台与具体账号，不能只以平台名作为唯一边界。

### 5.2 确认后的幂等承接

确认操作冻结草稿 ID、用户已确认的定位版本、计划版本及具体平台账号集合，并绑定一个稳定确认请求 ID。服务端校验所有权、版本仍有效以及目标账号归属；同一确认 ID 的重复请求返回原项目/工作项映射，不能换一份负载继续执行。页面展示后资料被修改时，旧确认不得静默采用新内容，应保留编辑并要求确认当前版本。

在同一数据库事务内完成账号项目的创建或明确采用、定位来源引用、账号专属经营资料关联、计划工作项和独立 Session 绑定，以及草稿到目标的承接映射。项目身份以用户、平台和具体账号为界，数据库唯一约束防止并发创建重复账号项目；确认版本下的每个计划项也只承接一次。事务不包含模型或连接器调用；生成计划已经完成的费用不在这里重算。

多平台承接只让用户本次确认的账号项目引用同一个不可变定位来源版本及各自适用的资料，不复制原定位 Session、问答、成果版本或计费运行单。每个新选题拥有新的独立 Session，初始输入来自对应账号资料和选题简报，不注入整段定位聊天。各项目后续定位修订、记忆和当前版本指针独立，不因共享初始来源而自动互相同步；后续跨项目读取仍遵守第 4.3 节。

若目标账号项目已存在，不能重复创建或静默覆盖其正式定位；须明确展示采用到该现有项目的影响，确认预期当前版本后更新，冲突时保留原项目。已有工作项和成果不自动改用新版本。增加账号、改计划或再次采用均须形成新的明确确认，不能改写已经成功的承接记录。

承接只新增来源和目标关联：定位草稿原 user/draft/session/request/generation 身份及已结算、待核实费用保持不变，不能迁移成多个项目各自的消费。确认成功后原定位记录仍能按原身份找回；响应丢失先查询原确认结果，再安全重试数据库操作，不重跑模型、不重复创建或扣费。事务失败不暴露半完成项目，原草稿及成果仍可恢复。

### 5.3 社媒项目准入

社交媒体项目在没有可用定位版本时只允许进入定位补全、资料查看和项目设置，不允许绕过服务端校验直接进行正式内容生成。已有正式版本时，新的定位修订不阻塞旧版本下正在进行的工作；新版本采用后，新工作项默认绑定新版，旧成果不自动重写。

第 2.3 节的定位草稿是完成这个前置条件的受控入口，不是将社媒项目准入改成可选。

## 6. Agent SDK Session 与上下文

### 6.1 Session 边界

每个工作项拥有独立持久化 Agent SDK Session；项目建立前的定位草稿也拥有自己的独立持久 Session。两者复用同一个 SDK Session 适配器、成果存储与恢复机制，分别由其执行作用域隔离。项目经营资料、成果、权限、预算和连接器授权独立保存，由运行时按请求提供。

不得让整个账号项目共用一个无限增长 Session，也不得把跨项目资料默认加入模型上下文。定位承接后保留原草稿 Session，不将其改名或复制为新选题的 Session。

### 6.2 运行上下文

服务端 RunContext 至少绑定：

- user ID；
- execution scope：按第 2.3 节二选一，定位为 positioning draft ID，项目内工作为 project ID + work item ID；
- 与该作用域匹配的 session ID；
- 当前成果和版本；
- 允许的 Skill 与 revision；
- 用户选择的普通对话模型（适用时）；
- 当前作用域的所有权与能力权限；项目/账号权限仅在实际绑定或采用目标时额外校验；
- 可用连接器及其授权范围；
- 联网允许/禁止状态；
- 计费运行单、预算和调用身份。

这些身份和权限不得由模型自行构造或从用户文本中覆盖。服务端按已持久化的 scope/session 关系解析对象；不存在、跨用户或 scope 混用时拒绝访问，不能仅因 project ID 为空就跳过鉴权。

2026-09-19 批准的全入口上下文规则（适用于普通/新窗口聊天、Skill、定位与工作项入口）：

- 每个相关的 Agent 入口都在**服务端**解析当前授权的用户/品牌/账号上下文，必需的精简上下文自动对模型可见；长历史与成果通过受作用域限制的工具按需读取。不得依赖用户复制粘贴、纯客户端资料传递、可选模型记忆或把全部 Session 合并。
- 已归属的业务记录（有效定位版本、账号策略、已接受选题计划与日期、进度、已保存成果）是权威来源；会话摘要只作补充，不替代权威记录。
- 新工作读取当前适用的已确认版本；已准入的重试保持其原始快照与 request/execution/billing 身份（仍受当前授权与撤回约束）。草稿、假设和另一个账号的策略不会静默变成“当前”。
- 已接受的排期与已验证或用户确认的进度可支持按用户时区生成回访简报；没有完成报告不等于未完成；变更或取消的排期停止过期提醒，历史工作仍可追溯。离站定时通知不在本切片范围内。
- 策略/历史对比只使用实际可得的历史与已批准账号/实验目标，不编造效果数据，也不承诺算法必然成功；重要策略变化仍须显式且有版本。

### 6.3 上下文选择

一次请求的模型输入由以下部分组成：

1. 当前 Agent/Skill 指令；
2. 当前执行作用域 Session 的相关历史；
3. 项目内工作使用精简账号经营资料；定位草稿使用本草稿已知与已确认资料，不要求尚不存在的账号定位；
4. 当前草稿或工作项的简报、成果和来源；
5. 本轮明确读取的其他成果或连接器资料；
6. 用户当前输入。

完整历史长期保存不等于每次全部发送。超出预算时由统一 Session 策略选择最近相关历史，并可使用管理员指定整理模型生成压缩摘要。原文不得因摘要而删除；已撤回或失效内容不得被摘要重新注入。

### 6.4 旧上下文退出条件

统一 SDK Session 在普通 Agent、Skill、恢复、刷新、多标签和断线场景验证通过后，删除旧 `ContextManager`、稳定区/动态区拼接、重复历史读取和旧摘要注入。删除前必须证明新路径覆盖最新消息、不重复、不串工作项且可恢复。

## 7. 模型角色与自动工具选择

### 7.1 模型角色

| 角色 | 选择规则 | 用户是否可改 |
| --- | --- | --- |
| 普通 Agent 模型 | 用户从管理员允许列表中选择 | 是 |
| Skill 执行模型 | Skill/module 的管理员配置 | 否 |
| 整理模型 | 管理员配置，且与对话职责分离 | 否 |
| Fusion 参与/分析/外层模型 | 管理员为套餐或场景配置 | 用户仅开关功能 |

普通对话模型不得被旧“智能路由”静默换成另一型号。模型不可用时明确失败或让用户选择其他允许模型，不使用关键词猜测替换。

### 7.2 Skill 调用

Skill 支持：

- 输入框 Skill 菜单；
- `/` 唤起；
- 技能广场进入并在当前项目/工作项使用；
- Agent 根据意图自动匹配允许的 Skill。

用户显式选择优先。自动匹配只读取 Skill 公开元数据，选中后才按需加载私有方法资源；不得将全部 Skill 正文放入每次上下文。Skill 的私有方法、模型和工具范围由服务器冻结并校验。

### 7.3 联网搜索

不向普通用户提供必须手动切换的“浏览器开关”。Agent 根据任务、时效性和用户指令决定是否调用搜索工具：

- 用户明确禁止联网：本轮不得搜索；
- 用户明确要求最新资料：调用允许工具，或明确说明当前不可用；
- 模型发起搜索前，服务端检查权限、预算和工具配置；
- 返回结果保存来源、时间和成本证据；
- 搜索发生时向用户展示，不得声称未实际发生的搜索。

统一 Runtime 验收后，删除旧正则搜索判断、旧模型升级判断和对应重复配置。

### 8.1 顶部导航


“技能广场”必须位于顶部导航栏，而非左侧主导航，也不得被降级为输入框中的唯一入口。

### 8.2 技能广场职责

技能广场负责：

- 分类、搜索和发现可用 Skill；

技能广场用于发现和了解；输入框用于当前工作中的快速调用。两者共享同一 Skill catalog、权限和发布状态，不维护两份清单。

## 9. 输入框与连接器交互

### 9.1 输入框结构

桌面端推荐：

```text
[＋ 文件/连接器] [Skill]     [普通模型] [多模型智囊团] [语音] [发送]
```

移动端将二级能力放入底部抽屉，但保持同一语义。

`＋` 菜单至少包含文件、图片、最近连接器、添加连接器和管理连接器。Skill 可使用独立按钮或与能力菜单组合，但必须易于发现。

### 9.2 连接器管理

连接器不进入顶层导航。授权、断开、权限说明、默认读写目标和最近同步状态使用输入框弹窗、抽屉或必要的设置子页面完成；OAuth callback 等技术路由不视为产品一级页面。

首批方向：

1. 飞书/Lark；
2. Notion；
3. Slack；
4. 后续按实际用户需求增加其他连接器。

### 9.3 飞书多维表格闭环

第一版飞书连接器必须跑通：

```text
OAuth 授权
→ 用户选择 Base 与数据表
→ Graylum 读取字段
→ 用户映射 Graylum 字段与飞书字段
→ 预览写入
→ 创建记录
→ 后续同步更新同一记录
```

每个同步关系保存 Graylum artifact/version 与飞书记录身份。重复同步应更新而非新增重复行。模型不能自行选择未批准的空间、Base、表或字段。

外部写入默认需要明确动作或已配置的自动同步规则；多个 Fusion 参与模型只能提出内容，外部写操作最多执行一次。

## 10. 多模型智囊团（Gold）

### 10.1 产品行为

管理员配置参与模型数量与型号、分析模型、外层模型、输出上限、允许工具和单次最高预算。用户开启后，各参与模型在隔离上下文中接收同一冻结任务输入。界面提供：

- 最终综合稿；
- 各模型原稿；
- 共识、分歧和风险；
- 实际成功/失败模型状态；
- 本次总积分。

六步定位阶段不让多个模型分别向用户发起多套问答。导师对话保持单一连续体验；智囊团适合在定位候选、内容策略、脚本、标题或评审阶段对同一份已收集资料并行推演。

### 10.2 不可省略的限制

1. **输入一致性**：参与模型真实收到同一 Skill revision、必要资料、用户输入和成果版本；
2. **副作用隔离**：外部写入、发布、付款或发送动作不得在参与模型内执行；
3. **全成本覆盖**：参与模型、分析模型、外层模型、搜索及工具成本全部纳入计费；
4. **部分失败透明**：不把配置数量冒充实际成功数量；
5. **真实对账前不生产收费**：必须完成小额真实调用与供应商账务核对。

### 10.3 Fusion 适配边界

Fusion 当前可作为实现候选，但不得把 Beta 能力当成永久协议。适配层必须保存实际取得的官方响应和 generation 身份；未取得时按第 11.6 节保留未知状态。适配层允许未来替换供应商而不改变 Graylum 项目、成果和账务核心。

若 OpenRouter 只为 Fusion 提供整次请求的权威总成本，则用户按总成本结算；内部模型清单用于展示和质量分析，不自行推导未经官方证明的每模型成本。

## 11. Provider-authoritative 聚合计费

### 11.1 现有基础与新增边界

现有积分余额、积分流水、原子预扣、结算、退费和 AI 成功/失败收口继续使用。新架构只增加多调用聚合和供应商权威成本，不建立第二套余额。

### 11.2 计费运行单

一次用户触发的 Agent 操作创建一个计费运行单，至少包含：

- run ID 与 request ID；
- user ID、execution scope 与 session ID：定位操作绑定 positioning draft ID，项目内操作绑定 project ID + work item ID；
- 模式：普通 Agent、Skill、summary、Fusion、connector 等；
- 预留积分；
- 成本上限；
- 冻结的积分兑换规则与商业倍率；
- 精确供应商成本总额；
- 最终积分；
- 状态与时间。

定位草稿使用同一预留、收据、结算与恢复路径，不建立另一套余额。运行单归属从首次操作起固定；一次定位可以有多张运行单，后续创建一个或多个账号项目仅增加来源关联，不修改历史费用归属、不复制收据或二次结算。定位仍有待核实费用时继续按原运行单处理，不能因承接成功而丢失、重置或假定已结算。

建议状态：`prepared`、`dispatched`、`cost_pending`、`settled`、`refunded`、`unknown`。不得扩展为另一套通用工作流 Harness。

### 11.3 供应商收据

每次实际供应商调用先持久化本地身份，再关联实际取得的收据：

- dispatch 前固定 local call ID、run ID、request ID、调用序号、作用域和预算关联；
- provider、调用账户范围与具体模型；
- 实际返回的 generation/response ID；尚未取得时可为空，不能用本地 ID 冒充；
- 实际取得的官方 cost、cost details、usage、缓存、推理和工具证据；未知不填零或估算值；
- 发送、成功、失败、取消或未知状态，以及已有证据 hash。

本地调用身份唯一，dispatch 前记录失败则不发送请求。取得后的 generation 身份在对应 provider/调用账户范围内唯一，并只能关联一条本地调用；重复回调或恢复不能二次计费。本地持久化不证明供应商已接收、支持幂等或能按本地 ID 查询。

### 11.4 精确金额

供应商成本和聚合使用 PostgreSQL `NUMERIC` 或固定精度整数。应用层在财务路径中传递十进制字符串或整数，不使用 JavaScript `number` 作为权威累计值。

计算顺序：

```text
官方供应商成本精确求和
× 冻结积分兑换比例
× 冻结商业倍率
→ 最后一次进位
→ 用户最终积分
```

不得对每个子调用分别进位后相加，也不得用结算时的最新倍率改写历史运行单。

### 11.5 原子结算

最终数据库 RPC 在一个事务内：

1. 锁定运行单并验证未终结；
2. 验证所需供应商收据完整或使用一个权威 Fusion 总收据；
3. 锁定用户余额；
4. 计算最终积分与预扣差额；
5. 更新余额；
6. 写积分流水和账务历史；
7. 写成本、usage 和运行状态；
8. 必要时保存最终成果关联；
9. 将运行单变为终态。

一个预扣不能同时 settle、refund 和 abort settle。断线、重复回调、页面刷新和多标签必须返回同一结果。

这里的原子性是站内账务事务，不包含外部模型请求，也不宣称供应商 exactly-once；dispatch 后丢失响应的情况按第 11.6 节处理。

### 11.6 成本未知与恢复

延续[既有聊天可靠性边界](../../testing/ordinary-chat-reliability.md)，不预设供应商支持幂等或任意请求查询：

- 已持久化 generation/response ID、但成本暂缺：保留 `cost_pending`，通过已验证的供应商查询能力按原 ID 核对。
- dispatch 后响应丢失，ID 从未返回或未成功持久化：保留 `unknown`、原本地调用、运行单、预留积分、输入及已保存结果；不能查询一个不存在的 generation ID。
- 只有供应商明确支持且已验证按客户端关联键可靠定位原调用时，才可使用 dispatch 前已持久化的关联键补取原 ID/回执。自建 request ID、请求头或相近日志时间不等于这种保证。

没有可靠关联能力或核对仍无证据时，停止自动恢复，在现有账务诊断/人工核对入口保留未决状态和证据缺口。查询应有次数与时间预算；超时、暂时查无记录或经过一段时间都不能证明原调用未执行。迟到可信回执校验关联并去重后，只沿原运行单恢复，不创建第二笔消费。

结果未确认前不得重发原调用、再次预扣或自动释放预留；成本未确认前不得用估算正式结算。不能同时退款与补扣、伪造零成本或把 `unknown` 显示为成功/已退款。可确认未 dispatch 时按既有失败路径释放预留；可确认因故障未交付可用结果时仍适用 Master Plan 的用户全退规则。结果不明不等于确认失败；无证据的人工处置仍需既有授权和账务审计，不能覆盖历史终态。本规格不授权真实退款、补扣或核销。

### 11.7 真实验证

生产开放前，在独立授权的低额度环境中覆盖普通调用和 Fusion：

- 不同参与模型数量；
- 流式/非流式；
- 搜索/无搜索；
- 正常完成、用户取消、部分模型失败、分析失败和断流；
- 响应 usage cost、generation total cost、Graylum 收据和 OpenRouter 余额变化一致；
- 重放、并发、断线和恢复不重复扣费。

第一批账务和第二批 Runtime 的隔离故障注入还必须覆盖 dispatch 前持久化失败、供应商可能接受但无响应 ID、ID 返回后落库失败、无关联查询能力、迟到回执和并发恢复。断言未知调用保留原预留/输入、不重发、不凭超时退款、不伪造零成本；可信回执到达后按原身份至多结算一次。宿主测试不冒充供应商幂等或查询能力证明。

没有这些证据时，Fusion 精准生产计费保持 BLOCKED。

## 12. 历史保存与删除

取消会员等级驱动的聊天历史自动删除。应通过前向修改废弃：

- `history_retention_days` 产品配置；
- `ConversationCleanupService`；
- 对话清理 API；
- Vercel 清理 cron；
- 管理后台入口；
- 相关测试和诊断。

不得删除或重写已经应用的历史 migration；使用前向兼容方式停止运行和移除引用。

继续支持用户主动删除、账号注销、法律删除、OAuth 撤销、临时文件和安全日志生命周期。主动删除必须传播到项目资料、索引、摘要和连接器引用，避免已删除内容通过摘要复活。

- 右侧：成果、资料、来源和版本；
- 底部：统一输入框。

右侧是稳定容器，不因使用普通 Skill、多步骤 Skill、搜索或连接器而整块替换。多步骤状态显示在右侧的进度/成果区域；普通 Skill 不伪造步骤。

六步定位页可采用左侧步骤、中间导师问答、右侧已提取/待确认信息。移动端将辅助区域放入抽屉。

### 13.4 设计规范

- 使用现有 Graylum CSS token、组件和深色金色品牌体系；
- 不在业务组件中散落新的固定颜色、圆角和阴影；
- 金色只用于主要行动、当前状态和关键强调；
- 覆盖 320、768、1024 和 1920 等代表宽度；
- 键盘可完成关键流程，有明确焦点样式；
- 触控目标满足移动端使用；
- 每页具备 loading、empty、error、offline/recovery、permission denied；
- 用户编辑未保存内容时，导航和刷新不能静默丢失；
- 参考 YouMind 等外部产品只借鉴布局和交互层级，不复制品牌与视觉素材。

### 13.5 旧路由迁移

新入口稳定前保留旧地址，并将其重定向到正确项目或新页面。旧深链接不能直接 404。完成真实恢复验证后，删除重复页面和组件。

## 14. 旧架构清理

统一新路径完成前不得先删旧入口。迁移验证后应删除：

- 关键词任务分类与主/助理模型智能切换；
- 正则联网判断与旧搜索旁路；
- 旧 `ContextManager` 和手写滑动窗口；
- 旧 `/api/ai/stream` 编排或其已被统一 Runtime 取代的逻辑；
- 全局聊天和旧工作台主入口；
- 重复 Skill 选择、成果展示和恢复组件；
- 会员历史自动清理服务、API、cron、设置和测试；
- 已无调用方的兼容执行器与配置。

继续保留并复用：

- Skill package、immutable revision 和私有资源读取；
- AI 候选、工作稿、确认快照、来源、版本和报告；
- 用户、项目和成果隔离；
- 现有唯一积分余额、流水与原子 RPC 基础；
- 管理员独立整理模型；
- PR #414 合并的有界 SDK 执行、成果承接和调用身份机制。

每次删除必须以调用方迁移和回归证据为依据，不以文件名或代码年代判断“垃圾”。

## 15. 分批交付与验收

本文只确定顺序，不创建或自动选择新 Launch task。下列七批对应 Master Plan 第 10 节文档阶段之后的第 2–8 项：先账务，再 Runtime，不合并为一个实施批次。两批共用第 2.3 节的最小作用域/调用身份契约，第一批用隔离适配验证钱路，第二批再接持久 Session 与执行。

七阶段现已映射至 [实施任务规格](V3-OPC-implementation.md) 和 [plan-core 依赖图](../plan-core.md)。第一批使用 [V3-BILL-2 开工契约](V3-BILL-2-provider-authoritative-billing.md)，第二批为 `V3-RUNTIME`；任务节点记录已确认工作，不表示授权或完成。以下产品顺序与范围保留。

### 第一批：Provider-authoritative 统一计费

- 计费运行单、供应商收据、精确金额、原子最终结算；
- 定位草稿与项目工作项两种作用域的计费身份契约；
- dispatch 前持久化、无供应商 ID 的未知状态及恢复；
- 隔离的多调用、并发、退款/结算互斥与故障注入验证；
- 不实施完整 Runtime 或启用真实 Fusion 生产收费。

### 第二批：统一 Agent Runtime 地基

- 依赖第一批经验证的账务接口，复用唯一钱路；
- Supabase-backed SDK Session；
- 定位草稿与项目工作项两种明确作用域，共用执行、Session、成果与账务机制；
- 普通 Agent、Skill 和整理模型的统一调用身份；
- 受控工具权限和恢复语义，集成复验第 11.7 节故障场景；
- 不启用真实 Fusion 生产收费。

### 第三批：首条纵向产品链路

```text
零项目新用户从首页建立定位草稿与 Session
→ 六步定位、保存与中途恢复
→ 草稿内确认定位和第一周计划
→ 幂等创建一个账号项目与计划选题
→ 一个选题工作空间
→ 使用一个 Skill
→ 保存成果
→ 刷新与重新登录后找回
```

以下是前三批按各自范围逐步补齐、第三批集成复验的要求，不是本文档已运行的测试：

- 零项目用户首轮问答前已有稳定 draft/session/request/计费身份；失败创建不调用 provider、不扣费，手动填写使用同一草稿机制；
- 中途退出、刷新、重新登录和多标签恢复同一草稿、确认版本及原费用；其他用户或混用 scope/session 的请求被拒绝，草稿不能成为无定位创作旁路；
- 向一个及多个平台账号承接后，每个项目只采用明确确认的来源，每个选题 Session 独立；原定位聊天和费用不复制、不改归属；
- 双击、并发确认和响应丢失后重试返回同一映射，无重复项目、选题、预扣或供应商调用；失败时无半完成项目且草稿仍可恢复；
- 过期确认、确认 ID 与负载不一致、目标账号已存在或正式版本变化时不静默覆盖；账号后续修订不传播到其他项目；
- 草稿已结算及成本待核实的两种情况下，承接均保留原运行单、供应商身份和原结算/恢复路径，不将承接本身作为再次收费操作。

### 第四批：新信息架构与输入框

- 顶部导航含技能广场；
- 项目与工作项路由；
- Skill、连接器、模型和智囊团入口；
- 响应式与可访问性验收；
- 旧路由兼容跳转。

### 第五批：飞书连接器

- OAuth；
- 读取指定资料；
- 多维表格字段映射；
- 写入和幂等更新；
- 解除授权和失败恢复。

### 第六批：Gold 多模型智囊团

- 冻结输入；
- 原稿与综合稿；
- 部分失败展示；
- 官方总成本收据；
- 低额度真实对账；
- Gold 权限和预算。

### 第七批：旧系统收口
