## 2. 两种形态各管什么、谁说了算

| | 策略数据（给 Agent） | 精简正文（给用户） |
| --- | --- | --- |
| 内容 | 第 3 节的固定字段 | 13 章 + 一句话结论，每章"结论 + 理由"，比现在短一半左右 |
| 谁读 | 自由对话、选题、复盘里的 AI 教练；页面画图 | 用户 |
| 权威性 | **后续 AI 判断的依据**（和用户确认过的字段一起） | 解释和说服用，不作为 Agent 的依据 |
| 用户手动修改报告 | 不变（沿用现有规则"手动修改只改报告正文，不改动各步已确认的内容"） | 改的就是它 |
| 评审团修订 | 和正文一起修订、一起采用（第 6.1 节） | 同左 |

和"用户确认过的字段"（`opc_profile`）的关系：**用户确认过的事实以确认字段为准**（例如目标、可投入资源）；
**AI 教练给出的策略以策略数据为准**（例如漏斗怎么分层、第 2 周做什么）。两者冲突时，以确认字段为准，并提示用户"报告里的建议基于旧的确认内容"。
Agent 读取时两份都拿到，各自带来源标签（第 5 节）。

## 3. 策略数据：字段定义、版本和校验

### 3.1 字段（版本 `v: 1`；校验代码放 `packages/api/src/shared/reportData.ts`，前端、服务端、导出共用）

所有文字字段都是纯文字；不认链接、图片、HTML。长度按 Unicode 字符数。

字段按现在报告模板里的**表格和清单的列**来定，不是只挑几项——第 12 节核对时发现，第一稿只给漏斗留 4 个字段，而真实报告的漏斗表每层有 9 列，那样会丢信息。

| 字段 | 内容（对应现在报告里的哪张表或哪个清单） | 对应章节 |
| --- | --- | --- |
| `summary` | 一句话结论 | 一句话结论 |
| `thisWeek[]` | 这周就做的事（现在"第一步"清单，3～8 条），第一条是"最先做的一件" | 一句话结论、运营手册 |
| `situation` | `strengths[]` 能用的优势、`resources` 时间人手预算、`limits[]` 限制、`missing[]` 还缺的信息，每条带 `basis` | 现状盘点 |
| `goal` | `primary` 主要目标、`outcome` 变现背后的结果、`feasibility`（可行 / 有条件 / 暂不建议）、`pros[]`、`cons[]`、`unknowns[]` | 目标和可行性 |
| `audience[]` | 人群表每一列：`name`、`job` 要完成的事、`trigger` 触发时刻、`wallet` 钱包和价格敏感、`whyBuy`、`whyNot`、`contentFit` / `moneyFit`、`basis`（你说的 / AI 推断 / 待验证）、`quote` 代表人物的一句话；另有 `core` 核心人群共同点 | 受众 |
| `platforms[]` | `platform`、`role` 主 / 辅、`reasons[]` | 平台选择 |
| `benchmarks[]` | `platform`、`account`（和宿主对标表同名）、`category`、`takeaway`；数字由宿主填 `metrics`（第 3.3 节）；没有合格对标时 `todo`：搜索词和下一步 | 对标账号分析 |
| `positioning` | `statement`、`value` 核心商业价值、`differentiators[]`（每条带依据）、`notClaims[]` 不能当优势写的、`verdict` | 账号定位 |
| `accountKit` | `hook` 记忆点、`boundary` 扩展边界、`naming` 命名思路、`name`、`handle`、`rejected[]`（名称 + 淘汰理由）、`avatar`、`bio` | 账号三件套 |
| `content` | `formats` 主 / 辅形式、`mix[]` 流量 / 信任 / 转化占比、`pillars[]`、`style`、`cadence` | 内容规划 |
| `topics[]` | 选题清单每一条：`title`、`forWhom`、`pain`、`howToShoot`、`tests` 测什么、`watch` 看什么（最多 12 条） | 内容规划 |
| `roadmap[]` | 起号路线图每一阶段：`stage`、`when`（以条件为准）、`purpose`、`do`、`watch`、`exitWhen` | 运营手册 |
| `plan30[]` | 30 天表每一周：`week`、`purpose`、`posts`、`topics`、`watch`、`reviewQuestion` 周末复盘问什么；另有 `day30Questions[]` | 运营手册 |
| `routine[]` | 每周固定流程：`when`、`task`、`minutes` | 运营手册 |
| `adjustments[]` | "数据怎么看、怎么调"表：`signal`、`meaning`、`action` | 运营手册 |
| `funnel[]` | 漏斗表每一层：`layer`、`role`、`forWhom`、`buyPoint`、`offer`、`price`（文字）、`filter`、`whyFilter`、`howToSell`、`watch`、`basis` | 变现路径 |
| `upgrades[]` | 升级路径：`from`、`to`、`how`、`when` | 变现路径 |
| `income` | `active[]`、`passive[]`、`order` 先做哪层、`formulas[]` 收益公式（文字，不写金额） | 变现路径 |
| `redLines[]` | 全报告的红线，只写一次（现在同一条红线在三四章里重复） | 平台、运营、变现 |
| `compliance[]` | 合规提醒，每条带 `topic`（字体、音乐、肖像……） | 合规提醒 |
| `assumptions[]` | 假设表每一列：`assumption`、`why`、`howToTest`、`signal`、`passIf`、`when`、`ifNot`，按验证先后排序 | 待验证的假设 |

每个文字字段 ≤ 120 字，每个数组有条数上限（照现在模板的上限定，例如人群 ≤ 6、选题 ≤ 12、漏斗 ≤ 6 层）。开工时把每一列的上限写进 `reportData.ts` 并配测试。

刻意不放进数据的：可行性评分、涨粉或收入预测、"多久见效"的时间点（Owner 定过绝不承诺见效时间和收益金额）。
"见效时间"一章只保留文字里的前提条件说明。

整份数据的字数上限由第 9 节的决定确定（核对见第 12 节）。

### 3.2 模型怎么交出来

还是那一次报告调用，模型在正文最后写一个代码块：

````markdown
## 待验证的假设
（精简正文……）

```graylum-report-data
{"v":1,"field":"summary","value":"……"}
{"v":1,"field":"thisWeek","value":["……","……"]}
{"v":1,"field":"funnel","value":[{"stage":"引流","offer":"……","price":"免费","goal":"……"}]}
{"v":1,"field":"plan30","value":[……]}
```
````

- 代码块语言名固定 `graylum-report-data`，**一个字段一行**，每行是一个完整的 JSON 对象。
  原因一：某一行写坏只丢这一个字段，不会连累其他字段；原因二：TS 和数据库的章节检查按 `## ` 行判断，以 `{` 开头的行不会被当成章节标题。
- 为什么不另开一次调用：另开一次就多一次模型调用、多一次冻结和收费，生成时间也更长；一次调用两部分一起写，内容一定出自同一份思路。
- 为什么不用"JSON 严格模式"把全文都变成 JSON：那样正文不能边写边显示（现有的逐字输出会失效），截断时整份作废；
  "正文 + 末尾一行数据"能保留现在的流式体验，截断时正文照常可读。

### 3.3 校验和降级（报告永远不会因为策略数据失败）

宿主在读报告和定稿时用同一个校验函数，输出"清洗后的数据 + 被丢掉的条目清单"：

| 情况 | 处理 | 报告能否定稿 |
| --- | --- | --- |
| 没有数据块（旧 Skill、模型漏写） | 视为"无策略数据"：页面按正文显示；Agent 只读确认字段（和今天一样） | 能 |
| 某一行 JSON 解析不了、`v` 不认识 | 只丢这一行对应的字段；其余照用 | 能 |
| 某个字段解析得了但不合格（超长、缺子项） | Agent 不读这个字段；页面不画图，改成把解析出来的文字按列表显示（只显示文字，不当成数据） | 能 |
| 数组里个别条目不合格 | 丢这几条；剩下的不够最少数量，就丢整个字段 | 能 |
| `benchmarks` 里的账号不在宿主对标表里 | 丢这一条 | 能 |
| 写到一半被截断（`length_limit`） | 数据块不完整 → 无策略数据；照旧按截断规则提示和收费（Owner 10-06 已定） | 照旧（截断本来就不能定稿） |
| 正在生成 | 页面不显示数据块，章节图表位置显示"整理中" | — |

- **正文保底**：模板要求正文对每个清单类字段保留一句话概括（例如"三层：免费模板 → 9.9 元打卡课 → 1999 元陪跑"、
  "4 周：先定人设 → 测 3 种开头 → 固定栏目 → 复盘调整"）。数据整行坏掉时，用户在正文里仍能读到要点，只是没有图；
  Agent 读不到这个字段，回答时按确认字段和正文所在版本说明"报告里这一项没有结构化数据"。
- 服务端完整性检查（TS 和 0206）**不改**，不看数据块。
- 对标数字：定稿时宿主读 `research_benchmark_rows`，**当前表的哈希等于报告冻结的 `benchmarkHash`** 才把粉丝、中位播放、互动率、周更次数、抓取时间填进
  `benchmarks[].metrics`；对不上（之后刷新过对标）就填 `null`，页面和 Agent 都只看到"可以学什么"，不看到对不上的数字。表里的 `null` 保持 `null`，不当 0。
- 定稿前在页面上看到的图，用的是读接口按同样规则临时取的数字。
- 存进版本的是**清洗后**的数据，加上 `dataVersion: 1`、`validatedAt`、`dropped`（被丢掉的字段路径，只有路径没有内容），方便统计合格率。

## 4. 给用户看的呈现

不是把长文美化，而是换一种读法：

1. **顶部"30 秒看懂"卡片**：一句话结论、这周第一步（醒目）、主平台、定位一句话、变现路径缩略（几层、各卖什么）。全部来自策略数据。
2. **目录**：13 章标题，桌面端固定在左侧，手机端收在顶部"目录"按钮里；点哪章跳到哪章；读过的章节变淡色。
3. **每章 = 图表（如果有）+ 精简正文**。正文先写结论和要点；"为什么这么建议"的理由默认收起，点"展开理由"再看。
4. **图表（首版 5 处，Owner 10-17 定；都从策略数据来）**：

| 章节 | 显示成什么 |
| --- | --- |
| 一句话结论 | "这周先做这一件事"醒目卡片（放在 30 秒看懂里）：做什么、为什么、做到什么算完成 |
| 受众 | 人群卡片：是谁、痛点、什么时候买、"内容匹配 / 变现匹配"两个标签、信息来源标签 |
| 对标账号分析 | 横向条形图：粉丝数、近期中位播放；旁边列互动率、周更次数、可以学什么；没数字的只列文字 |
| 变现路径 | 上宽下窄的分层漏斗：每层卖什么、建议价格、目的 |
| 运营手册 | 4 周横排时间线（每周重点、动作、看哪个指标、怎样算过关）+ 指标清单 |

   平台选择、内容规划两章首版不画图（Owner 定首版 5 处），对应字段照样存进策略数据给 Agent 读，页面上是精简正文；以后要不要画见第 11 节。
5. **没有策略数据的报告**（旧报告、数据不合格）：照样有目录（从 `## 标题` 生成），没有卡片和图，正文全文显示。

精简正文怎么"精简"：由报告模板规定（第 7.1 节）。**不靠删内容，靠不重复和换读法**：表格和清单只存在策略数据里（页面从数据画成图表或表格），正文只写结论和理由；每份报告都一样的通用讲解改成页面固定说明。用户默认看到的只有"30 秒看懂"和每章结论（约 1500～2500 字），其余点开才显示。具体字数口径见第 9 节，核对见第 12 节。

## 5. 后续 Agent 怎么读（复用现有机制）

复用自由对话已有的 `read_source` 工作区读取（0218），不新建工具：

- 工作区索引里，每个有策略数据的已确认定位多一条 `kind: 'strategy_report'`（和这份定位同一个 `sourceVersionId`），列在定位后面、账号策略和选题前面。
- 读这一条，返回 `{ kind: 'workspace_source', identity, body }`，`body` 是清洗后的策略数据 JSON（不截断；长度受第 9 节定的数据上限约束，超出说明校验出错，返回 `unavailable`）。
  不和现有的确认字段挤在同一个 4000 字的 `body` 里，免得 JSON 被截断成半截。
- 自由对话的宿主说明（`primaryInstructions.ts` 的工作区段）加一句：问到"下一步做什么、本周计划、变现、要看什么指标、对标"时，读完定位再读它的策略报告；
  回答里说明依据是"第 N 版定位报告"；策略数据和确认字段冲突时以确认字段为准。
- 权限、删除、依赖检查完全沿用：`opc_source_allowed`（本人、已发布、没删除、草稿没撤回）、0218 的依赖复查和删除连带清理。
- 选题和写作等内容流程**不走**上面的自由对话索引，各自在建材料时直接调用 `opc_profile(版本)`，现在有 3 处：
  `opc_topic_bind`（0113，第一周选题的材料 `topic:first-week`）、内容条目的材料投影（0229 的两处）、`opc_business_context`（0139，定位草稿会话的 `businessContext.source.profile`）。
  PR-3 新增一个函数 `opc_source_material(版本)`，返回 `{profile, strategy}`（`profile` 和现在的 `opc_profile` 完全一样，`strategy` 是清洗后的策略数据，没有就是 `null`），

### 12.3 "点开才显示的理由"算不算 12000 字

**算**。"点开才显示"只是页面的显示方式，理由仍是模型写进正文的文字，生成时一样花 token、服务端一样按字数数。所以"读起来少"靠的是页面默认只展开结论，
"字数"的限制管的是模型一共写多少，两件事要分开看。

照这个口径算（策略数据用 JSON，比同样内容的 Markdown 表格多约 0～10%）：

| | 报告 1 | 报告 2 |
| --- | --- | --- |
| 策略数据（原表格和清单） | 约 4000～4500 字 | 约 7500～8500 字 |
| 正文（结论 + 理由，去掉通用讲解和重复） | 约 3500～4000 字 | 约 4000～4500 字 |
| 正文保底的一句话概括（第 3.3 节） | 约 300 字 | 约 500 字 |
| 合计 | 约 7800～8800 字 | 约 12000～13500 字 |
| A（合计 ≤ 12000）要删的个性化内容 | 0 | 约 500～1200 字（再留一点余量就更多） |
| B（正文 ≤ 12000、数据 ≤ 9000）要删的 | 0 | 0 |

### 12.4 替代办法

- 推荐第 9 节的 **B**：数据另算上限，正文不重复数据。原因：A 对内容多的用户恰好最吃亏——信息越多的人，被删的越多；B 的额外费用每份最多约 0.03 美元。
- 不推荐"另开一次模型调用专门出数据"：多一次调用就多一次冻结和收费、多 20～40 秒，两次调用的说法还可能对不上。
- 不推荐"把理由也不计入上限"：理由是模型写的，不计入上限等于不设上限，费用和时间没法预估。
- 无论选哪个，PR-4 真实生成 2 份报告后都按本节的表重新核对一次；核对出要删个性化内容，就不发布新 Skill 版本（按 Owner 10-17"赶不上冻结就不上"的决定处理）。
