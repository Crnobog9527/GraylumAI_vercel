## 3. 现状和关键发现

**仓库里没有事务邮件服务**（2026-10-13 按 staging `f8c24fb2` 核对）：
没有 Resend / SendGrid / Postmark / nodemailer 依赖，没有发信相关环境变量，没有通知或发件记录表，也没有退订字段。
现在所有邮件都由 Supabase Auth 发（注册、验证、重置密码、注销确认 OTP），SMTP 在 Supabase 后台配置，不在仓库里。
给 Owner 的付款告警走 Sentry（`apps/web/src/lib/payment-alert.mjs`），不是邮件。客服工单（`tickets`）也没有邮件通知。

**Stripe 已经替我们发了一部分**：

| 订单类型 | Stripe 自动发什么 | 对本任务的影响 |
| --- | --- | --- |
| MP（国际银行卡）订阅 | Link 发收据、发票、退款通知；**年付订阅在每年续费前必定发一封续费提醒**（默认提前 15 天，可在后台改，最少 7 天，关不掉），后台打开"Upcoming renewals"后每次续费前都发 | 用户本来就会收到 Link 的年度提醒；我们自己的①照常发（见下） |
| 中国大陆银行卡订阅（普通 Stripe） | 后台打开订阅邮件设置里的续费提醒后，Stripe 按设置天数在续费前发邮件（实施时在沙盒复核） | 默认不打开，由我们自己的①发 |
| 微信/支付宝单笔 | 只有付款收据；不续费，Stripe 不会提醒到期 | **② 必须我们自己发** |
| 恢复 Pro、拒付后重订 | Stripe 不知道这些业务规则 | **③④ 必须我们自己发** |

记录 X 已定"银行卡年付续费前提醒和微信创始会员到期提醒共用一套"，所以**默认方案是①②③④都走我们自己的同一套发送机制**
（同一张发送记录表、同样的重试和验收），MP 年付用户会另外收到一封 Link 的年度提醒，内容不冲突。
只靠 Stripe 后台发①、不自己发，是对记录 X 的替代，需要 Owner 明确批准才能用（决定项 N1），本方案不默认采用。

## 4. 设计

### 4.1 发信服务

- 推荐 **Resend**（决定项 N2）：免费档每月 3,000 封、每天 100 封、3 个发信域名；Pro 档 20 美元/月 5 万封
  （[官网价格页](https://resend.com/pricing)，2026-10-13 读取，开工前再核一次）。上线初期提醒量很小，免费档足够。
- 备选：如果 Owner 在 Supabase 后台给 Auth 配的 SMTP 本来就是某家邮件服务，可以直接用同一家的 API，少开一个账号；这需要 Owner 告诉我们是哪家（不需要给密钥）。
- 接入方式：服务端一个很薄的发送模块（`packages/api/src/services/notify/`），只用 HTTPS API，不引入模板框架；
  模板是代码里的纯文本 + 简单 HTML，中英文各一份（语言规则见决定项 N4）。
- 需要 Owner 做的平台事项：注册账号、在 graylum.com 加发信域名的 DNS 记录（SPF/DKIM）、生成 API 密钥并自己放进 Vercel 环境变量
  （新增凭证，AGENTS 第 1 节）。staging 用单独的密钥和单独的子域名（例如 `notify-staging`），只发到测试邮箱。

### 4.2 发送记录（防重复）

- 新表 `payment_notices`：`id`、`user_id`、`kind`（`wallet_expiry` / `restore_pro_expiry` / `dispute_won_resubscribe` 等）、
  `source_ref`（对应订单或订阅的内部编号）、`due_key`（这一次提醒针对的期末日期加档位，如 `2027-03-01:-7d`）、`state`（待发 / 已发 / 明确失败 / 结果未知 / 跳过 / 转人工）、`first_attempt_at`（第一次调用发信服务的时间）、
  `attempts`、`provider_message_id`、`payload_digest`、`template_version`、`created_at`、`sent_at`。唯一键 `(kind, source_ref, due_key)`。
- 第一次发送前固定这封邮件：记下模板版本和"收件人 + 语言 + 渲染后正文"的摘要 `payload_digest`（只存摘要，不存邮箱和正文）。
  重试时用同一模板版本重新生成，摘要不一致（例如用户改了邮箱或语言）就**不再用旧幂等键重发**，转人工核对，避免 Resend 返回 409 或发错人。
- **为什么要新表**（AGENTS 第 5 节）：仓库里没有任何发件记录或通知表；不记录就无法保证"同一时点只发一次"，定时任务重跑或并发时会重复发。
  这张表不存邮箱、不存正文，发送时现读 `profiles.email`。
- 保留：按日志口径最多 30 天后删除（随 #867 的日志清理一起做，决定项 N6）；注销时立即删除该用户的行。

### 4.3 什么时候发（建议值，均为决定项 N3）

| 提醒 | 触发 | 建议时点 | 内容要点 |
| --- | --- | --- | --- |
| ② 钱包创始会员到期 | 微信/支付宝买的 `founder` / `founder_renewal`，会员期末将到 | 到期前 7 天、到期当天、宽限期第 5 天（宽限截止前 2 天） | 到期日、按 496 美元续买一年的入口、宽限截止日，过了就失去创始身份 |
| ②′ 钱包普通 1 年会员到期 | 微信/支付宝 1 年 Pro/Gold | 到期前 7 天（是否要做见 N3） | 到期日、续买入口 |
| ③ 恢复的 Pro 即将到期 | Pro 升 Gold 退款后恢复的 Pro 期限 | 原到期日前 7 天 | 原 Pro 不会自动扣费，需要的话自己重新订阅 |
| ④ 拒付判赢后重订 | CHARGEBACK 判赢解冻后 | 解冻当时一次 | 订阅已停，不会自动扣费，需要的话自己重新订阅 |
| ① 银行卡年付扣款前 | MP 和大陆卡的年付订阅（含创始年付），没有停止续费 | 扣款前 7 天（建议值） | 扣款日、金额（不含税的标价，MP 另加税）、怎么取消 |

- 定时：挂在现有每天 04:00 的 `billing-reconcile`（`route.ts` 已经用 `Promise.all` 并跑几项）或 03:00 的 `release-subscription-credits` 上，
  不新建定时任务。每天扫一次"未来 N 天内到期"的订单，生成待发记录再发送，失败的下次重试，最多 3 次后标失败并发 Sentry 告警。
  每次发送都把这条记录的 `id` 作为发信服务的幂等键（Resend 的 `Idempotency-Key` 请求头，[官方说明](https://resend.com/docs/dashboard/emails/idempotency-keys)：保留 24 小时，重试时正文必须相同），
  超时等结果不确定时用**同一个幂等键**重试，供应商不会重复投递；超过幂等键有效期仍不确定的，转人工核对，不再自动重发。
  区分两种失败：发信服务明确拒绝（4xx 且有错误码，例如参数或域名错误）记"明确失败"，修好原因后可以重试；5xx、超时或连接中断都记"结果未知"，
  只在 `first_attempt_at` 起 24 小时内用同一个幂等键重试，过了 24 小时转人工。因为定时任务每天只跑一次，"结果未知"的重试**在同一次任务里做完**：
  现有两个定时入口的执行时限只有 60 秒，还要做别的账务工作，所以同一次任务里只做短重试（例如等 5 秒、15 秒各一次，并按剩余时间判断，不够就不试）；
  仍不确定的立即转人工并发 Sentry 告警，后台提供"用同一幂等键重新发送"按钮，管理员在 24 小时内点一下即可，不靠第二天的定时任务。
- 发之前再核一次：已经续费、已经退款、已注销、被拒付冻结的不发（标"跳过"）。
- 每封只发给账号本人的登录邮箱；没有邮箱（例如注销中）就跳过。事务邮件不需要退订链接，但每封底部写"这是关于你的订单的通知"。

## 7. 验收（Stripe 测试模式 + 测试邮箱）

- **正常**：MP 和大陆卡年付测试订阅用测试时钟推到扣款前 7 天 → 收到①；用测试时钟和支付宝测试付款造出将到期的创始订单 → 到期前 7 天、当天、宽限第 5 天各收到一封；恢复 Pro 场景收到一封；
  MP 年付订阅在沙盒打开续费提醒后，测试时钟推进时 Stripe 产生续费提醒事件（沙盒不真发邮件，只核对设置和事件）。
- **⑤ 创始身份结束**（必做，F2 已采用）：测试时钟让创始身份结束 → 当天收到一封，重复扫描不重发；`frozen` 不发。
- **人工重发**：模拟一次结果未知 → 后台出现重发按钮 → 管理员点击后用同一幂等键发出、只收到一封；非管理员调用被拒绝；超过 24 小时按钮不可用。
- **④ 模板**：直接调用"判赢后重新订阅"发送函数 → 测试邮箱收到一封，同一拒付调两次只发一封。
- **重复**：同一天定时任务跑两次、两个实例并发跑 → 每个时点只发一封（唯一键挡住）。
- **并发**：用户在发信前一刻续费 → 发信前复核，标"跳过"、不发。
- **失败**：发信服务返回错误或超时 → 记失败、下次重试、3 次后告警，不阻塞同一批其他提醒；结果不确定（超时、没拿到 `provider_message_id`）时用同一幂等键重试，测试确认供应商只投递一封；超过有效期转人工；两次尝试之间用户改了邮箱或语言 → 摘要不一致，转人工、不重发。
- **隐私**：表里没有邮箱和正文；注销后该用户的行被删除；staging 只能发到测试邮箱白名单。
