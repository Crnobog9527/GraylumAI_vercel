# PAY-DISPUTE-GUARD 实施方案（high，仅方案）

状态：2026-10-13 第一版，**仅方案**。本次只新增本文，不写代码、不建迁移、不调用 Stripe、不读取密钥。
需要 Owner 决定的事项列在第 8 节，由总控转交。判输后的扣回、申诉材料导出、限制反复拒付仍归上线后的 CHARGEBACK，不在本任务。

## 1. 要做到什么、怎样算做完、不做什么

- **要做到**（第 51 项记录 X、Z、AC、AD）：收到拒付通知后，按被拒付的那笔付款：
  ① 记录拒付，不能忽略；② 先冻结、可以撤回——订阅冻结这份订阅的付费权益、暂停以后的积分发放，并冻结这份付款已发放还没用完的积分；
  钱包一次性会员冻结这一期权益（1 年期还暂停以后按月发放的积分）；积分包冻结这个包里没用完的积分；都不动其他来源；
  ③ 同时停止这份订阅的自动续费，拒付期间不再扣款；④ 通知 Owner 人工处理（记录 Y：所有拒付都不自动接受）。
- **怎样算做完**：第 7 节验收通过；同一拒付事件重复或乱序到达结果不变；冻结可以由管理员撤回且撤回后数字对得上。
- **不做**：判输扣回、判赢后的逐期补发、申诉材料导出、反复拒付限制、账单商户名（都归 CHARGEBACK）；Radar 和"提前欺诈预警"
  （Owner 2026-10-12 前期不做 Radar）；自动接受或自动反驳拒付。

## 3. 现状和关键发现

**代码**（staging `f8c24fb2`）：

- Stripe 回调 `apps/web/src/app/api/stripe/webhook/route.ts` 不处理 `charge.dispute.*`，落到 `default` 直接返回 200。
- 没有拒付记录表，没有任何"冻结积分 / 冻结权益"机制。唯一相关的是退款前的保护：订单已被拒付时禁止退款
  （`refundPolicy.ts:17,82`、`packageRefund.ts:69`、`subscriptionRefundPreview.ts:127`、`monthlyRefundProvider.ts:104`、`0185:34`）。
- Stripe 回调没有按事件编号去重的表，靠各业务对象自己的唯一键（Waffo 有 `waffo_event_receipts`）。
- Waffo 拒付查询（GraphQL `chargebacks`）方案里写了，**代码里从来没做**；`waffoReconciliation.ts` 只查付款和退款。

**三条通道的拒付各不相同**：

| 通道 | 谁处理拒付 | 我们会收到什么 | 对本任务的含义 |
| --- | --- | --- | --- |
| MP（国际银行卡） | Stripe 是记录商户，自己审核、自己提交证据、**认为赢不了时可能直接接受**；我们也能在后台自己接受或反驳（反驳要付举证费） | 标准 `charge.dispute.*` 事件（MP 下是否完全一样**未实测**，见第 7 节第一条） | 冻结和停续费照做；"不自动接受"对 MP 只能约束我们自己，管不了 Stripe（决定项 D2） |
| 中国大陆银行卡订阅（普通 Stripe） | Graylum 是卖家，Owner 在 Stripe 后台人工应对 | 标准 `charge.dispute.*` 事件 | 完整适用 |
| 微信/支付宝单笔 | Stripe 文档写明没有会导致扣回款项的拒付流程 | 正常不会收到 | 代码按同一套处理，收到就照常冻结并告警 |
| Waffo 旧订单 | Waffo，无回调，只能查询 | — | 见 4.6 |

**外部发生的退款和取消**（不是拒付，但会和拒付交织）：MP 下 Link 客服 60 天内可以给用户退款，Stripe 找我们 48 小时没回复时可以不经同意直接退；

## 4. 设计

### 4.1 事件和动作

| Stripe 事件 | 动作 |
| --- | --- |
| `charge.dispute.created` | 找到对应订单（4.2）→ 写拒付记录 → 冻结（4.3）→ 停止续费（4.4）→ Sentry 告警给 Owner（含举证截止日 `evidence_details.due_by`）→ 站内提示用户 |
| `charge.dispute.updated` | 更新状态和截止日（按 Stripe 事件时间单调合并：已结案的 `won` / `lost` / `warning_closed` 不会被迟到的 `updated` 改回未结）；如果冻结和停续费还没做（例如 `created` 延迟或丢失），先补做同一套冻结和停续费 |
| `charge.dispute.funds_withdrawn` / `funds_reinstated` | 在资金流水里各记一行（金额、时间、结算交易编号，按事件编号去重），不改冻结 |
| `charge.dispute.closed`（`won` / `lost` / `warning_closed`） | 记结果并告警；冻结和停续费还没做的先补做；**冻结保持**，等管理员处理：赢了由管理员点"撤回冻结"（本任务提供），输了的扣回等 CHARGEBACK（上线前由 Owner 人工按记录 Z/AC 处理） |

- 去重分两层：**事件**按 Stripe 事件编号 `event.id` 去重（同一拒付的多次 `updated` 是不同事件，都会被处理），并保存每个拒付最后合并到的事件时间，
  用于单调合并；**副作用**（冻结、停续费、告警）按"拒付编号 + 动作"做幂等键（沿用 `credit_transactions.idempotency_key` 的做法），重复或乱序到达不会冻两次。
  任何一个拒付事件先到，都会先补建记录并执行"确保已冻结、已停续费"这一步（已做过就跳过），不依赖 `created` 一定送达。
- 串行化：拒付处理和这笔付款的发放（首次付款、续费）在**同一个付款编号**上用同一把锁——事务开头按 Stripe 付款编号取
  `pg_advisory_xact_lock`。锁键必须两边一致：一律先把各自手上的编号（拒付给的 charge、续费给的 invoice、首次付款给的结账会话）
  解析成同一个**规范付款键**——`商户命名空间 + 模式（test/live）+ PaymentIntent 编号`（作用域写法沿用 `stripeReferences.ts:9-16`、`0204:7-10`），
  再由它算出锁键；`payment_disputes` 也存 `merchant_namespace`、`mode` 和这个规范键，拿到锁后**重新检查**对方的记录。这样两边同时进行时，后拿到锁的一方一定能看到先提交的那一方，
  不会出现"拒付查不到订单、付款也查不到拒付"、双方各自提交的情况。
  **订阅还要一把订阅级锁**：拒付针对上一期、下一期续费同时到账时，两期付款编号不同，付款级锁互不阻挡。所以订阅的续费发放和拒付处理
  还都要先取同一把按订阅编号算出的 advisory lock（加锁顺序：先订阅、再付款），拿到锁后续费发放先查这份订阅有没有冻结中的拒付：
  有的话，这一期付款按"付款成功但本站不发放"处理（沿用 2026-10-12 决定的做法：不开通、不发积分、立即确认停续费，这笔钱按原规则全额退款），
  并告警 Owner；它是一笔独立付款，不会被并入上一期的冻结，也不会让用户付了钱却一直拿不到服务（决定项 D6）。
  拒付到达时如果下一期已经发放完：下一期是一笔独立且没被拒付的付款，它的积分和会员权益都**照常保留**（被拒付的上一期已经结束，
  记录 X 的"冻结会员权益"对它已经没有可冻的期限）；只冻结上一期剩下的积分、停止以后的续费，并告警 Owner 核对（决定项 D6）。
  **人工退款也用这把锁**：`pay_common_monthly_refund_claim`（把来源改成 `reversed`）和退款失败后的恢复 `pay_common_monthly_refund_finish`（0194:152-159，把积分加回、来源改回 `granted`）
  都先取同一把付款级锁，拿到锁后再查有没有拒付：claim 时已有拒付就拒绝退款；退款失败恢复时如果中途来了拒付，就把来源恢复成"拒付冻结中"、
  加回的积分计入冻结额，而不是恢复成可用的 `granted`。
  **积分包退款同样处理**：`pay_common_package_refund_claim`、退款结果处理和重试（`0185_pay_common_package_refund.sql`，失败恢复在 `:202-210`）
  也先取同一把规范付款锁、拿到锁后查拒付；claim 时已有拒付就拒绝，退款失败或取消要恢复积分时如果中途来了拒付，恢复的积分计入这个包的冻结额，不变成可用。
  **外部退款（Link 代退款、后台直接退款，`charge.refunded` / `refund.*`）也用这把锁**：处理器拿到锁后先查这笔付款是否冻结中；
  是的话在同一事务里把冻结额直接转成退款扣回（冻结账目标为"已被退款取代"，不再另扣一次），并认得"拒付冻结中"的来源状态、不因此报错。
  这个处理器由 MP 窗口在 PR-3 写；PR-D1 合并时由本任务把加锁和冻结转换补进去（MP 窗口届时已停写；没停写就请它顺带加）。
- 找不到对应订单：拒付记录写成"待匹配"并告警，回调返回 200。Stripe 不保证事件顺序（[官方说明](https://docs.stripe.com/webhooks#event-ordering)），
  对应的付款或续费可能还没处理完，所以"待匹配"不是终点：之后每次收到这个拒付的 `updated` / `closed`，以及每天 04:00 的 `billing-reconcile`，
  都重新查找订单，找到后立即补做冻结和停续费（同样按幂等键，不会冻两次）。只有管理员核实确属站外付款（或订单已按退款结束）后才把它标成"已结案"；
  超过 24 小时仍待匹配的再告警一次。
  **付款或续费回调本身也要主动认领**：首次付款发放（`pay_waffo_fulfill_payment`）和 Stripe 续费发放在写订单映射、开通权益和发积分的**同一个事务里**，
  先查有没有指向这笔付款的"待匹配"拒付；有的话当场建立冻结和停续费标记，再提交，不让权益和积分先被用起来。
  这两处是支付发放代码，由 PR-D1 在 MP 窗口停写之后加入（或请 MP 窗口顺带加一个调用点），见第 5 节。数据库暂时出错返回 500 让 Stripe 重试。

### 4.2 从拒付找到订单

拒付带 `charge` 和 `payment_intent`（新版接口里 `payment_intent` 可能为空，要再取一次 charge）。
单笔（钱包、MP 积分包）按结账会话/付款编号对到 `payment_orders`；订阅按 charge → 发票 → 订阅对到 `user_subscriptions` 和这一期的订单。
具体用哪几个字段由 MP 窗口 PR-3 定下的映射为准，本任务复用同一个查找函数，不另写一套。

### 4.3 冻结（可撤回）

- **权益**：在会员事实函数（`pay_common_membership_facts`，0214）里加一个条件——**按期判断，不按整份订阅判断**：只有当前生效的那一期（它对应的付款订单）本身有"冻结中"的拒付时，才视为没有付费权益；被拒付的是已经结束的上一期、当前这一期是另一笔已开通的付款时，当前权益不受影响（与 4.4 和 D6 一致）。
  年付按月发放时，被拒付的是这笔年付，它覆盖的整年都算被拒付的期限。
  不改订阅本身的期限和状态，撤回冻结后自动恢复，不需要补写期限。
- **以后的积分发放**：月付续费已经因为停续费不会再发生；年付按月发放和钱包 1 年期按月发放的定时任务（03:00）跳过"冻结中"的来源。
  只在扫描时跳过不够：扫描（例如 `pay_waffo_release_due` 选候选）在加锁之前，扫描后拒付才冻结的话，已选中的那一期仍会发出去。
  所以冻结检查要放进**实际发放的函数里**（`pay_waffo_grant_period`、Stripe 年付按月发放的 SQL），在它们现有的加锁顺序下、拿到锁之后再查一次，
  冻结中就不发；拒付冻结也按同一顺序加锁。
  撤回后按原发放日补发由 CHARGEBACK 负责（记录 AD），上线前由管理员撤回时手动触发一次补发检查。
- **已发放、没用完的积分**：按这笔付款的积分来源算出还剩多少，用一条"拒付冻结"账目把它从可用余额里扣出来（不删），撤回时写一条反向账目还回去。
  只动这一个来源，不动其他来源（记录 Z、AC）。订阅积分的剩余量复用已有的 `subscription_credit_grants.consumed_amount`，不新建第二本账。
  读剩余量、写冻结账目（以及撤回时写反向账目）必须在**同一个数据库事务**里完成，并沿用现有消费路径的加锁顺序
  （先锁 `profiles`，再锁 `subscription_credit_grants`，见 `0053_refund_1b_consumed_amount_termination.sql:24-26`），
  这样用户同时在用积分时不会按过期的余量多冻，撤回时也不会把已经用掉的积分还回去。
- **冻结之后的消费也要绕开这个来源**：只从余额里扣出冻结额还不够——现在的扣费函数 `atomic_pre_deduct`
  （`0061_refund_1b_expired_quarantine_repair.sql:183-222`）会从任何 `status='granted'` 的来源里扣，冻结后用户用"其他来源"的积分，
  账目仍可能记到被冻结的来源上，之后撤回或别的来源退款就会多还或多扣。所以 PR-D1 要给来源加一个冻结状态
  （例如在 `subscription_credit_grants` 上增加"拒付冻结中"的状态或标记），并让**新的预扣跳过冻结中的来源**；
  撤回冻结时把状态改回原值、按反向账目还回余额。
  **冻结前已经预扣、冻结后才结束的在途调用**：结算和恢复（`atomic_settle` / `atomic_refund`）仍按调用原来绑定的来源
  （`chargedGrantId`、`amountToPeriod`）逆向处理，不跳过、不改记到其他来源；如果因此有积分退回到被冻结的来源，
  在同一事务里把这部分加进冻结额（冻结额 = 冻结时剩余 + 之后退回到这个来源的量），实扣多于预扣时，超出的部分仍记在原来源上（`atomic_settle` 现在就是这样做，`0057_refund_1b_actual_refund_accounting_repair.sql:137-148`），
  这部分其实是从已冻结的剩余里用掉的，所以在同一事务里**把冻结额减去同样的量**，不能从总余额里再扣；冻结额不够减时，超出部分按现有规则从其他余额扣，
  并标记人工核对。这样其他来源不会被多扣，之后撤回也不会多还。**BILL-PAYG 的整轮补偿**（`0162_bill_payg.sql` 的 `bill2_payg_compensate`）不经过 `atomic_settle` / `atomic_refund`，会直接改来源和余额，
  而且只认 `granted` / `reversed` 两种状态：PR-D1 要同时改它——认得"拒付冻结中"的来源，补偿回到这个来源的积分同样计入冻结额，不变成可用余额。
  这会改 BILL2 的扣费核心函数，属于高风险改动，须按 AGENTS 第 4 节补并发测试。
- **积分包**：现在的积分包发放（`0211:216-222`）只加进总余额和流水，**没有记"这个包还剩多少"**；PAY-COMMON PR-5 只通用化订阅来源，也不会补上。
  而"冻结这个包里没用完的积分"是已定承诺（第 51 项记录 Z），所以**逐包的来源记录是本任务的硬前置**：单独一个 PR-D0（high，BILL2 核心），
  让每个积分包像订阅一样成为一个来源（发放时建来源、扣费和退回记到具体来源上），并补并发测试。PR-D0 合并之前 PR-D1 不开工，不留"只告警不冻结"的降级做法。
- **订阅的跨期积分也要记到来源上**：积分永不过期，但现在的 `atomic_pre_deduct`（`0061:183-222`）只给当前有效期内的来源增加 `consumed_amount`，
  用掉过去各期剩余积分的那部分（`v_to_other`）没有记到任何来源上，于是已经结束的分期看起来还有剩余。被拒付的如果是已结束的分期，
  按 `credits_granted - consumed_amount` 去冻就会冻到别的付款的积分。所以 PR-D0 同时要让**所有订阅分期的跨期消费都记到具体来源**，
  并给已有来源补一次核对（算不清的已有来源标记为"来源不明"，这些来源被拒付时按"来源数据异常"处理：不冻积分、只告警）。
- **来源数据异常时**（例如来源记录损坏，不是设计内的情况）：一律不冻积分、不扣总余额，只标记人工核对并告警，绝不用其他来源的积分顶上。
- 冻结期间：禁止对这笔付款再发起退款（已有保护）；不禁止用户用其他来源的积分。

### 4.4 停止续费

- MP 和大陆卡订阅：调用 MP 窗口 PR-4 提供的"期末停止"入口（`cancel_at_period_end=true`），读回确认；
  判赢后**不自动恢复**扣费（记录 AD），提醒用户自己重新订阅（PAY-NOTIFY ④）。
- 推荐用"期末停止"而不是"立即取消"：权益已经冻结，立即取消会触发 `customer.subscription.deleted` 走到期结束流程，撤回冻结时就恢复不了这一期（决定项 D3）。
- 调用失败或结果不确定：先读订阅实际状态再决定是否重试，最多 3 次，仍失败就告警人工处理（AGENTS 第 3 节）。

### 4.5 和外部退款、取消同时发生

| 情况 | 处理 |
| --- | --- |
| 已经被 Link 代退款的付款又被拒付 | 记录拒付并告警，不再冻结已收回的积分（MP PR-3 已收回），由 Owner 在后台核对是否双重扣款 |
| 拒付冻结中又收到 Link 代退款（`charge.refunded`） | 按外部退款处理（收回积分、结束这一期），同时把冻结账目改为"已被退款取代"，避免重复扣 |
| 用户在 Link 自己取消、或 Stripe 因删除数据取消订阅 | 冻结照常；停续费这一步发现已经取消就直接记"已停止" |
| 创始会员被拒付 | 冻结期间按 PAY-FOUNDER 决定项 F5 处理徽章和展示；判输结束创始身份归 CHARGEBACK，名额不放回 |

### 4.7 新表

`payment_disputes`：`id`、`provider`、`provider_dispute_id`（和 `merchant_namespace`、`mode` 一起唯一）、`merchant_namespace`、`mode`、`payment_key`（规范付款键 = 命名空间 + 模式 + PaymentIntent 编号，加索引；付款级锁、付款回调认领、每日重查都只用它）、`provider_charge_id`、`provider_payment_intent_id`、`provider_invoice_id`（原始编号留作核对）、`last_event_at`（单调合并用）、`order_id`、`subscription_id`、`amount`、`currency`、`reason`、`status`、
`evidence_due_by`、`opened_at`、`closed_at`、`outcome`、`freeze_state`（冻结中 / 已撤回 / 已被退款取代）、`renewal_stop_state`。

每个拒付事件在合并状态之前先在同一事务里写入这张表，写不进去（已经有了）就说明是重复投递：只跳过**状态合并**，不跳过未完成的动作——仍按拒付记录上的 `freeze_state`、`renewal_stop_state`
把没做完的冻结和停续费接着做完，全部完成才返回 200。每日 04:00 对账也会重查"冻结中但停续费未确认"的拒付并补做。
资金动作另记一张流水 `payment_dispute_fund_events`（每个事件一行）：拒付编号、动作（被银行扣回 / 返还）、金额、币种、发生时间、
Stripe 的结算交易编号和事件编号（唯一，防重复）。`funds_withdrawn` 和 `funds_reinstated` 都写这里，不覆盖拒付主记录，三年后仍能说清钱是怎么走的。
**为什么要新表**（AGENTS 第 5 节）：现在没有任何地方记拒付；冻结要能撤回，就必须有一条能对上"冻了谁、冻了多少、撤回没有"的记录。
这是账务记录，按 3 年保留，只存白名单字段（不存原始事件全文、不存原因描述以外的自由文本）。
- **到期清理**：三张表（拒付主记录、资金流水、事件回执）加入账务记录的 3 年到期清理（从交易年度结束起算，和其他账务记录一起做，按 2026-10-12 决定这项清理在上线后实施）；
  先删事件回执和资金流水、再删拒付主记录；还没结案的拒付只是暂停删除，结案后仍按原来的交易年度期限算（已经过期的就在下一次清理时删），不重新起算 3 年。
- **注销**：三张表只有内部编号、金额、时间和 Stripe 编号，没有个人内容，注销时按账务记录保留（和 `payment_orders` 同样处理）；
  PR-D1 同时把这三张表加进 DATA-ERASURE 的财务字段白名单（文档同步）。

## 7. 验收（Stripe 测试模式）

- **先验证一件没测过的事**：在沙盒用 Stripe 的拒付测试卡（官方测试卡清单里的 dispute 卡）分别付一笔 MP 订阅和一笔大陆卡订阅，
  确认 MP 下确实会发出 `charge.dispute.created/closed`，以及字段（`payment_intent`、发票关联）和普通 Stripe 是否一样。不一样就先回来改方案。
- **正常**：MP 订阅、大陆卡订阅、MP 积分包、钱包 1 年期各造一次拒付 → 权益立即失效、余额里只有这笔来源被冻、其他来源可用、订阅变为期末停止、Owner 收到告警；
  管理员撤回 → 权益和积分恢复，数字和冻结前一致；订阅保持停止续费。
- **重复和乱序**：同一 `created` 投递两次、`closed` 先到 → 只冻一次，记录完整。
- **并发**：拒付和续费发票（`invoice.paid`）、拒付和 Link 代退款（`charge.refunded`）同时到达 → 不重复扣、不漏冻，按 4.5 的结果；
  用户正在消耗积分时同时冻结、同时撤回 → 冻结量等于当时真实剩余、撤回不会还回已消耗的部分，余额前后能对上。
- **在途调用**：调用先预扣（绑定到这个来源）→ 拒付冻结 → 调用失败退回 / 少扣结算 → 退回的积分回到原来源并计入冻结额，其他来源不变、总数对得上。
- **到期清理**：把时间推过 3 年 → 已结案的三张表记录按先回执和流水、后主记录的顺序被删除；未结案的保留；原期限已过才结案的，结案后下一次清理就删（不重新起算）。
- **未开通的下一期退款**：上一期冻结后下一期扣款成功 → 发起全额退款并读回确认；退款接口超时 → 先查实际状态，不重复退；退款失败 → 告警。
- **只冻被拒付的那一期**：下一期已开通后上一期被拒付 → 会员事实函数仍返回有权益；当前期本身被拒付 → 返回无权益。
- **跨期积分**：上一期剩余的积分在本期被用掉一部分 → 上一期被拒付 → 只冻上一期真实剩下的部分，其他付款的积分不动。
- **停续费中途中断**：冻结已提交、调用 Stripe 停续费前进程退出 → 同一事件重投时补做停续费；没有重投时每日对账补做。
- **重复投递**：同一 `event.id` 投递两次（包括进程重启后）→ 第二次直接返回 200，不重复合并。
- **多次 `updated`**：同一拒付先后收到两条不同的 `updated` → 两条都处理，最后状态和截止日以较新的一条为准。
- **资金扣回和返还**：先 `funds_withdrawn` 再 `funds_reinstated`、重复投递 → 流水里正好两行，金额和时间都对。
- **外部退款和拒付同时处理**：`charge.refunded` 和 `charge.dispute.created` 同时到达 → 无论先后，同一笔积分只收回一次，冻结账目和退款扣回不重复。
- **积分包退款中途来拒付**：积分包退款已 claim → 拒付到达 → Stripe 退款失败或取消 → 恢复的积分计入冻结额，不能再被用掉。
- **退款中途来拒付**：人工退款已 claim → 拒付到达 → Stripe 退款失败、执行恢复 → 来源变成冻结中，积分不变成可用。
- **按月发放和冻结同时发生**：发放任务已选中某一期、同时拒付冻结 → 这一期不发出，或发出后计入冻结额，不会变成可用余额。
- **整轮补偿**：预扣并结算 → 拒付冻结 → 整轮确认失败走 PAYG 补偿 → 补偿成功、不报 `BILL2_COMPENSATION_GRANT_UNRESOLVED`，补回的积分计入冻结额。
- **上一期拒付、下一期续费同时到**：上一期的拒付和下一期的 `invoice.paid` 同时处理 → 下一期不开通、不发积分、进入全额退款并告警；下一期先发完的 → 下一期的会员和积分照常可用，只冻上一期剩余积分并停续费。
- **付款和拒付同时处理**：两个事务同时开始 → 无论谁先提交，最后都是冻结状态。
- **多笔同额付款**：同一用户两笔同金额付款，其中一笔先被拒付（待匹配）→ 只有那一笔的付款回调认领到它，另一笔正常开通。
- **迟到的 `updated`**：`closed`(won) 先处理、较早的 `updated` 后到 → 状态仍是 `won`。
- **只收到 `closed`**：`created` 没送达、直接收到 `closed` → 冻结和停续费照样补上。
- **超额结算**：预扣 → 冻结 → 实际用量大于预扣量 → 冻结额相应减少、其他来源不变，撤回后总数对得上。
- **先拒付后付款**：拒付事件先到、付款回调后到 → 付款回调提交时已经是冻结状态，用户从没拿到可用的权益和积分。
- **冻结后继续用其他来源**：冻结后用户消费、调用失败恢复积分、撤回冻结 → 被冻结来源的 `consumed_amount` 一直不变，消费和恢复都记在其他来源上；
  撤回后再对其他来源退款，数字仍然对得上。
- **乱序**：拒付先于付款或续费回调到达 → 先记"待匹配"；付款或续费回调的事务提交时就已经冻结并停续费（不等后续事件或每日对账）。定时重查只用于验证"之后一直没有付款回调"的记录会被再次告警。
- **失败**：停续费接口返回错误 → 读回实际状态后重试，最终告警；找不到订单 → 记录并告警、返回 200；数据库出错 → 返回 500、Stripe 重试后结果一致。
- **来源保护**：争议积分包已用完、账号只剩其他来源积分时 → 冻结 0、其他来源一分不动；积分包还剩一部分时 → 只冻这个包剩下的（依赖 PR-D0 的逐包来源）。
- **其他**：冻结期间对这笔付款发起退款被拒绝；创始会员被冻结时 PAY-FOUNDER 的状态函数按 F5 结果返回。
