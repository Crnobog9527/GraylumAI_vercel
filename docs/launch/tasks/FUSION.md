## 实现机制（从规划正文移来）

- **不用 OpenRouter 的 Fusion**，由 Graylum 自己并行调用；现有适配器也拒绝 `openrouter/` 开头的元模型，并要求返回模型等于请求模型。
- **并行方式**：现有 BILL2 一次执行里的调用是串行的，时间预算在最坏情况下只够约 2 次真实调用；每个模型需要一次独立执行，放在挂在主会话下的附属会话里（会话同一时间只允许一个执行），输入是从主会话冻结的同一份快照。
- **评审模式**：先并行跑 N 个评审执行，再跑一次汇总执行（输入 = 评审 Skill + 原报告 + 全部评审意见）。
- **对比模式**：并行跑 N 个执行；第一版不开放任何工具，需要的资料由宿主在开始前读好并冻结进同一份快照；用户选中一个回答时，宿主把"这一轮的用户请求 + 选中的回答"作为明确的采用动作写回主会话历史（不调用模型、不收费、按请求 ID 幂等）；对比开始时冻结主会话历史版本，采用时主会话已有新轮次就不直接追加，改为让用户把选中的回答引用到新消息里或放弃。
- **上下文容量**：Skill 加资料放不进某个参与模型的上下文窗口时，在扣费前拒绝该模型。

## 计费运行单：整组一个

保留 BILL2 技术契约"一次用户收费操作一个运行单、汇总后只取整一次"（契约第 36、77–78 行）：整组 Fusion 只开一个运行单，只预扣一次，各模型的调用都登记在这一个运行单上，最后汇总结算、只取整一次。不采用"每个模型一个运行单"：那样每个模型各自取整，三次 0.0001 美元的调用会扣 3 积分而不是 1 积分，也和契约冲突。

这需要扩展 BILL2：多个执行向同一运行单登记调用（调用序号原子分配、可并行派发）；运行单内区分"成功 / 确认失败 / 结果未知"；支持部分结算，使某个模型结果未知时只保留它的预扣，其余部分先结算并退回。实施时同步修改 BILL2 技术契约里"Fusion 部分模型失败"一行。属于高风险。

## 预扣估算

- 每个模型的上限 = 本次冻结输入的 token 数 × 输入单价 + 回答长度上限 × 输出单价（来自该模型已批准的报价）。token 数用与供应商一致的方式计算并留余量，计算方式随运行单冻结。
- 评审模式里汇总修订那一次的输入在开始时未知，按"评审 Skill + 原报告 + 各评审模型回答长度上限之和"估算；实际输入只用于结算和上下文校验。
- 这套估算规则在 RUNTIME-PROD 里统一实现，普通调用和 Fusion 共用，Fusion 直接复用。

## 必测项清单（来自 2026-09-27 Codex 审查和 Fable 评估，PR #448）

1. 多个模型并行时不会因为"会话同一时间只允许一个执行"而在准入时失败。
2. 整组只有一个运行单、只预扣一次、汇总后只取整一次，不会因各模型分别取整而多收。
3. 汇总修订那一次的预扣上限在开始时可计算，且不会不够用。
4. 对比结果的采用：主会话已有新轮次时不直接追加，上下文顺序不会错乱。
5. Fusion 结果、备选回答和附属会话数据接入账号注销流程（依赖 DATA-ERASURE）。
6. 某个模型"结果未知"时，其他模型的结算和退款不被卡住，页面显示被冻结的积分。
7. 确认失败的调用不向用户收费；供应商仍然收费时，成本入账由平台承担。
8. 退款发生时存在未结算的 Fusion 运行：结算后金额守恒。
9. 月度积分释放发生在预扣和结算之间时结算正确。
10. 权限在服务端检查：没有权限的会员不能通过接口直接发起；会员降级后新发起的按新等级判断，进行中的照常完成并结算。
