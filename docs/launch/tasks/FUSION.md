## 实现机制（从规划正文移来）

- **来源**（Owner 2026-09-30 修订 D12）：评审模式不联网，只用前面已收集的资料。首选 OpenRouter 的 Fusion 服务端工具（`openrouter:fusion`），放在只给评审用的专用 workspace 里，禁用 `web_search` 和 `web_fetch`；实测不通过就用备选方案，由 Graylum 自己并行调用。对比模式由 Graylum 自己并行调用。开工前必须实测的五项见 [Master Plan 第 4.3 节](../MASTER_PLAN.md#fusion)。现有适配器拒绝 `openrouter/` 开头的元模型，并要求返回模型等于请求模型；服务端工具不是元模型，实施时核对这两条检查。实测通过、采用首选方案时，在该实施 PR 里同步修改 `docs/ENGINEERING.md` 第 6 节"多模型由 Graylum 自己并行调用、不使用 `openrouter/` 元模型"这一句（按治理变更由 Owner 批准）；采用备选方案则不用改。
- **并行方式（对比模式和评审备选方案）**：现有 BILL2 一次执行里的调用是串行的，时间预算在最坏情况下只够约 2 次真实调用；每个模型需要一次独立执行，放在挂在主会话下的附属会话里（会话同一时间只允许一个执行），输入是从主会话冻结的同一份快照。
- **评审模式（首选方案）**：一次评审执行里，Agent 调用一次 Fusion 服务端工具（评审团 3–8 个模型，评审提示词由宿主固定写进请求内容，输入是同一份冻结快照：报告和前面已收集的资料），得到各模型的评审意见和分析；再由汇总模型按评审 Skill 合并修改清单、写出修订稿。修订稿再交给下一轮 Fusion 复核，直到没有评审模型提出关键修改，或达到后台设定的轮数上限。Fusion 每次请求只能调用一次，所以每一轮是一个独立请求；整组各轮仍登记在同一个运行单上。宿主在每轮的 Fusion 调用里把 `max_tool_calls` 显式设成最小值 1，不依赖默认值，并随运行单冻结。评审里的每一个调用都不联网：发起 Fusion 的外层请求只带 `openrouter:fusion` 这一个工具，不沿用普通 Runtime 的工具白名单；汇总修订调用不带任何工具。
- **评审模式（备选方案）**：复用对比模式的多模型并行调用。每一轮 N 个评审执行拿同一份冻结快照（评审 Skill、报告、前面已收集的资料）并行评审；评审和汇总调用都不带任何工具，不沿用普通 Runtime 的工具白名单；再跑一次汇总执行，由汇总模型按评审 Skill 完成分析、合并意见、写出修订稿；多轮直到达成共识或到轮数上限。
- **评审输出形式**：两种方案下，评审模型都只输出修改意见清单（位置、问题、建议），不重写全文；每份意见的长度上限由后台设置，随运行单冻结；评审模型和分析模型不写修订稿；每一轮的修订稿只由汇总模型（首选方案里是外层模型或汇总模型）写一份。首选方案里，这个上限对应 Fusion 的 `max_completion_tokens` 或同等参数，由宿主显式设定；按官方文档，这个参数是每一次内部评审团和分析模型调用的最大输出，包含思考 token，所以它同时作用于分析模型，预扣估算里的"分析模型回答长度上限"在首选方案下取同一个值。预扣估算里的"评审团回答长度上限""评审回答长度上限"就是这个意见长度上限。
- **对比模式**：并行跑 N 个执行；第一版不开放任何工具，需要的资料由宿主在开始前读好并冻结进同一份快照；用户选中一个回答时，宿主把"这一轮的用户请求 + 选中的回答"作为明确的采用动作写回主会话历史（不调用模型、不收费、按请求 ID 幂等）；对比开始时冻结主会话历史版本，采用时主会话已有新轮次就不直接追加，改为让用户把选中的回答引用到新消息里或放弃。
- **上下文容量**：Skill 加资料放不进某个参与模型的上下文窗口时，在扣费前拒绝该模型。评审模式另外准入时按每一步最坏情况的合计上下文检查，口径和预扣估算一致（每次读取的输入上限 + 回答长度上限）：覆盖首选方案的评审团、分析模型、外层请求的两次读取、汇总修订，以及备选方案的评审和汇总修订。装不下就先按规则调低上限，仍装不下就在预扣前拒绝，并告诉用户原因。

## 计费运行单：整组一个

保留 BILL2 技术契约"一次用户收费操作一个运行单、汇总后只取整一次"（契约第 36、77–78 行）：整组 Fusion 只开一个运行单，只预扣一次，各模型的调用都登记在这一个运行单上，最后汇总结算、只取整一次。不采用"每个模型一个运行单"：那样每个模型各自取整，三次 0.0001 美元的调用会扣 3 积分而不是 1 积分，也和契约冲突。

这需要扩展 BILL2：多个执行向同一运行单登记调用（调用序号原子分配、可并行派发）；运行单内区分"成功 / 确认失败 / 结果未知"；支持部分结算，使某个模型结果未知时只保留它的预扣，其余部分先结算并退回。评审模式用首选方案时，结算单位是一次 Fusion 调用（整体成功 / 整体确认失败 / 整体结果未知），不是 Fusion 内部的各个模型；用备选方案时和对比模式一样按模型。实施时同步修改 BILL2 技术契约里"Fusion 部分模型失败"一行。属于高风险。

## 预扣估算

- 每个模型的上限 = 本次冻结输入的 token 数 × 输入单价 + 回答长度上限 × 输出单价（来自该模型已批准的报价）。token 数用与供应商一致的方式计算并留余量，计算方式随运行单冻结。对比模式按这一条估算。

### 评审模式

**总规则**：估算的单位是**实际发出的每一次模型读取**。每次读取的费用上限 = 输入上限 × 输入单价 + 回答长度上限 × 输出单价。
- 下面列出的调用只是已知的最低清单。实现时凡是清单之外的读取（重试、工具多轮、宿主补发等），一律按上限加进估算；不能确定上限的调用，不允许在评审模式里发出。
- 输入上限 = 这次调用实际放进上下文的每一项的上限之和；回答按宿主设定的回答长度上限计算，思考（reasoning）token 也算在回答里；Fusion 的 `max_completion_tokens` 等长度参数由宿主显式设定，不依赖默认值。
- 会调用工具的模型（包括 Fusion 工具，以及首选方案里被禁用的联网工具）每多一次工具调用就多一次读取：后一次读取的输入 = 前一次的全部输入 + 前一次的工具调用参数（按工具调用参数的长度上限）+ 工具结果（按结果外壳和内容的上限；工具被拒时是失败结果外壳的上限）。
- 一轮的全部调用加起来，再乘以轮数上限，另加固定余量（和 RUNTIME-PROD 的统一估算规则一致）。所有长度上限、`max_tool_calls`、轮数上限和单价都由宿主设定，并随运行单冻结。实际 token 数只用于结算和上下文校验，不用于预扣。

**"报告"这一项**：第 1 轮按原报告长度；第 2 轮起按 max(原报告长度, 汇总修订的回答长度上限)，因为修订稿可能比原报告长。

**首选方案（OpenRouter Fusion，联网已禁用）每一轮的调用**：
1. **评审团每个模型**（共 N 个）：联网工具被禁用后，模型仍可能尝试调用一次并收到失败结果，所以按"`max_tool_calls` + 1 = 2"次读取估算；没有联网内容，也没有联网费用。
   - 第一次：输入 = 评审提示词和评审 Skill + 报告 + 已收集的资料 + 工具定义和消息外壳；回答 = 评审团回答长度上限（这次可能是工具调用参数，也可能直接是评审回答）。
   - 第二次：输入 = 第一次的全部输入 + 工具调用参数上限 + 工具失败结果外壳上限；回答 = 评审团回答长度上限。
2. **分析模型**：同样按 2 次读取估算，没有联网费用。
   - 第一次：输入 = 分析模型自己的提示词 + 评审提示词和评审 Skill + 报告 + 已收集的资料 + 各评审团回答长度上限之和 + 工具定义和消息外壳；回答 = 分析模型回答长度上限。
   - 第二次：输入 = 第一次的全部输入 + 工具调用参数上限 + 工具失败结果外壳上限；回答 = 分析模型回答长度上限。
3. **发起 Fusion 的外层请求**，分两次读取：
   - 第一次（发出 Fusion 工具调用）：输入 = 评审提示词和评审 Skill + 报告 + 已收集的资料 + Fusion 工具定义和消息外壳；回答 = 工具调用参数的长度上限。
   - 第二次（工具结果返回后）：输入 = 第一次的全部输入 + 工具调用 + 工具结果（各评审团回答长度上限之和 + 分析模型回答长度上限 + 工具结果外壳）；回答 = 外层请求的回答长度上限。
4. **汇总修订**：输入 = 评审 Skill + 报告 + 已收集的资料 + 各评审团回答长度上限之和 + 分析模型回答长度上限 + 工具结果外壳；回答 = 汇总修订的回答长度上限。如果宿主让发起 Fusion 的外层模型直接写修订稿（第 3、4 项是同一次调用），就不再单独算第 4 项，但第 3 项的第二次读取必须包含两项里的全部内容，回答按两者中较大的上限；第一次读取照常计入。

每一轮 = N × 第 1 项 + 第 2 项 + 第 3 项 + 第 4 项。

**备选方案（自己做，不带工具）每一轮的调用**：每次调用只读一次。
- **每个评审模型**：输入 = 评审 Skill + 报告 + 已收集的资料；回答 = 评审回答长度上限。
- **汇总修订**：输入 = 评审 Skill + 报告 + 已收集的资料 + 各评审回答长度上限之和；回答 = 汇总修订的回答长度上限。
- 每一轮 = N × 评审模型 + 汇总修订。

每轮的输入不带上一轮的评审意见；实现时如果要带，就把它按上限加进对应调用的输入。

- 这套估算规则在 RUNTIME-PROD 里统一实现，普通调用和 Fusion 共用，Fusion 直接复用。

## 必测项清单（来自 2026-09-27 Codex 审查和 Fable 评估，PR #448）

1. 多个模型并行时不会因为"会话同一时间只允许一个执行"而在准入时失败。
2. 整组只有一个运行单、只预扣一次、汇总后只取整一次，不会因各模型分别取整而多收。
3. 评审模式的预扣上限在开始时可计算（首选方案和备选方案分别验证），按轮数上限把每一轮的全部调用（首选方案：评审团、分析模型、外层请求、汇总修订；备选方案：评审模型、汇总修订）都算进去，多轮评审跑满轮数也不会不够用；修订稿长于原报告时预扣仍够用；汇总修订的输入包含分析模型的结构化输出；按上面每一项上限算出的预扣，在所有项目都取到上限时仍够用；外层请求的两次读取都计入；工具调用被拒后的第二次读取包含工具调用参数和失败结果；用一次完整评审的请求日志核对，每一次实际发出的模型读取都能对应到估算里的一项。
4. 对比结果的采用：主会话已有新轮次时不直接追加，上下文顺序不会错乱。
5. Fusion 结果、备选回答和附属会话数据接入账号注销流程（依赖 DATA-ERASURE）。
6. 对比模式：某个模型"结果未知"时，其他模型的结算和退款不被卡住，页面显示被冻结的积分。
7. 确认失败的调用不向用户收费；供应商仍然收费时，成本入账由平台承担。评审模式用首选方案时按整次 Fusion 调用判断：整体成功按官方总成本收费，整体确认失败不收费，整体结果未知冻结这一次调用的预扣、核实后再处理；用备选方案时按模型逐个判断。
8. 退款发生时存在未结算的 Fusion 运行：结算后金额守恒。
9. 月度积分释放发生在预扣和结算之间时结算正确。
10. 权限在服务端检查：没有权限的会员不能通过接口直接发起；会员降级后新发起的按新等级判断，进行中的照常完成并结算。
11. 评审模式的多轮循环在达成共识或到达轮数上限时停止；单次请求里第二次调用 Fusion 被拒绝（`fusion_invocation_capped`）时按失败处理，不无限重试。
12. 首选方案：每次 Fusion 调用作为一个整体结算，OpenRouter 只返回总成本时按总成本一次结算，不自行拆分各模型成本；总成本和分项同时出现且矛盾时不结算（BILL2 技术契约第 71 行）。
13. 评审提示词在每个评审团模型上都生效：实测每个模型的评审意见都按评审 Skill 的检查项给出。
14. 首选方案：每轮 Fusion 调用都显式设定 `max_tool_calls` 为 1，发出的请求里能看到这个值；外层请求只带 `openrouter:fusion` 一个工具，汇总修订调用不带工具；整次评审里的每一个调用（外层请求、评审团、分析模型、汇总修订）都没有发生搜索和抓取（用量里 `web_search_requests` 为 0，也没有抓取记录），整次调用正常返回。
15. 备选方案：评审模式发出的每一个请求（评审和汇总修订）都不带任何工具，整次评审不发生联网调用。
16. 最坏合计上下文超出某一步模型窗口时，在预扣前拒绝或调低上限，不会在评审团跑完后才失败。
