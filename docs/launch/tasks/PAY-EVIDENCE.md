# PAY-EVIDENCE 实施方案（high，仅方案）

状态：2026-10-13 第一版，**仅方案**。本次只新增本文，不写代码、不建迁移、不调用 Stripe、不读取密钥。
**保留期限必须由 Owner 定**（第 7 节 E1），在 Owner 批准并同步修订 DATA-ERASURE 之前，不开始采集任何 IP 或设备信息（第 51 项记录 W A ③）。

## 1. 要做到什么、怎样算做完、不做什么

- **要做到**：用户主动结账时，记下少量"是本人操作"的技术证据（IP、浏览器标识等），用于反驳"盗刷 / 我没买过"类拒付；
  到期自动删除；接入账号注销清理。
- **怎样算做完**：第 6 节验收通过；DATA-ERASURE 的保留和清理契约已按 Owner 定的期限修订并合并；证据和账务记录分开存放。
- **不做**：条款版本和订单同意（已在收款核心 `payment_orders.terms_version` / `terms_accepted_at`，0204:156-157）；
  设备指纹、第三方指纹或风控服务（Owner 2026-10-12 明确前期不做 Radar 规则）；申诉材料一键导出（上线后 CHARGEBACK）；
  续费时的证据（续费是 Stripe 自动扣款，没有用户在场，关联原订单的证据即可）。

## 2. 依据

- MASTER_PLAN 第 2.1 节第 51 项记录 W（A ③：IP、浏览器、设备不进收款核心同意记录，PAY-EVIDENCE 定留存、DATA-ERASURE 改契约之后才采集）；第 7.1 节 PAY-EVIDENCE 行。
- [DATA-ERASURE](DATA-ERASURE.md) 第 3.1 节财务字段白名单："IP/UA……必须清掉（有具体争议保全需求须另批）"；2026-10-12 保留期决定（日志最多 30 天、账务 3 年、同意记录 1 年）。
- Stripe 官方 [How Managed Payments works](https://docs.stripe.com/payments/managed-payments/how-it-works) "Dispute support"：
  MP 订单由 Stripe 处理拒付、自己提交证据、**不会向我们要补充证据**；我们也可以在后台自己反驳（要付举证费）。

## 3. 现状和关键发现

- 付款相关**目前不存任何 IP 或浏览器信息**。下单限流读 `x-vercel-forwarded-for`（`packages/api/src/services/stripe.ts:24-35`）只给 Upstash 用，不落库。
- 其他地方已有 IP/UA 列（`user_activity_logs.ip_address`、`invitation_records`、`ai_usage_logs`），都不是付款证据，不复用：
  它们各有自己的清理规则，混用会让保留期变得说不清。
- **证据对哪类订单有用**：
  - 中国大陆银行卡订阅（普通 Stripe）：Graylum 是卖家，拒付要我们自己应对，**证据最有用**。
  - MP（国际银行卡）：Stripe 代处理、不找我们要证据；只有 Owner 想在后台自己反驳时才用得上。
  - 微信/支付宝单笔：Stripe 文档写明没有会导致扣回款项的拒付流程（PAY-WAFFO 第 2 节已核实），**基本用不上**。

## 4. 设计

### 4.1 采集什么（最少够用）

只在用户点"去付款"、服务端创建订单的那一刻采集一次：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| IP 地址 | Vercel 请求头 `x-vercel-forwarded-for`（取第一个） | 拒付表单里的"购买时 IP"，Stripe 可据此和发卡地区比对 |
| IP 所在国家/地区 | Vercel 请求头 `x-vercel-ip-country` | 判断是否异地，不调第三方定位服务 |
| 浏览器标识 User-Agent | 请求头，截断到 512 字符 | 说明设备类型 |
| 浏览器语言 | `accept-language`，截断 | 辅助 |
| 采集时间、订单内部编号 | 服务端 | 和订单、同意记录对上 |

不采集：设备指纹、屏幕分辨率、Cookie 标识、精确地理位置、卡信息（卡信息只在 Stripe）。

采集范围（决定项 E2）：推荐 **所有银行卡订单（MP 和大陆卡）**，钱包单笔不采集。理由：大陆卡必须；MP 保留 Owner 自己反驳的可能；钱包没有拒付流程，采了也用不上。

### 4.2 存在哪里

- 新表 `payment_order_evidence`：`order_id`（主键，关联 `payment_orders`）、`ip`、`ip_country`、`user_agent`、`accept_language`、`captured_at`、`expires_at`、`hold_reason`（有未结拒付时延长）、`pending_delete_at`（两步删除的"待删除"标记时间，见 4.3）。
- **为什么不放进 `payment_orders`**（AGENTS 第 5 节）：订单是账务记录，按 3 年保留，DATA-ERASURE 白名单明确不许带 IP/UA；
  单独一张表才能按更短的期限删掉，不碰账务。普通用户和前端都读不到这张表，只有服务端和管理员后台可读。

### 4.3 保留和删除（建议值，Owner 定）

- 卡组织的拒付期限一般是交易后 120 天左右，个别原因可到 540 天（参考值，开工前按 Stripe 文档复核）。
- **从没付款成功的订单**（结账被放弃、失败或过期）：没有交易，证据没有用处。建议在订单关单（`closed_unpaid`）时同一事务里删掉证据；
  万一漏删，清理任务按"创建后 7 天仍没有付款"兜底删除（建议值，决定项 E1 一并定）。
- 建议 **A**：付款成功的订单保留到"这笔订单最后一次扣款后 540 天"（订阅每次续费成功时顺延 `expires_at`），有未结拒付时延到拒付结束后 90 天；到期删除整行。
- 备选 **B**：保留到"最后一次扣款后 180 天"（覆盖大部分拒付，隐私更好，个别晚到的拒付没有证据）。年付订阅要到第 365 天才第一次续费，按 B 会在续费前就删掉证据，所以**选 B 时年付订阅仍按 A 保留**（到首次续费之后再顺延）。
- 保全由拒付流程负责写：PAY-DISPUTE-GUARD 收到拒付（任何第一个拒付事件）时，在同一事务里给这笔订单的证据写 `hold_reason`。
  证据只挂在用户亲自结账的那张订单上；续费会另生成一张订单，并通过 `source_order_id` 指回最初的结账订单，
  所以续费被拒付时、续费成功顺延 `expires_at` 时，都要**沿 `source_order_id` 找到最初那张订单的证据行**再操作；
  同一个订阅的多期续费共用最初那一行证据，可能同时有好几笔未结拒付，所以**保全不靠单个标记**：
  清理任务删除前直接查 `payment_disputes`，只要还有任何一笔指向这行证据（沿 `source_order_id`）且没有结案的拒付，就不删；
  `hold_reason` 只作说明。清理和保全要串行，而且不能靠行锁（清理先锁住、删掉并提交后，等着的一方就锁不到任何行了）：两边都先取**同一把 advisory lock**，
  键由最初结账订单的编号算出，这把锁和证据行是否还在无关。拒付流程在写拒付记录之前就取这把锁；清理任务取到锁后再查一次有没有未结拒付，有就不删。
  拒付处理已经开始、但比清理晚拿到锁的情况也要保住证据，所以**删除分两步**：清理第一次看到到期且没有未结拒付时，只给这一行标上
  "待删除"（记下标记时间，内容不动）；至少 24 小时后的下一次清理再取锁、再查一次，仍没有未结拒付才真正删除。期间来了拒付就清掉"待删除"标记。
  一次回调处理只需要几秒到几分钟，24 小时足够让已经开始的拒付事务提交。每笔拒付结案或被退款取代时，把 `expires_at` 设为"该笔结案时间 + 90 天"和原到期时间中较晚的那个（只往后推，不往前改）。
  两个任务谁后合并，谁负责把这个调用点接上，并跑下面的跨任务验收。
- 删除执行：挂在现有每天 05:00 的 `account-erasure` 或 #867 的日志清理（迁移 0226）上，分两步执行：`expires_at` 已到且没有未结拒付的行先写 `pending_delete_at`；只有 `pending_delete_at` 已满 24 小时、
  取锁后再查仍没有未结拒付的行才真正删除（最终删除条件是 `pending_delete_at`，不是 `expires_at`）。来了拒付就把 `pending_delete_at` 清空。不新建定时任务。

### 4.4 账号注销时（决定项 E3）

- 建议 **A**：注销时删除，**除非**这笔订单有未结拒付（那时保留到拒付结束后 90 天再删）。注销路径（`account_erasure_local_cleanup`）
  也用 4.3 的同一把 advisory lock 和同样的两步删除：注销时只写 `pending_delete_at`（证据从此不再出现在任何查询结果里），24 小时后由清理任务按同一规则真正删除，
  这样注销和第一个拒付事件同时发生时证据也能保住。隐私优先，和"注销清用户 IP/UA"的现行规则一致，只多一个有具体争议时的例外（正是 DATA-ERASURE 白名单写的"有具体争议保全需求须另批"）。
- 备选 **B**：注销后照常保留到 4.3 的期限（防止有人先注销再拒付），要在隐私条款里写明。
- 不论选哪种，都要改 `account_erasure_local_cleanup`（0191:317 起）和 DATA-ERASURE 文档的清理契约；库外删除清单（#869）不涉及，因为证据只在数据库里。

为什么要同一事务：请求结束后 IP 和浏览器信息再也拿不回来，如果先放行订单再补写，失败的那笔会永久缺证据。
因为这一步落在建订单的 SQL（`pay_waffo_admit_purchase`）或紧挨着它的服务端入口里，属于支付代码，必须由 MP 窗口顺带做或等它停写后再做。

采集开关默认关闭（`system_settings`），PR-E1 和 DATA-ERASURE 修订都合并后才在 staging 打开。

## 6. 验收（Stripe 测试模式 + 本机数据库测试）

- **正常**：MP 和大陆卡测试结账各一次 → 表里各一行，字段正确，`expires_at` 按批准的期限；钱包结账 → 不采集（如按推荐）。
- **重复**：同一订单重复提交（收款核心返回同一订单）→ 证据仍只有一行，不覆盖第一次的记录。
- **并发**：同一用户两个标签页同时下单 → 每个订单各一行，不串。
- **失败**：请求头缺失 → 写空值、照常下单；证据写入失败 → 订单和结账会话都不创建、返回可重试的错误、Sentry 告警（保证每笔银行卡订单都有证据）；开关关闭时不写任何数据。
- **拒付保全（跨任务）**：造一笔拒付 → 证据写上保全、原到期时间到了也不删 → 拒付结案 → 结案后 90 天内仍在、之后被删除；被退款取代时同理。
- **没付款的结账**：结账放弃 / 失败 / 过期关单 → 证据随即删除；关单没触发时 7 天后被清理任务删除。
- **到期和注销**：测试时间推过 `expires_at` → 定时清理删掉；有未结拒付的不删；注销按批准的规则删或留；普通用户接口读不到这张表。
- **续费顺延**：测试时钟续费成功 → 最初结账订单那一行的 `expires_at` 顺延。
- **注销和拒付同时发生**：注销清理和第一个拒付事件同时处理 → 证据只被标为待删除，拒付提交后标记清掉、证据保留。
- **清理和拒付同时发生**：证据刚好到期，清理先拿到锁、拒付事务已开始但晚拿到锁 → 这一轮只标"待删除"，拒付提交后标记被清掉，证据保留；没有拒付的，24 小时后才真正删除。
- **两笔续费拒付重叠**：第二、三期先后被拒付 → 第二期先结案 → 证据仍保留（第三期未结）→ 第三期结案后 90 天才删。
- **续费被拒付**：第二期续费被拒付 → 最初结账订单的证据被保全、不被清理，结案后 90 天再删。
